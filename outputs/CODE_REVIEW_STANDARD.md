# Tide 代码审查标准与流程（v1.0）

> 适用仓库：`coustea/AI-Agent`（tide）
> 生效范围：`cmd/`、`internal/` 全部 Go 代码、`Makefile`、`.github/`、`outputs/` 设计文档
> 维护者：仓库维护者；本标准自身修订走 T0（纯文档）流程
> 制定依据：2026-10 两轮全仓评审（`CODE_REVIEW_2026-10-18.md`、`CODE_REVIEW_R2_2026-10-18.md`）与 D1–D13 加固实施过程

---

## 一、为什么需要这套机制：现状诊断

代码质量"参差不齐"不是态度问题，是**缺少让质量可判定的结构**。当前仓库有四个具体缺口，每一个都能用数据或历史缺陷证明。

### 1.1 机器门禁是失效的

| 项 | 现状 | 后果 |
|---|---|---|
| CI Go 版本 | `.github/workflows/ci.yml` 固定 `1.24`，`go.mod` 要求 `1.26.2` | `go test` 在 setup 阶段即报 `go.mod requires go >= 1.26.2`，**CI 从未真正守护过代码** |
| 静态检查 | 无 `golangci-lint` 配置，CI 不跑 `go vet`、不跑 `gofmt -l` | 未使用变量、错误的 `fmt` 动词、未格式化代码可静默合入 |
| 竞态检测 | 从未跑 `-race` | `agent` 的 `running` 标志、`tui` 的 `mdCache` 这类并发点无保护 |
| 覆盖率 | 无门槛、无报告 | 新增代码可以零测试合入 |

### 1.2 审查靠记忆，不靠清单

两轮评审发现的问题集中在**同几个域反复出现**，说明不是随机失误：

- 安全域：`sh -c "rm -rf ~/data"`、`xargs rm`、`python -c "shutil.rmtree"` 连续绕过审批
- 生命周期域：中断留下残缺 `tool_calls`、全链路零超时、零 `recover`
- 契约域：`reasoning_content` 被回灌出站、`nil *Client` 被包成非 nil 接口
- 前端域：全局单值 `currentAPIKey` 依赖 6 处手工清空

这些都是**有清单就能在合入前拦下**的类型，而不是需要天赋才能发现的类型。

### 1.3 严重度无统一口径

同一份代码里"必须改"和"建议改"混在一起，导致：阻断项被当成风格意见忽略，风格项被当成阻断项反复拉扯。评审报告里 P0/P1/P2 的划分是对的，但没有落成**可执行的处置规则**（谁在什么时限内做什么）。

### 1.4 缺陷修完不沉淀

D1–D13 修了 13 类问题，但修复本身没有被转成"下次自动拦住"的资产：没有对应的 lint 规则、没有进入清单、部分只有一次性断言。**同一个坑可以再踩一次**。

### 1.5 规模事实（决定了审查强度该放在哪）

| 包 | 生产行 | 测试行 | 测试/生产 | 审查权重 |
|---|---:|---:|---:|---|
| `internal/tui` | 3043 | 1345 | 0.44 | **最高**（占生产代码 37%） |
| `internal/agent` | 977 | 1474 | 1.51 | 高（状态机 + 生命周期） |
| `internal/tool/builtin` | 950 | 488 | 0.51 | **最高**（沙箱与命令执行） |
| `internal/permission` | 713 | 379 | 0.53 | **最高**（安全边界） |
| `internal/gateway` | 587 | 733 | 1.25 | 高（协议与网络） |
| `internal/config` | 586 | 215 | 0.37 | 中（上帝包倾向） |
| `internal/memory` | 378 | 309 | 0.82 | 中（轮次原子性） |
| `internal/middleware` | 340 | 47 | **0.14** | 中（落盘策略，测试薄弱） |
| `internal/tool` | 280 | 302 | 1.08 | 中 |
| `internal/protocol` | 230 | 0 | — | 高（契约，改动即跨端） |

## 二、审查体系：四层防线

机器能判的，绝不占用人；人能判的，必须有清单；清单判不了的，交给架构审查。

```text
┌──────────────────────────────────────────────────────────────┐
│ L0 机器门禁   格式 / vet / 测试 / 竞态 / lint / 构建矩阵        │  无例外，红即阻断
├──────────────────────────────────────────────────────────────┤
│ L1 作者自审   变更分级 + 分域清单勾选 + 验证命令留痕            │  PR 描述即证据
├──────────────────────────────────────────────────────────────┤
│ L2 同行审查   正确性 / 安全 / 测试有效性 / 分层依赖             │  按严重度出结论
├──────────────────────────────────────────────────────────────┤
│ L3 架构审查   契约变更 / 跨包依赖 / 并发模型 / 删除公共 API     │  仅 T3 触发
└──────────────────────────────────────────────────────────────┘
```

| 层 | 谁执行 | 拦什么 | 何时执行 | 不通过的处理 |
|---|---|---|---|---|
| L0 | CI + 本地 `make verify` | 编译、格式、单测、竞态、lint、跨平台构建 | 每次 push / PR | 作者修，不得 `--no-verify` 绕过 |
| L1 | 作者 | 是否触发设计文档、清单逐项、验证结果 | 提交 PR 前 | 补做，不进入 L2 |
| L2 | 至少 1 名审查者 | P0/P1 缺陷、测试是否真的能失败 | PR 打开后 | 打回修订 |
| L3 | 维护者（T3 时 2 人） | 设计合理性、边界是否被穿透、是否留兼容层 | 设计文档阶段 + 合入前 | 退回设计 |

## 三、严重度分级：唯一的判定口径

**判定原则（一句话）**：用户能否感知到"坏了"或"危险了"→ P0/P1；只是"以后会难改"→ P2；只是"看起来不顺手"→ P3。

| 级别 | 定义 | 典型情形（本仓库语境） | 处置 | 是否阻断合入 |
|---|---|---|---|---|
| **P0** | 安全边界失效、数据丢失/污染、进程崩溃、凭据泄漏、契约破坏导致跨端不可用 | 权限闸门可绕过；沙箱可被软链穿透；密钥写入日志；`protocol` 字段语义变更未同步 TUI；中断后会话永久 400 | **本轮必须修**，禁止"下个 PR 修" | 是，无豁免 |
| **P1** | 常见路径功能失效、缺兜底导致挂死、错误被吞、关键路径无测试、引入兼容层/死代码 | 无超时；`recover` 缺失；`err` 被 `_` 丢弃；新工具无表驱动用例；为旧实现保留别名 | 合入前修；确有客观原因可**书面豁免**（PR 内记录理由 + 跟进 Issue 编号） | 是（除非书面豁免） |
| **P2** | 性能热点、可维护性缺陷、可观测性不足、重复实现 | 每事件全量重写文件；同一路径判定有 5 处实现；日志缺关键字段 | 记入 backlog，指定跟进人 | 否 |
| **P3** | 命名、注释、局部风格、可读性 | 变量名不达意；注释复述代码 | 作者自行决定 | 否 |

### 3.1 分级判定树

```text
这条意见会导致……
├─ 用户数据被破坏 / 越权执行 / 凭据外泄 / 崩溃 / 跨端契约不一致？
│   └─ 是 → P0
├─ 常见操作路径结果错误 / 可能永久挂起 / 错误无法归因 / 改动无测试守护？
│   └─ 是 → P1
├─ 功能正确但实现会显著拖慢后续修改（重复、耦合、状态双份、无日志）？
│   └─ 是 → P2
└─ 其余 → P3
```

### 3.2 分级的三条纪律

1. **P0 不允许"顺手改"**：P0 必须单独提交、单独说明根因、带回归用例。混在大改动里会掩盖根因。
2. **P1 豁免必须留痕**：豁免只能由维护者在 PR 中书面给出，格式 `豁免 P1：<理由> / 跟进：#<issue>`。口头同意无效。
3. **P3 不得反复提**：同一处 P3 提过一次、作者明确不采纳后，不得在后续 PR 重复提出。风格问题交给 `gofmt` 和 lint，不占用人。

## 四、分域检查清单

按域组织，每条都标注**为什么本仓库需要它**（对应真实历史缺陷）。审查时按变更触及的域取用，不要求全量。

### A. 契约与分层（`protocol` / 跨包依赖）

- [ ] `protocol` 是否仍然零内部依赖、无闭包、可 JSON 序列化？
- [ ] 契约字段增删是否同步了**所有**消费端（TUI / Agent / Desktop）？—— *历史：`Traces()` 从 `Agent` 接口移除时，TUI 需同步改为注入 `TraceSource`*
- [ ] 依赖方向是否单向？`tui` 不得 import `config`，`protocol` 不得 import 任何内部包。—— *历史：TUI 曾直接依赖 config 包*
- [ ] 出站数据是否做了"最小必要"裁剪？入站字段不等于可回灌字段。—— *历史：`reasoning_content` 每轮回灌，DeepSeek 直接 400*
- [ ] 接口返回是否避免了"nil 具体类型包成非 nil 接口"？—— *历史：`NewGatewayFromConfig` 返回 nil `*Client`，导致"未就绪"判定失效*

### B. 并发与生命周期（`agent` / `gateway` / `tool` / `tui`）

- [ ] 每个可能阻塞的调用是否有 `context` 传递与超时？（网络、进程、文件）—— *历史：全链路零超时，一条挂死 bash 让整轮永久挂起*
- [ ] `context` 是否从入口一路传到最内层，中间没有 `context.Background()` 截断？
- [ ] 每个 `go func()` 是否有退出条件、是否可能泄漏、是否 `recover`？—— *历史：`agentLoop` 无 `recover`，一次 panic 打崩整个 TUI*
- [ ] 取消（Ctrl+C / Esc / 退出）后，状态是否完全复位：`running`、`isGenerating`、挂起审批、子进程组？
- [ ] 中断发生在"多步原子操作"中间时，数据结构是否仍然自洽？—— *历史：assistant 已落 N 个 `tool_calls`、tool 结果只落 M 个，历史残缺导致此后每轮 400*
- [ ] 共享可变状态是否有锁，或明确注释"仅单 goroutine 访问"？（本仓库面向单用户，**不要求为并发请求加锁**，但要求不出现真实数据竞争）

### C. 安全（`permission` / `fsutil` / `builtin` / `gateway`）

- [ ] 新增/修改命令判定规则时，是否同时补了**绕过用例**（`sh -c` 包装、`eval`、命令替换、`xargs`、解释器 `-c`）？
- [ ] 安全判定是否用了 `strings.Contains` 这类字面量匹配？—— *历史：Gate 1 用 `Contains("rm -rf /")`，既误杀 `/tmp/x` 又漏检 `sh -c`*
- [ ] 路径判定是否统一走 `fsutil.ResolveInWorkspace`，而不是各自 `filepath.Abs`？—— *历史：5 处重复实现，全部漏 `EvalSymlinks`，软链可越界*
- [ ] 新增文件写入是否指定了最小权限（配置/日志 `0600`，普通文件 `0644`）？
- [ ] 密钥是否可能进入日志、trace payload、错误消息、测试夹具？
- [ ] 危险操作是否有"无法静态判定即审批"的兜底，而不是"判定不出来就放行"？

### D. 错误处理与可观测性

- [ ] 每个 `err` 是被处理、被包装上抛，还是被 `_` 丢弃？丢弃处是否有注释说明为何可丢？
- [ ] 错误消息是否包含"哪个操作、哪个对象、什么原因"，而不是裸 `err`？
- [ ] 面向用户的错误是否泄漏了内部路径/堆栈/密钥？
- [ ] 关键状态迁移（轮次开始/结束、工具执行、审批决策、配置切换）是否有日志或 trace 事件？
- [ ] 日志写入是否在热路径上做全量重写？是否在流式回调里做同步 I/O？—— *历史：每个事件全量重写 `latest.json`*

### E. 状态机与前端（`tui`）

- [ ] 新增 `state` 时，是否穷举了所有按键在该状态下的行为（含 `Esc` / `Ctrl+C` / 空输入回车）？
- [ ] 是否新增了"必须手工在 N 处清空"的全局可变字段？—— *历史：`currentAPIKey` 依赖 6 处手工清空，跨厂商泄漏*
- [ ] 渲染缓存是否以"内容 + 宽度"为 key，流式增量是否被排除在缓存外？
- [ ] 长内容是否用 `textutil.TruncateUTF8` 截断（不得按字节切 UTF-8）？
- [ ] 视图是否在窗口 resize 后仍正确（宽度硬编码会溢出）？

### F. 测试有效性

- [ ] 测试是否**只验证入站解析**而没验证**出站 payload**？—— *历史：`reasoning_content` 有解析测试、无出站断言，缺陷长期潜伏*
- [ ] 安全类改动是否用**表驱动**覆盖"必须拦"与"必须放行"两侧？只测拦截会误伤正常用法。
- [ ] 测试是否依赖真实凭据、真实网络、真实本地服务？（必须用 `httptest` 或 fake）
- [ ] 断言是否具体（值/错误类型/字段存在性），而不是只断言 `err == nil`？
- [ ] 新代码的失败路径（超时、panic、取消、空输入）是否有用例？

### G. 可维护性与整洁度

- [ ] 是否引入了兼容层、别名、`Deprecated` 标记、为旧实现保留的分支？（**本仓库明令禁止**）
- [ ] 是否有未调用的导出函数、未使用的字段、`TODO` 无主？
- [ ] 是否存在"同一事实有两份状态"（如 `Content` 与 `Blocks` 各存一份）？
- [ ] 新增抽象是否真的降低了复杂度，还是只是把代码挪了个位置？（**反对过度封装**）
- [ ] 注释是否解释"为什么"，而不是复述"做了什么"？是否中文？

## 五、变更分级与审查流程

### 5.1 变更分级（决定流程强度）

| 级别 | 判定 | 示例 | 设计文档 | 审查人数 | 合入条件 |
|---|---|---|---|---|---|
| **T0** | 纯文档、注释、README | 本标准；拼写修正 | 不需要 | 0 | CI 绿即可 |
| **T1** | 单点缺陷修复，无接口/行为契约变化，≤200 行 | 修一个越界判断；补一个超时 | 不需要 | 1 | CI 绿 + 1 人通过 |
| **T2** | 新功能、新工具、新 Provider、行为变化 | 新增 `web_fetch` 工具；接入新厂商 | 设计要点（PR 描述内，含影响面与验收） | 1 | CI 绿 + 1 人通过 + 新路径有测试 |
| **T3** | 结构性变更：跨包依赖、`protocol` 契约、权限/沙箱规则、装配顺序、并发模型、删除公共 API | D3 权限规范化；D5 WorkDirRef；D10 包迁移 | **必须**，`outputs/` 下独立文档并审核通过 | 2（或维护者 + 24h 冷却自审） | 设计通过 + CI 绿 + 2 人通过 + 回归用例 |

**PR 体量纪律**：单 PR 有效改动（新增+删除，不含测试夹具与生成代码）建议 ≤400 行。超过需在描述里说明为何不能拆。参考反例：D1–D13 的一批改动达 44 文件 / +2270 −865，审查者实际上无法逐行确认，只能抽查。

### 5.2 流程状态机

```text
[Issue / 需求]
      │
      ├─ T0 ──────────────────────────────────────────► 直接提交
      │
      ├─ T1/T2 ──► 分支实现 ──► 自检(make verify) ──► PR ──► L0 ──► L2 ──► 合入
      │                                                        │       │
      │                                                        └─红─┐  └─打回─┐
      │                                                             ▼        ▼
      │                                                          作者修   作者修
      │
      └─ T3 ──► 设计文档(outputs/) ──► L3 审核 ──► 批准 ──► 实现 ──► PR ──► L0 ──► L2+L3 ──► 合入
                                          │
                                          └─ 退回 → 修订设计（此阶段禁止动代码）
```

**硬性红线（沿用仓库既有约定，此处明确为审查阻断项）**：T3 的设计文档未获明确批准前，**不得改动任何业务代码**——包括删旧文件、改写实现、新增包。违反时审查者必须要求完整回退代码、只保留待审文档。

### 5.3 时限（SLA）

| 环节 | 时限 | 超时处理 |
|---|---|---|
| L0 机器门禁 | 10 分钟内出结果 | 修 CI，不绕过 |
| L2 首次响应（T1） | 24 小时 | CI 绿且仅 T1 时可自行合入 |
| L2 首次响应（T2/T3） | 48 小时 | **不得自行合入**，升级给维护者 |
| 作者修订 | 收到意见后 48 小时 | 视为放弃，PR 关闭（可重开） |

### 5.4 角色与职责

**作者**
- 提交前必须自己跑 `make verify`，并在 PR 中贴出结果
- PR 描述写清"改了什么 / 为什么 / 影响面 / 怎么验证"，不写"优化代码"这种空话
- 主动标注自评严重度与不确定点（"这里我不确定 `xargs` 是否漏检"比装作没问题更有价值）
- 一次提交只做一件事；提交信息用中文「主题：描述」

**审查者**
- 先看**变更意图与影响面**，再看 diff；先看测试，再看实现
- 每条意见必须带：严重度、`文件:行`、问题、依据、建议、验收方式
- 只提自己能说清"为什么"的意见；不确定就写成提问，不写成结论
- 不重写作者的代码，不把个人风格当缺陷，不在 P3 上纠缠
- 明确给出结论：`通过` / `修订后通过` / `打回`

**维护者**
- 裁定分级争议（P1 还是 P2），批准 P1 豁免
- 每月主持复盘，把逃逸缺陷转成规则
- 拒绝超出范围的 PR（例如顺手重构无关模块）

### 5.5 单人维护模式（当前实际情况）

仓库当前实质是单人维护，"同行审查"退化为自审。退化时必须用流程补偿，不能直接省略：

1. **冷却期**：T3 变更完成后至少间隔 24 小时再自审合入，避免"刚写完的兴奋期"。
2. **换视角自审**：不看 diff，而是从"如果我要攻击这段代码"和"如果半年后我来改它"两个视角重读。
3. **机器门禁不得降级**：单人模式下 L0 是唯一外部约束，必须完整（含 `-race`、lint、跨平台构建）。
4. **留痕**：PR 描述里写"自审已过 + 冷却时长 + 重点怀疑点"，便于事后追溯。

## 六、审查意见的写法与回应

### 6.1 意见格式（强制）

```text
[P1] internal/permission/normalize.go:102 — splitSegments 把 | 当作命令分隔符，
导致 `echo x | xargs rm` 被切成两段，右侧危险动词漏检。
依据：管道两侧命令都会执行，且 xargs 会把左侧输出变成 rm 的参数。
建议：仅按 ; && || 换行 切段，管道保留在段内，由 analyzeInto 递归处理。
验收：表驱动新增用例 {"pipe to xargs", `echo x | xargs rm`, "approve"}。
```

六个要素缺一不可：**级别 / 位置 / 问题 / 依据 / 建议 / 验收**。缺"验收"的意见等于把判断成本转嫁给作者。

### 6.2 回应格式

| 回应 | 写法 | 后续 |
|---|---|---|
| 接受 | `已修：<commit>` + 说明改法 | 审查者确认后关闭 |
| 反驳 | `不同意 P1：<技术依据>` | 审查者要么撤回，要么升级维护者裁定 |
| 延期 | `接受，转 P2：已建 #<issue>` | 需审查者同意降级 |
| 已存在 | `该问题在 <commit> 已修，见 <文件:行>` | 审查者核实后撤回 |

**禁止**：无说明的"已改"、把 P0 降级为 P2 自行处理、用"下次一起改"关闭 P1。

### 6.3 反模式速查（本仓库真实踩过，见到即按对应级别处理）

| # | 反模式 | 级别 | 历史出处 |
|---|---|---|---|
| 1 | 为旧内部实现保留别名/兼容层 | P1 | 仓库约定明令禁止 |
| 2 | 安全判定用字面量 `Contains` | P0 | Gate 1 漏检 `sh -c` |
| 3 | 路径判定各自实现、不做符号链接解析 | P0 | 5 处重复 + 软链越界 |
| 4 | 只测入站解析、不测出站 payload | P1 | `reasoning_content` 回灌 |
| 5 | 无超时 / 无 `recover` 的外部调用 | P1 | 挂死与崩溃 |
| 6 | 全局可变状态靠"记得清空"维持 | P1 | `currentAPIKey` 6 处清空 |
| 7 | 同一事实存两份状态 | P2 | `ChatMessage.Content/Blocks` |
| 8 | 热路径同步 I/O、全量重写 | P2 | 每事件重写 `latest.json` |
| 9 | 为"以后可能用到"提前抽象 | P2 | 反对过度封装 |
| 10 | 一条提交塞多个不相关变更 | P2 | `D1/D2/D9` 合为一次提交 |

## 七、机器门禁落地

### 7.1 本地一键验证

`make verify` 是**唯一**的提交前标准动作，等价于 CI 的核心检查：

```bash
make verify   # gofmt 检查 + go vet + go test -race + 构建
make lint     # golangci-lint（需本地安装，CI 亦跑）
```

### 7.2 CI 必过项（顺序即失败优先级）

1. `gofmt -l` 无输出
2. `go vet ./...` 零告警
3. `go test -race -count=1 ./...` 全绿
4. `go build ./...` + 三平台交叉编译（linux/amd64、darwin/arm64、windows/amd64）
5. `golangci-lint run --new-from-rev=origin/main`（**灰度期非阻断**，见 7.3）

### 7.3 lint 灰度策略（避免"一上来全红"）

存量代码必然有历史告警，直接阻断会让所有人绕过门禁。分三步：

| 阶段 | 时长 | 做法 | 通过标准 |
|---|---|---|---|
| 灰度 | 2 周 | CI 中 `continue-on-error: true`，只看趋势 | 新增代码零新增告警 |
| 收敛 | 2 周 | 设 `--new-from-rev`，只拦新增 | 存量告警清零或写入 `issues.exclude-rules` 并注明理由 |
| 阻断 | 长期 | 去掉 `continue-on-error` | 任何新增告警阻断合入 |

### 7.4 覆盖度门槛

不追求总覆盖率数字（`tui` 的渲染代码天然难测）。改为**按包设下限 + 新增代码必测**：

| 包 | 行覆盖下限 | 说明 |
|---|---:|---|
| `permission` / `fsutil` | 85% | 安全边界，规则分支必须全覆盖 |
| `tool` / `tool/builtin` | 80% | 沙箱与命令执行 |
| `gateway` / `memory` | 75% | 协议拼装与轮次裁剪 |
| `agent` | 70% | 状态机 |
| `tui` | 50% | 渲染豁免，状态迁移必须测 |
| `config` / `middleware` | 70% | 当前 `middleware` 仅 0.14 测试比，需补 |

新增/修改函数的覆盖率为 **100%**（含错误分支），由审查者人工确认，不依赖工具卡点。

## 八、度量与闭环

### 8.1 四个指标（每月统计一次，不必上系统）

| 指标 | 定义 | 目标 | 超标时的动作 |
|---|---|---|---|
| **逃逸缺陷率** | 合入后发现的 P0/P1 ÷ 当期 P0/P1 总数 | < 20% | 复盘该批次的审查盲区，补清单项 |
| **首次通过率** | 一次审查即通过的 PR ÷ 总 PR | > 60% | 过低说明自审无效，加强 L1 |
| **审查时长中位数** | PR 打开到首次意见 | < 24h | 检查是否审查者过载 |
| **规则沉淀数** | 当期新增的测试用例 / lint 规则 / 清单条目 | ≥ 逃逸缺陷数 | 未达标说明闭环断裂 |

### 8.2 闭环机制（本标准的核心）

> **任何 P0/P1 缺陷，无论逃逸还是被拦下，48 小时内必须至少产出以下一项：**
> 1. 一条能复现它的**测试用例**（首选）
> 2. 一条能自动拦住它的 **lint 规则 / 静态检查**
> 3. 一条进入第四章清单的**新条目**（仅当前两者都不可行时）

同时登记到缺陷台账（可放 `outputs/` 或 Issue）：

| 日期 | 缺陷 | 级别 | 来源（逃逸/拦下） | 沉淀形式 | 落点 |
|---|---|---|---|---|---|
| 2026-10-18 | `reasoning_content` 回灌导致 400 | P1 | 评审发现 | 测试 | `gateway_test.go:TestBuildRequestPayload_StripsReasoningContent` |
| 2026-10-18 | `sh -c` 绕过权限审批 | P0 | 评审发现 | 测试 + 清单 | `permission_test.go` 表驱动 22 例 / 清单 C-1 |
| 2026-10-18 | 软链穿透工作区 | P0 | 评审发现 | 代码收敛 + 测试 | `fsutil.ResolveInWorkspace` |
| 2026-10-18 | CI Go 版本漂移导致门禁失效 | P1 | 本标准制定 | CI 修复 | `.github/workflows/ci.yml` |

### 8.3 每月复盘（30 分钟，单人也要做）

四个固定问题：
1. 这个月逃逸了哪些缺陷？分别属于哪个域？
2. 清单里哪一条**本该**拦住它？是清单缺失，还是没执行？
3. 有没有 P3 意见占用了过多时间？
4. 有没有规则已经过时（代码结构变了，清单还在管旧结构）？

## 十一、实施顺序（本标准自身的落地）

| 步骤 | 内容 | 产出 | 验收 |
|---|---|---|---|
| 1 | 修复 CI Go 版本、补 `vet` / `gofmt` / `-race` | `.github/workflows/ci.yml` | CI 在 `my-agent` 分支真实变绿 |
| 2 | 加 `make verify` / `make lint` | `Makefile` | 本地一条命令完成提交前检查 |
| 3 | 加 lint 配置（灰度） | `.golangci.yml` | 本地可跑出告警清单 |
| 4 | 加 PR 模板 | `.github/pull_request_template.md` | 新建 PR 自动带出检查表 |
| 5 | 按第七章 7.3 收敛 lint 存量告警 | 分批提交 | 新增代码零告警 |
| 6 | 补 `middleware` / `protocol` 测试缺口 | 测试 | 覆盖率达到 7.4 下限 |
| 7 | 更新 README「开发与测试」「贡献指南」引用本标准 | `README.md` | 文档与代码一致 |
| 8 | 建立缺陷台账并开始月度复盘 | `outputs/` 或 Issue | 连续两月有记录 |

**本标准不追求一次到位**：步骤 1–4 当天可完成，5–8 需持续两个迭代。审查机制的价值在"每次缺陷都让下次更容易"，而不是"一次写出完美清单"。
