### 泛型约定

v0.9.x 的 ADK 全面泛型化，所有类型都有一个 `Typed*` 泛型版本，外加一个非泛型别名。以 Agent 为例：

```go
// adk/interface.go:453
type TypedAgent[M MessageType] interface {
    Name(ctx context.Context) string
    Description(ctx context.Context) string
    Run(ctx context.Context, input *TypedAgentInput[M], options ...AgentRunOption) *AsyncIterator[*TypedAgentEvent[M]]
}

// adk/interface.go:467
type Agent = TypedAgent[*schema.Message]
```

`M` 的约束是 `adk.MessageType`（`adk/interface.go:43`）：

```go
// MessageType 是 ADK 中消息类型的封闭类型约束。
// 只有 *schema.Message 和 *schema.AgenticMessage 满足这个约束。
// 外部包无法向这个联合添加新类型；所有泛型函数
// 在 ADK 内部都对这两种类型做穷举类型分支。
type MessageType interface {
    *schema.Message | *schema.AgenticMessage
}
```

这是 Go 的 **sealed union（封闭联合）**技巧：接口里只放类型项（type term），不放方法。这样的接口**不能作为变量的类型使用**，只能作为类型约束。效果是：

- 框架内部可以用 `switch any(zero).(type)` 做穷举分派，编译器保证只有两个分支；
- 外部包**无法**往这个联合里加新类型，所以框架的行为边界是封闭、可推理的；
- 代价是你写不出 `var m adk.MessageType`，只能用泛型函数 `func f[M adk.MessageType](m M)`。

配套的 nil 判断也受影响。泛型指针类型不能直接和 `nil` 比较（Go 规范限制），源码给了标准解法（`adk/interface.go:56`）：

```go
func isNilMessage[M MessageType](msg M) bool {
    var zero M
    return any(msg) == any(zero)
}
```

**这个坑你一定会踩**：写泛型代码时 `if msg == nil` 直接编译失败，报 `cannot convert nil to type M`。用 `any(msg) == nil` 也不行——装箱后是带类型的 nil，不等于 `nil`。必须走 `isNilMessage` 的写法。

### 两条消息路径

v0.9.x 同时存在两套消息协议，这是本章最重要的认知前提：

| 路径 | 消息类型 | 工具调用怎么表达 | 适用 |
|---|---|---|---|
| Message 路径 | `*schema.Message` | 独立的 `ToolCalls` 字段 + `Role: tool` 消息 | OpenAI 风格 Chat Completion API，绝大多数模型 |
| Agentic 路径 | `*schema.AgenticMessage` | `ContentBlock` 里的 `function_tool_call` / `function_tool_result` 块 | Claude / Gemini 等原生 agentic 协议，服务端工具、MCP |

两条路径**共享** `adk` 的 Agent / Runner / 事件机制，但消息结构完全不同。本章以 Message 路径为主线（它是绝大多数项目的实际选择），Agentic 路径的结构与选型放在 [1.8](#18-agenticmessage另一条消息路径)。

# 第 1 章　Message：对话的唯一数据单位

## 1.1 结构体全字段

`schema/message.go:503`：

```go
type Message struct {
    Role RoleType `json:"role"`

    // Content 用于用户文本输入和模型文本输出。
    Content string `json:"content"`

    // 若 MultiContent 非空，则用它替代 Content
    // 若 MultiContent 为空，则使用 Content
    // 已弃用：用户多模态输入请用 UserInputMultiContent，
    // 模型多模态输出请用 AssistantGenMultiContent。
    MultiContent []ChatMessagePart `json:"multi_content,omitempty"`

    // UserInputMultiContent 把用户提供的多模态内容传给模型。
    UserInputMultiContent []MessageInputPart `json:"user_input_multi_content,omitempty"`

    // AssistantGenMultiContent 用于接收模型的多模态输出。
    AssistantGenMultiContent []MessageOutputPart `json:"assistant_output_multi_content,omitempty"`

    Name string `json:"name,omitempty"`

    // 仅用于 assistant 消息
    ToolCalls []ToolCall `json:"tool_calls,omitempty"`

    // 仅用于 tool 消息
    ToolCallID string `json:"tool_call_id,omitempty"`
    // 仅用于 tool 消息
    ToolName string `json:"tool_name,omitempty"`

    ResponseMeta *ResponseMeta `json:"response_meta,omitempty"`

    // ReasoningContent 是模型的思考过程，
    // 模型返回推理内容时才会填充。
    ReasoningContent string `json:"reasoning_content,omitempty"`

    // 供模型实现自定义使用的信息
    Extra map[string]any `json:"extra,omitempty"`
}
```

12 个字段。但它们的**有效组合只有四种**——由 `Role` 决定哪些字段有意义：

| 字段 | system | user | assistant | tool |
|---|:---:|:---:|:---:|:---:|
| `Content` | ✅ | ✅ | ✅ | ✅ |
| `UserInputMultiContent` | ⚠️ | ✅ | ❌ | ❌ |
| `AssistantGenMultiContent` | ❌ | ❌ | ✅ | ❌ |
| `MultiContent`（已弃用） | ❌ | ⚠️ | ⚠️ | ❌ |
| `Name` | ⚠️ | ⚠️ | ⚠️ | ⚠️ |
| `ToolCalls` | ❌ | ❌ | ✅ | ❌ |
| `ToolCallID` | ❌ | ❌ | ❌ | ✅ |
| `ToolName` | ❌ | ❌ | ❌ | ✅ |
| `ReasoningContent` | ❌ | ❌ | ✅ | ❌ |
| `ResponseMeta` | ❌ | ❌ | ✅ | ❌ |
| `Extra` | ✅ | ✅ | ✅ | ✅ |

（✅ = 有明确语义；⚠️ = 部分模型实现支持，需逐个核对；❌ = 无意义，设置了也会被适配器忽略或导致报错）

**注意表里的 ⚠️**。这不是"框架不支持"，而是"框架允许，但具体模型实现可能不支持"。`AGENTS.md` 里那条规则说的就是这个：

> 框架消息字段存在，不代表所用模型和适配器支持该模态；接入前核对实际支持范围。

比如 `Name` 字段：OpenAI 的 Chat Completion API 里 `name` 是可选的参与者标识，但很多兼容实现直接丢弃它。你不能靠 `Name` 来做业务逻辑。

### 设计意图：为什么是一个大结构体而不是接口

对比一下：一个"更 Go"的设计可能是 `type Message interface { Role() RoleType }`，然后 `SystemMessage` / `UserMessage` / `ToolMessage` 各实现一套。

Eino 选了平铺结构体，原因有三：

1. **序列化友好**。检查点（checkpoint）用 gob 编码，`Message` 是具体结构体，gob 直接支持；接口字段需要 `gob.Register` 注册所有实现，容易漏。
2. **适配器实现成本低**。每个模型适配器（openai / ark / claude / ollama）只做字段映射，不需要处理类型断言。
3. **用户可以就地构造**。`&schema.Message{Role: schema.User, Content: "hi"}` 一行搞定，不需要工厂。

代价就是上面那张表——**合法性靠约定，不靠类型系统**。框架不会阻止你给 `User` 消息设置 `ToolCalls`，模型适配器也不会报错，只是这个工具调用会被静默丢弃。

**这是一条重要的调试经验**：如果工具调用莫名其妙没生效，先检查那条消息的 `Role` 对不对。

## 1.2 RoleType：只有四种

`schema/message.go:109`：

```go
type RoleType string

const (
    // Assistant 是助手角色，表示这条消息由 ChatModel 返回。
    Assistant RoleType = "assistant"
    // User 是用户角色，表示这条消息来自用户。
    User RoleType = "user"
    // System 是系统角色，表示这条消息是系统提示。
    System RoleType = "system"
    // Tool 是工具角色，表示工具调用的输出。
    Tool RoleType = "tool"
)
```

四个值，没有第五个。这对应 OpenAI Chat Completion 的四种 role，也是目前所有主流模型的事实标准。

### 顺序约束

模型的输入是一个**有序**切片。顺序不是随意的，有一条硬约束：

```
system 消息 → [user → assistant → (tool → assistant)*]*
```

具体规则：

1. **`system` 必须在最前面**。大多数适配器会把所有 `system` 消息合并成一条放在开头，或者直接取第一条。把 `system` 放在中间，行为不确定。
2. **`tool` 消息必须紧跟在带 `ToolCalls` 的 `assistant` 消息后面**，且 `ToolCallID` 必须对应上。这是协议级约束，不满足会直接 API 报错。
3. **一个 `assistant` 发起 N 个工具调用，就必须有 N 条 `tool` 消息**。少一条、多一条都会被拒绝。

第 3 条是最容易出错的。如果你只回填了部分工具结果（比如某个工具超时被跳过了），下一次请求就会失败。正确做法是给失败的工具也回填一条 `ToolMessage`，内容是错误描述。

### 一个反直觉的点

`Role` 的零值是 `""`，不是任何一个合法角色。这意味着：

```go
var m schema.Message
// m.Role == "" —— 这是一个非法消息
```

`ConcatMessages` 对 `Role` 的处理是"首个非空值胜出"（`schema/message.go:1670` 起）：

```go
if msg.Role != "" {
    if ret.Role == "" {
        ret.Role = msg.Role
    } else if ret.Role != msg.Role {
        return nil, fmt.Errorf("cannot concat messages with different roles: '%s' '%s'", ret.Role, msg.Role)
    }
}
```

也就是说流式分片里，只有第一个分片带 `Role`，后面都是空的，这是**正常且必要**的。如果你自己手工拼接分片并检查"每一片 Role 都必须一致"，就会误判。

## 1.3 多模态：三代字段的演进

`schema.Message` 里有三个多模态字段，这是历史包袱，必须搞清楚谁替代谁。

### 第一代：MultiContent（已弃用）

```go
// 已弃用：用户多模态输入请用 UserInputMultiContent，
// 模型多模态输出请用 AssistantGenMultiContent。
MultiContent []ChatMessagePart
```

问题在于：**它不区分方向**。同一个 `ChatMessagePart` 类型既用于"用户传图给模型"，也用于"模型生成图给用户"。但这两者的语义完全不同：

- 用户传图：URL / base64 / 文件 ID，需要 `Detail`（low/high/auto）控制模型看多细；
- 模型生成图：URL / base64，可能带 `RevisedPrompt`（DALL·E 改写后的提示词）。

塞进一个结构体，字段就互相污染。所以弃用了。

### 第二代：方向分离

用户侧 `MessageInputPart`（`schema/message.go:213`）：

```go
type MessageInputPart struct {
    Type ChatMessagePartType `json:"type"`
    Text string `json:"text,omitempty"`
    Image *MessageInputImage `json:"image,omitempty"`
    Audio *MessageInputAudio `json:"audio,omitempty"`
    Video *MessageInputVideo `json:"video,omitempty"`
    File  *MessageInputFile  `json:"file,omitempty"`
    // ToolSearchResult 保存一次工具搜索请求的结果，
    // 包含匹配到的工具名及其定义。
    ToolSearchResult *ToolSearchResult `json:"tool_search_result,omitempty"`
    Extra map[string]any `json:"extra,omitempty"`
}
```

模型侧 `MessageOutputPart`（`schema/message.go:274`）：

```go
type MessageOutputPart struct {
    Type ChatMessagePartType `json:"type"`
    Text string `json:"text,omitempty"`
    Image *MessageOutputImage `json:"image,omitempty"`
    Audio *MessageOutputAudio `json:"audio,omitempty"`
    Video *MessageOutputVideo `json:"video,omitempty"`
    // Reasoning 保存模型生成的推理内容。
    Reasoning *MessageOutputReasoning `json:"reasoning,omitempty"`
    Extra map[string]any `json:"extra,omitempty"`
    // StreamingMeta 保存流式响应的元数据。
    // 该字段通常只在运行期使用，不参与序列化。
    StreamingMeta *MessageStreamingMeta `json:"-"`
}
```

差异点：

| | MessageInputPart | MessageOutputPart |
|---|---|---|
| 独有 | `File`（文档输入）、`ToolSearchResult` | `Reasoning`、`StreamingMeta` |
| 无 | `Reasoning`、`StreamingMeta` | `File` |

**为什么输出侧没有 `File`？** 因为模型目前不会"生成一个文件"。工具可以返回文件（那是 `EnhancedTool` 的 `ToolResult`），但模型生成的是文本和图像。

**为什么输入侧没有 `Reasoning`？** 思维链是模型产出的，不会作为输入回灌。虽然某些实现允许把上一轮的 reasoning 传回去（比如 Anthropic 的 extended thinking 需要签名），但那走的是 `Content` 或 `Extra`，不走 `Reasoning` 这个 part 类型。

**`StreamingMeta` 标了 `json:"-"`**，这是关键细节：流式分片里它记录这个 part 在完整内容中的位置索引，用于 `ConcatMessages` 时排序合并。它**不参与序列化**，所以你不能靠持久化再恢复来重建流式状态。

### 第三代：AgenticMessage 的 ContentBlock

见 [1.8](#18-agenticmessage另一条消息路径)。简单说，Agentic 路径把"part"升级成了"block"，用 20 种类型覆盖了服务端工具、MCP、审批等场景。

### ChatMessagePartType：7 个值

`schema/message.go:324`：

```go
type ChatMessagePartType string

const (
    ChatMessagePartTypeText            ChatMessagePartType = "text"
    ChatMessagePartTypeImageURL        ChatMessagePartType = "image_url"
    ChatMessagePartTypeAudioURL        ChatMessagePartType = "audio_url"
    ChatMessagePartTypeVideoURL        ChatMessagePartType = "video_url"
    ChatMessagePartTypeFileURL         ChatMessagePartType = "file_url"
    ChatMessagePartTypeReasoning       ChatMessagePartType = "reasoning"
    ChatMessagePartTypeToolSearchResult ChatMessagePartType = "tool_search_result"
)
```

注意最后两个：

- `reasoning` 只出现在 `MessageOutputPart`；
- `tool_search_result` 只出现在 `MessageInputPart`。

这两个值在 OpenAI 的公开 API 里没有直接对应物，是 Eino 为适配不同厂商扩展出来的。如果你的模型适配器不认，就会忽略整个 part。

### 陷阱：Type 与填充字段必须匹配

框架**不校验** `Type` 和实际填充的字段是否一致。你完全可以这样写：

```go
schema.MessageInputPart{
    Type: schema.ChatMessagePartTypeText,
    Image: &schema.MessageInputImage{ /* ... */ },  // Type 说是 text，却填了 Image
}
```

编译通过，运行时适配器会读到 `Type == "text"`，然后去读 `Text` 字段，得到空字符串。**图像被静默丢弃**。

这是最容易浪费半小时的 bug。写多模态消息时，务必让 `Type` 和填充字段严格对应。

## 1.4 构造函数：不要手写结构体

`schema/message.go` 提供了四个构造函数：

```go
// schema/message.go:1118
func SystemMessage(content string) *Message

// schema/message.go:1126
func AssistantMessage(content string, toolCalls []ToolCall) *Message

// schema/message.go:1135
func UserMessage(content string) *Message

// schema/message.go:1158
func ToolMessage(content string, toolCallID string, opts ...ToolMessageOption) *Message
```

前三个很直白。第四个 `ToolMessage` 值得展开——它有可变参数 `ToolMessageOption`：

```go
// schema/message.go:1148
type ToolMessageOption func(*toolMessageOptions)

// schema/message.go:1151
func WithToolName(name string) ToolMessageOption
```

`WithToolName` 设置 `Message.ToolName` 字段。这个字段是**可选**的：

- 不给：`ToolName` 为空，某些模型（如 OpenAI）不需要它，靠 `ToolCallID` 关联就够了；
- 给：多一层冗余关联，好处是日志和事件流里能直接看出"这条结果来自哪个工具"，不用反查 `ToolCallID`。

**建议总是给**。因为在 `AgentEvent` 里，流式模式下你拿到 `Message` 之前只有 `TypedMessageVariant.ToolName`（`adk/interface.go:73` 的注释明确说明了这点）：

```go
// ToolName 是产生本事件的工具名。
// 仅对 *schema.Message 事件有意义：Role == schema.Tool 时非空。
// 流式模式下，这是在消费流之前唯一能确认来源工具的方式。
// （流被消费之前）
ToolName string
```

但要注意：这个 `ToolName` 是框架从 `ToolCallID` 反查填的，不是你 `ToolMessage` 里的那个字段。两者来源不同，不要混淆。

### 为什么不建议手写结构体

```go
// 能用，但脆弱
msg := &schema.Message{Role: schema.User, Content: "hi"}
```

问题在于：手写时你**必须自己记得**哪些字段该填。比如构造 `assistant` 消息时忘了 `Role` 的零值问题，或者构造 `tool` 消息时漏了 `ToolCallID`。

构造函数把这些约束固化了。而且未来版本加字段时，构造函数会同步更新，手写结构体不会。

## 1.5 ConcatMessages：流式拼接的全部真相

这是本章**技术密度最高**的一节。`ConcatMessages` 是流式输出的核心，几乎所有"流式结果不对"的 bug 都源于对它行为的不了解。

### 签名与定位

`schema/message.go:1670`：

```go
func ConcatMessages(msgs []*Message) (*Message, error)
```

它接收一个消息分片切片，合并成一个完整消息。谁在调用它？

- `adk` 里 `concatMessageStream`（`adk/interface.go:489`）—— 消费流式事件；
- `TypedMessageVariant.GetMessage()`（`adk/interface.go:107`）—— 这是你直接会用的：

```go
func (mv *TypedMessageVariant[M]) GetMessage() (M, error) {
    if mv.IsStreaming {
        return concatMessageStream(mv.MessageStream)
    }
    return mv.Message, nil
}
```

### 四组一致性校验

合并时，有四组字段做"首个非空胜出 + 冲突报错"处理：

```go
// 1. Role（角色）
if msg.Role != "" {
    if ret.Role == "" {
        ret.Role = msg.Role
    } else if ret.Role != msg.Role {
        return nil, fmt.Errorf("cannot concat messages with different roles: '%s' '%s'", ret.Role, msg.Role)
    }
}

// 2. Name（名称）
if msg.Name != "" { /* 同上，报 different names */ }

// 3. ToolCallID（工具调用 ID）
if msg.ToolCallID != "" { /* 同上，报 different toolCallIDs */ }

// 4. ToolName（工具名）
if msg.ToolName != "" { /* 同上，报 different toolNames */ }
```

**语义**：分片可以重复携带这些字段，只要值一致就没问题；一旦不一致，说明你把两个不同消息的分片混在一起了，直接报错。

### 源码里的一个真实 bug

看 `ToolName` 那段（`schema/message.go:1670` 附近）：

```go
if msg.ToolName != "" {
    if ret.ToolName == "" {
        ret.ToolName = msg.ToolName
    } else if ret.ToolName != msg.ToolName {
        return nil, fmt.Errorf("cannot concat messages with"+
            " different toolNames: '%s' '%s'", ret.ToolCallID, msg.ToolCallID)
    }
}
```

**报错信息里填的是 `ToolCallID`，不是 `ToolName`。**

所以你看到这个错误时，打印出来的两个 `%s` 是空字符串（因为 `ToolCallID` 在 `assistant` 消息里通常为空），而不是实际的工具名。

调试建议：遇到 `different toolNames: '' ''` 这种报错，别怀疑工具名，去检查**是不是把两条不同工具的结果消息分片混流了**。这是 v0.9.23 的已知小瑕疵，不影响功能，只影响可读性。

### Content 与 ReasoningContent：字符串累加

```go
if msg.Content != "" {
    contents = append(contents, msg.Content)
    contentLen += len(msg.Content)
}
// ...
if len(contents) > 0 {
    var sb strings.Builder
    sb.Grow(contentLen)
    for _, content := range contents {
        sb.WriteString(content)
    }
    ret.Content = sb.String()
}
```

两个细节：

1. **空分片被跳过**。`Content == ""` 的分片不进入 `contents`，所以不会影响结果。这解释了为什么流式帧里经常有空 `Content` 的帧——它们携带的是 `Role`、`ResponseMeta` 或 `ToolCalls` 增量。
2. **预分配容量**。`sb.Grow(contentLen)` 先算好总长度，避免多次扩容。这是个好习惯，但只在分片数量很大时才有意义。

`ReasoningContent` 走完全相同的逻辑。所以最终消息里，`Content` 和 `ReasoningContent` 是两个独立的完整字符串。

### ToolCalls：按 Index 分组累加

这是最复杂的部分。`concatToolCalls`（`schema/message.go:1297`）：

```go
func concatToolCalls(chunks []ToolCall) ([]ToolCall, error) {
    var merged []ToolCall
    m := make(map[int][]int)
    for i := range chunks {
        index := chunks[i].Index
        if index == nil {
            merged = append(merged, chunks[i])   // 无 Index，直接独立成一条
        } else {
            m[*index] = append(m[*index], i)     // 有 Index，按索引分组
        }
    }

    var args strings.Builder
    for k, v := range m {
        index := k
        toolCall := ToolCall{Index: &index}
        if len(v) > 0 {
            toolCall = chunks[v[0]]              // 以首片为基底
        }

        args.Reset()
        toolID, toolType, toolName := "", "", "" // 这些字段在任何分片中都原子输出
        extraList := make([]map[string]any, 0, len(v))

        for _, n := range v {
            chunk := chunks[n]
            if chunk.ID != "" {
                if toolID == "" {
                    toolID = chunk.ID
                } else if toolID != chunk.ID {
                    return nil, fmt.Errorf("cannot concat ToolCalls with different tool id: '%s' '%s'", toolID, chunk.ID)
                }
            }
            // Type / Function.Name 同理
            if chunk.Function.Arguments != "" {
                args.WriteString(chunk.Function.Arguments)
            }
            if len(chunk.Extra) > 0 {
                extraList = append(extraList, chunk.Extra)
            }
        }

        toolCall.ID = toolID
        toolCall.Type = toolType
        toolCall.Function.Name = toolName
        toolCall.Function.Arguments = args.String()
        // ...
    }
}
```

关键机制：

**（1）`Index` 是分组键**

模型返回多个并行工具调用时，流式分片长这样：

```
chunk 1: ToolCalls: [{Index:0, ID:"call_a", Name:"search", Arguments:"{\"q\":"}]
chunk 2: ToolCalls: [{Index:1, ID:"call_b", Name:"calc",   Arguments:"{\"x\":"}]
chunk 3: ToolCalls: [{Index:0, Arguments:"\"go\"}"}]
chunk 4: ToolCalls: [{Index:1, Arguments:"1}"}]
```

`Index` 交错到达，必须按 `Index` 归组。归组后 index=0 的分片是 chunk1+chunk3，index=1 的是 chunk2+chunk4。

**（2）`ID` / `Type` / `Name` 是"原子字段"**

源码注释 `// these field will output atomically in any chunk` 说明了：这三个字段**要么完整出现在一个分片里，要么完全不出现**，不会被拆分。所以它们采用"首个非空值胜出"策略。

而 `Arguments` 是**流式的**——它被逐字符拆分，必须字符串累加。

**（3）`Arguments` 用 `strings.Builder` 累加**

注意 `args` 是在循环外声明、每次迭代 `args.Reset()` 复用的。这是个微优化，避免为每个工具调用分配新 Builder。

**（4）没有 `Index` 的 ToolCall 直接独立成条**

这是兼容路径。非流式场景下模型返回的 `ToolCall` 通常没有 `Index`，每个都是完整的，直接 append 即可。

### 由此推导出的三个实践结论

**结论 1：流中断 = 非法 JSON**

`Arguments` 是累加出来的。如果流在中途断开（网络抖动、ctx 取消、`ShouldRetry` 触发），你拿到的是**半截 JSON**：

```json
{"query": "golang con
```

`json.Unmarshal` 会失败。这就是为什么流式场景下必须把"流错误"和"内容解析失败"分开处理——前者是网络问题，后者可能是断流导致。

**结论 2：`ToolCall.Index` 可能为 nil，不要直接解引用**

```go
// 错误
idx := *tc.Index  // 非流式场景下 panic

// 正确
if tc.Index != nil {
    idx := *tc.Index
}
```

**结论 3：不要自己拼流**

看到上面这些逻辑，应该明白为什么不该手写 `for { chunk := Recv(); result += chunk.Content }`：

- 你会漏掉 `ToolCalls` 的 `Index` 分组；
- 你会漏掉 `ResponseMeta` 的合并（见下）；
- 你会漏掉 `Extra` 的合并；
- 多模态 part 需要按 `StreamingMeta.Index` 排序。

**用 `ConcatMessages`，或者用 `MessageVariant.GetMessage()`。**

### ResponseMeta 的合并策略：取极值

这块逻辑很特别，值得单独说：

```go
if msg.ResponseMeta != nil && ret.ResponseMeta != nil {
    // 保留最后一个有效的 FinishReason。
    if msg.ResponseMeta.FinishReason != "" {
        ret.ResponseMeta.FinishReason = msg.ResponseMeta.FinishReason
    }

    if msg.ResponseMeta.Usage != nil {
        if ret.ResponseMeta.Usage == nil {
            ret.ResponseMeta.Usage = &TokenUsage{}
        }
        if msg.ResponseMeta.Usage.PromptTokens > ret.ResponseMeta.Usage.PromptTokens {
            ret.ResponseMeta.Usage.PromptTokens = msg.ResponseMeta.Usage.PromptTokens
        }
        // CompletionTokens / TotalTokens / CachedTokens / CacheWriteTokens / ReasoningTokens 同理
    }

    if msg.ResponseMeta.LogProbs != nil {
        ret.ResponseMeta.LogProbs.Content = append(ret.ResponseMeta.LogProbs.Content, msg.ResponseMeta.LogProbs.Content...)
    }
}
```

**为什么 token 数取最大值而不是求和？**

因为流式响应里，每个分片携带的 `Usage` 是**累计值**（到当前分片为止的总用量），不是增量。最后一个分片的值就是最终值。取最大值是"取最后那个累计值"的等价写法（累计值单调不减）。

如果某个适配器错误地发送了增量值，取最大值会得到错误结果。这是"信任适配器实现正确"的隐含假设。

**`FinishReason` 取最后一个非空值**，因为中间分片可能是空字符串，只有结束分片才有真实值。

**`LogProbs` 是唯一 append 的字段**，因为它是逐 token 的列表，天然是增量。

### Extra 的合并

`concatExtra` 处理 `Extra map[string]any`。多个分片的 `Extra` 会合并成一个 map。具体策略见 `concatExtra` 实现，但要点是：**同 key 冲突时会报错**，不会静默覆盖。

所以不要在流式分片里放"每片不同值"的 `Extra`。要放就放常量。

## 1.6 ResponseMeta 与 TokenUsage

`schema/message.go:453`：

```go
type ResponseMeta struct {
    // FinishReason 是本次对话响应结束的原因。
    // 通常是 "stop"、"length"、"tool_calls"、"content_filter"、"null"。
    FinishReason string `json:"finish_reason,omitempty"`
    Usage *TokenUsage `json:"usage,omitempty"`
    LogProbs *LogProbs `json:"logprobs,omitempty"`
}
```

### FinishReason 的五个值

| 值 | 含义 | 你要做什么 |
|---|---|---|
| `stop` | 正常结束 | 无 |
| `length` | 达到 `MaxTokens` 上限被截断 | 内容不完整；要么调大上限，要么让用户继续 |
| `tool_calls` | 模型要求调用工具 | 执行工具并回填结果，继续循环 |
| `content_filter` | 被内容安全策略拦截 | 内容为空或部分；需要给用户明确提示 |
| `null` | 部分实现用字符串 `"null"` 表示无值 | 当作未知处理 |

**`length` 是最容易被忽略的**。很多项目直接把 `Content` 存库返回给用户，用户看到一句被腰斩的话，以为是模型能力问题。正确做法是检查 `FinishReason == "length"` 并做处理。

**注意它是 `string` 不是枚举类型**。所以你不能用 `switch` 做穷举检查，也不能靠编译器提醒。源码注释里写的 "It's usually ..." 已经说明了这点——这是由各适配器自由填写的。

### TokenUsage 的细分

`schema/message.go:540`：

```go
type TokenUsage struct {
    // PromptTokens 是提示词 token 数，包含本次请求的全部输入 token。
    PromptTokens int `json:"prompt_tokens"`
    // PromptTokenDetails 是提示词 token 的细分。
    PromptTokenDetails PromptTokenDetails `json:"prompt_token_details"`
    CompletionTokens int `json:"completion_tokens"`
    TotalTokens int `json:"total_tokens"`
    CompletionTokensDetails CompletionTokensDetails `json:"completion_token_details"`
}

type PromptTokenDetails struct {
    // CachedTokens 是从缓存读取的提示词 token 数。
    CachedTokens int `json:"cached_tokens"`
    // CacheWriteTokens 是写入缓存的提示词 token 数。
    CacheWriteTokens int `json:"cache_write_tokens"`
}

type CompletionTokensDetails struct {
    // ReasoningTokens 是模型用于推理生成的 token 数。
    // 目前 OpenAI、Gemini、ARK 和 Qwen 的 chat model 支持该字段。
    // 其他模型该字段恒为 0。
    ReasoningTokens int `json:"reasoning_tokens,omitempty"`
}
```

四个细分字段的实际价值：

**`PromptTokenDetails.CachedTokens`** —— 这是**成本核算的关键**。命中 prompt 缓存的部分通常只收 10% 甚至免费。如果你的 Agent 每轮都重建 system prompt（见 [3.6](#36-defaultgenmodelinput每轮重拼的代价)），`CachedTokens` 会一直是 0，成本翻好几倍。

监控这个指标，是发现"prompt 缓存失效"的最快方式。

**`PromptTokenDetails.CacheWriteTokens`** —— Anthropic 风格的显式缓存写入。写入本身可能收费（比正常输入贵 25%），但后续读取便宜。这个字段帮你判断缓存策略是否划算。

**`CompletionTokensDetails.ReasoningTokens`** —— 推理模型（o1/o3、DeepSeek-R1、QwQ）的思维链 token 数。它**计入** `CompletionTokens`，所以你按 `CompletionTokens` 计费是对的。但用户看到的输出长度远小于它，如果按"输出字数"做限流就会失真。

源码注释明确列出了支持范围：OpenAI、Gemini、ARK、Qwen。其他模型恒为 0——**不要用这个字段判断"模型有没有思考"**，因为不支持它的模型也是 0。

## 1.7 Message.Format：三种模板引擎

`schema/message.go:679`：

```go
func (m *Message) Format(_ context.Context, vs map[string]any, formatType FormatType) ([]*Message, error)
```

注意返回值是 `[]*Message` 而不是 `*Message`。为什么？因为 `Message` 实现了 `MessagesTemplate` 接口（`schema/message.go:580`）：

```go
type MessagesTemplate interface {
    Format(ctx context.Context, vs map[string]any, formatType FormatType) ([]*Message, error)
}
```

这个接口的另一个实现是 `MessagesPlaceholder`——一个占位符可以展开成**多条**消息。所以 `Message.Format` 返回单元素切片，是为了和接口统一。

### 三种 FormatType

`schema/message.go:97`：

```go
type FormatType uint8

const (
    // FString 由 pyfmt(github.com/slongfield/pyfmt) 支持，
    // 它是 https://peps.python.org/pep-3101/ 的一个实现。
    FString FormatType = 0
    // GoTemplate 见 https://pkg.go.dev/text/template。
    GoTemplate FormatType = 1
    // Jinja2 由 gonja(github.com/nikolalohinski/gonja) 支持，
    // 它是 https://jinja.palletsprojects.com/en/3.1.x/templates/ 的一个实现。
    Jinja2 FormatType = 2
)
```

**注意 `FString = 0`**，是零值。这意味着如果你忘了传 `formatType`，默认就是 Python f-string 语法。

### 三者的差异与选择

| | 语法 | 依赖 | 适合 |
|---|---|---|---|
| `FString` | `{name}` | pyfmt（纯 Go，零依赖） | 简单变量替换 |
| `GoTemplate` | `{{.Name}}` | 标准库 `text/template` | 需要条件、循环、函数 |
| `Jinja2` | `{{ name }}` | gonja（较重） | 从 Python 项目迁移过来的 prompt |

**选 `FString` 除非你有明确理由。** 它最轻，语法最像 Python 的 `str.format`，写 prompt 时最直观。

### FString 的坑：字面花括号必须转义

如果你的 prompt 里包含 JSON 示例：

```
请返回如下格式：
{"name": "...", "age": 0}
```

用 `FString` 格式化时，`{` 会被当成占位符起始符，直接报错：

```
unexpected '{' in field name
```

正确写法是把字面花括号双写：

```
请返回如下格式：
{{"name": "...", "age": 0}}
```

渲染后得到单个 `{` 和 `}`。

**这个坑在 Agent 场景下会被放大**，因为 `defaultGenModelInput` 会自动用 `FString` 格式化 instruction——只要存在 `SessionValues`（见 [3.6](#36-defaultgenmodelinput每轮重拼的代价)）。也就是说：**你的 instruction 里只要有 JSON 示例，一旦用了 `WithSessionValues`，就会报错**。

### `MessagesPlaceholder`：展开多条消息

```go
// schema/message.go:619
func (p *messagesPlaceholder) Format(_ context.Context, vs map[string]any, _ FormatType) ([]*Message, error)
```

用法是把一个 `[]*Message` 塞进模板的指定位置。典型场景是"历史消息"：

```go
chatTemplate := prompt.FromMessages(
    schema.SystemMessage("you are an eino helper"),
    schema.MessagesPlaceholder("history", false),  // 展开 vs["history"]
)
msgs, err := chatTemplate.Format(ctx, map[string]any{
    "history": historyMessages,
})
```

第二个参数 `optional`：`false` 表示 `history` 必须存在，缺失时报错；`true` 表示可以缺失。

**这个 API 在 Agent 场景下基本用不到**，因为 Agent 自己管理消息历史。它主要用于纯 Chain 场景（prompt → model → parser）。

## 1.8 AgenticMessage：另一条消息路径

前面所有内容都是 Message 路径。现在看 Agentic 路径。

`schema/agentic_message.go:71`：

```go
type AgenticMessage struct {
    Role AgenticRoleType `json:"role"`
    ContentBlocks []*ContentBlock `json:"content_blocks,omitempty"`
    ResponseMeta *AgenticResponseMeta `json:"response_meta,omitempty"`
    Extra map[string]any `json:"extra,omitempty"`
}
```

四个字段。对比 `Message` 的 12 个，差异巨大。

### 核心差异：工具调用从"字段"变成"块"

Message 路径里，工具调用是消息的**字段**：

```go
// assistant 消息
Message{Role: Assistant, ToolCalls: []ToolCall{...}}
// tool 消息
Message{Role: Tool, ToolCallID: "call_a", Content: "结果"}
```

Agentic 路径里，工具调用是消息内容里的**块**：

```go
AgenticMessage{
    Role: AgenticRoleTypeAssistant,
    ContentBlocks: []*ContentBlock{
        {Type: ContentBlockTypeAssistantGenText, AssistantGenText: &AssistantGenText{Text: "我来查一下"}},
        {Type: ContentBlockTypeFunctionToolCall, FunctionToolCall: &FunctionToolCall{CallID: "call_a", Name: "search", Arguments: "..."}},
    },
}
```

**后果**：

1. **不需要 `tool` 角色**。工具结果作为 `function_tool_result` 块，塞进 `user` 或 `assistant` 消息里。所以 `AgenticRoleType` 只有三个值（`schema/agentic_message.go:65`）：

```go
const (
    AgenticRoleTypeSystem    AgenticRoleType = "system"
    AgenticRoleTypeUser      AgenticRoleType = "user"
    AgenticRoleTypeAssistant AgenticRoleType = "assistant"
)
```

2. **一条消息可以同时包含文本和工具调用**。Message 路径也能做到（`Content` + `ToolCalls`），但 Agentic 路径能表达**顺序**：先说话、再调用、再说话。

3. **支持服务端工具和 MCP**。这是 Message 路径做不到的，因为 OpenAI 的 `tools` 只有客户端工具概念。

### ContentBlock 的结构：类型标签 + 可选载荷

`schema/agentic_message.go:102`：

```go
type ContentBlock struct {
    Type ContentBlockType `json:"type"`
    Reasoning *Reasoning `json:"reasoning,omitempty"`
    UserInputText *UserInputText `json:"user_input_text,omitempty"`
    UserInputImage *UserInputImage `json:"user_input_image,omitempty"`
    // ... 共 20 个可选载荷字段
    StreamingMeta *StreamingMeta `json:"streaming_meta,omitempty"`
    Extra map[string]any `json:"extra,omitempty"`
}
```

这是 Go 里模拟 sum type 的常见手法：**一个 `Type` 标签 + 20 个可能为 nil 的载荷指针**。

代价很明显：你必须在读取前判断 `Type`，再判断对应字段非 nil。框架**不校验**一致性——和 [1.3](#陷阱type-与填充字段必须匹配) 说的问题一样。

### 与 Message 的互转

**框架不提供自动互转**。你不能把一个 `*schema.Message` 直接当 `*schema.AgenticMessage` 用，因为 `MessageType` 是封闭联合，且两者的语义不等价。

如果要在一个系统里同时支持两条路径，你必须自己写转换，并且明确转换的**有损点**：

| 转换方向 | 有损的地方 |
|---|---|
| Message → Agentic | `ToolCalls` 变成 block，`tool` 角色的消息需要合并进 user 消息；`Name` 字段无处安放 |
| Agentic → Message | 服务端工具块、MCP 块、审批块**全部丢失**；多条文本块需要拼接 |

### 选型建议

**选 Message 路径，如果**：

- 用 OpenAI / Ark / DeepSeek / Qwen / Ollama 等 Chat Completion 风格 API；
- 工具都是你自己实现的客户端函数；
- 不需要 MCP。

**选 Agentic 路径，如果**：

- 用 Claude 的原生 tool use，或 Gemini 的 function calling 协议；
- 需要服务端工具（模型侧直接执行 web search / code interpreter）；
- 需要 MCP 生态；
- 需要人工审批流。

**不要混用**。同一个 Agent 只能走一条路径——`adk` 内部通过 `switch any(zero).(type)` 分派到 `buildMessageReActRunFunc` 或 `buildAgenticReActRunFunc`（`adk/chatmodel.go:1115` / `1246`），两条路径的图结构、工具节点、事件构造都不一样。

## 1.9 StreamReader：流式消费协议

所有流式 API（`ChatModel.Stream`、`StreamableTool.StreamableRun`、`AgentEvent.MessageStream`）都返回 `*schema.StreamReader[T]`。

### 三个核心方法

`schema/stream.go:195`：

```go
func (sr *StreamReader[T]) Recv() (T, error)
```

标准消费模式（源码注释直接给了）：

```go
for {
    chunk, err := sr.Recv()
    if errors.Is(err, io.EOF) {
        break
    }
    if err != nil {
        panic(err)
    }
    fmt.Println(chunk)
}
```

`schema/stream.go:229`：

```go
// Close 安全关闭 StreamReader。
// 它只应调用一次，多次调用可能不符合预期。
// 注意：使用 Recv() 之后务必调用 Close()。
func (sr *StreamReader[T]) Close()
```

**必须 `defer sr.Close()`**。不关的后果：生产者 goroutine 阻塞在发送上（如果底层是带缓冲 channel），或者缓冲区泄漏。

`schema/stream.go:261`：

```go
// Copy 创建 n 个独立的 StreamReader，每个都能收到
// 原流的每一个元素。Copy 之后原 StreamReader 不可再用。
func (sr *StreamReader[T]) Copy(n int) []*StreamReader[T]
```

### Copy 的语义陷阱

源码注释写得很清楚：**`Copy` 之后原 reader 不可用**。

```go
copies := sr.Copy(2)
sr1, sr2 := copies[0], copies[1]
// 此时 sr 已经不能用了，调 sr.Recv() 行为未定义
defer sr1.Close()
defer sr2.Close()
```

**什么时候需要 Copy？**

当同一个流要被两处消费时。典型场景：

- 一边推给前端 SSE，一边累积完整消息存库；
- 一边给回调 handler 做日志，一边给下一个节点处理。

源码注释给的例子就是这个：

```go
// 当两个以上处理分支需要同一条流时使用 Copy——
// 例如一条流既要喂给回调 handler，又要喂给
// 图中的下一个节点。
```

**`n < 2` 时返回原 reader 本身**：

```go
if n < 2 {
    return []*StreamReader[T]{sr}
}
```

所以 `Copy(1)` 不会创建副本，就是 `[]*StreamReader[T]{sr}`。这个行为容易误判——你以为得到了独立副本，实际上是同一个。

### SetAutomaticClose：不能替代 defer

`schema/stream.go:279`：

```go
func (sr *StreamReader[T]) SetAutomaticClose()
```

它的实现依赖 `runtime.SetFinalizer`——在 GC 回收时自动关闭。

**为什么不能依赖它？**

1. **GC 时机不确定**。Go 的 GC 是并发的、非实时的。一个流可能存活很久，在此期间生产者一直阻塞。
2. **`SetFinalizer` 本身有局限**。对象如果被其他对象引用形成环，finalizer 可能不执行；程序退出时 finalizer 也不保证执行。
3. **框架自己也是这么说的**。`adk/interface.go:453` 的 `TypedAgent.Run` 注释：

```go
// 注意：建议对 AsyncIterator 发出的 AgentEvent 中的 MessageStream
// 调用 SetAutomaticClose()，这样即使事件没有被处理，
// MessageStream 也能被关闭。
```

注意措辞是 **recommended**，场景是"事件没被处理时兜底"。**正常路径仍然必须 `defer Close()`**。

### 为什么 StreamReader 只能读一次

`StreamReader` 不是 `io.Reader`——它没有 `Seek`，没有缓冲重放。底层要么是一个 channel（`stream[T]`），要么是一个数组（`arrayReader[T]`），要么是多流合并（`multiStreamReader[T]`）。

一旦 `Recv` 消费了一个元素，它就没了。所以：

- 不能"先扫一遍看有多少个工具调用，再从头读一遍"；
- 不能"读失败后重试"；
- 想多次消费，只能 `Copy`。

# 第 2 章　ChatModel：只负责和模型通信

## 2.1 接口的三层结构

`components/model/interface.go` 里定义了五个类型，它们的关系是一条继承链：

```
BaseModel[M]                      ← 最底层，泛型，只有 Generate/Stream
    ├── BaseChatModel             ← = BaseModel[*schema.Message]
    │       ├── ChatModel         ← + BindTools（已弃用）
    │       └── ToolCallingChatModel ← + WithTools（推荐）
    └── AgenticModel              ← = BaseModel[*schema.AgenticMessage]
```

### BaseModel：只有两个方法

`components/model/interface.go:36`：

```go
type BaseModel[M messageType] interface {
    Generate(ctx context.Context, input []M, opts ...Option) (M, error)
    Stream(ctx context.Context, input []M, opts ...Option) (*schema.StreamReader[M], error)
}
```

注意这里的约束名是小写的 `messageType`（不是 `adk.MessageType`）。这是 `components/model` 包内部的约束定义，和 `adk` 包的那个是**两个独立的 sealed union**，只是成员相同。

为什么要分开？因为分层：`components/model` 不应该依赖 `adk`。这是依赖方向的问题——组件层是底层，ADK 是上层。

### BaseChatModel：别名，不是新类型

`components/model/interface.go:71`：

```go
type BaseChatModel = BaseModel[*schema.Message]
```

`=` 表示**类型别名**，不是定义新类型。所以 `BaseChatModel` 和 `BaseModel[*schema.Message]` 完全等价，可以互相赋值、互相断言。

源码注释解释了它的存在：

```go
// BaseChatModel 是 BaseModel 特化到 *schema.Message 的向后兼容别名。
// 所有使用 model.BaseChatModel 的既有代码
// 无需修改即可继续工作。
```

这是泛型化改造时保留向后兼容的手法。v0.8 之前只有 `BaseChatModel`，v0.9 引入泛型后加了 `BaseModel[M]`，用别名把老的接上。

**对你的影响**：写新代码时用 `model.BaseModel[M]`（泛型友好），读老代码时看到 `BaseChatModel` 就理解为 `*schema.Message` 特化版。

### ChatModel：已弃用

`components/model/interface.go:80`：

```go
// 已弃用：请改用 [ToolCallingChatModel]。
//
// ChatModel 通过 [ChatModel.BindTools] 在 [BaseChatModel] 之上扩展了工具绑定能力。
// BindTools 原地修改实例，同一实例被并发使用时会引发竞态：
// 一个 goroutine 的工具列表可能
// 覆盖另一个的。建议改用 [ToolCallingChatModel.WithTools]，它返回
// 一个新的不可变实例，并发安全。
type ChatModel interface {
    BaseChatModel

    // BindTools 把工具绑定到模型。
    // 通常在请求 ChatModel 之前先 BindTools。
    // 注意 BindTools 与 Generate 之间并非原子操作。
    BindTools(tools []*schema.ToolInfo) error
}
```

源码注释里有两处明确提到并发问题：

1. 类型级注释："`BindTools` mutates the instance in place, which causes a race condition"
2. 方法级注释："notice the non-atomic problem of BindTools and Generate"

**这不是理论风险，是实际会出的事故**。场景：

```go
// 假设 base 是共享的 *openai.ChatModel
base.BindTools(toolsA)   // goroutine 1 绑定工具集 A
// ... 中间被调度 ...
base.Generate(ctx, msgs) // 此刻 tools 可能已被 goroutine 2 改成 B
```

结果：goroutine 1 的请求带着 goroutine 2 的工具集发给模型。模型可能调用了 A 里没有的工具，或者该调 A 却调了 B。

### ToolCallingChatModel：推荐

`components/model/interface.go:99`：

```go
// ToolCallingChatModel 在 [BaseChatModel] 之上扩展了安全的工具绑定能力。
//
// 与已弃用的 [ChatModel.BindTools] 不同，[ToolCallingChatModel.WithTools]
// 不修改接收者——它返回一个附带指定工具的新实例。
// 这使得跨 goroutine 共享基础模型实例是安全的，
// 并可派生出带不同工具集的按请求变体：
//
// base, _ := openai.NewChatModel(ctx, cfg)           // 共享，不带工具
// withSearch, _ := base.WithTools([]*schema.ToolInfo{searchTool})
// withCalc, _  := base.WithTools([]*schema.ToolInfo{calcTool})
type ToolCallingChatModel interface {
    BaseChatModel

    WithTools(tools []*schema.ToolInfo) (ToolCallingChatModel, error)
}
```

源码注释里那个例子就是**正确用法的模板**：

- `base` 全局共享一份，不带工具；
- 每次请求按需 `WithTools` 派生出带特定工具集的实例；
- 派生出的实例互相独立，并发安全。

**代价**：每次 `WithTools` 可能产生一次分配。如果你的模型实现内部深拷贝了配置，高频调用会有 GC 压力。实际影响通常可忽略，但要知道这个权衡存在。

### AgenticModel：无 WithTools

`components/model/interface.go:109`：

```go
// AgenticModel 是 BaseModel 特化到 *schema.AgenticMessage 的类型别名。
// 与 ToolCallingChatModel 不同，agentic 模型
// 不提供 WithTools 方法；工具通过
// model.WithTools 选项在请求时传入，与 ChatModelAgent 绑定工具的方式一致。
type AgenticModel = BaseModel[*schema.AgenticMessage]
```

**关键差异**：Agentic 模型没有 `WithTools` 方法，工具通过**调用时选项** `model.WithTools` 传入。

为什么设计不一样？因为 Agentic 协议里工具列表是每次请求的一部分（和服务端工具、MCP 工具一起放在请求体里），不是一个"模型实例的属性"。

### 实现关系检查

写适配器时怎么确认实现了哪个接口？用编译期断言：

```go
var _ model.ToolCallingChatModel = (*MyModel)(nil)
```

如果没实现，编译直接报错，比运行时 panic 好。

**注意**：一个类型可以同时实现 `ChatModel` 和 `ToolCallingChatModel`。`eino-ext` 的 openai 实现就是这样——既有 `BindTools`（兼容老代码），也有 `WithTools`（推荐）。你在 `adk` 里看到的是 `model.BaseModel[M]`，因为 Agent 只用 `Generate`/`Stream`，工具通过 `model.WithTools` 选项传。

源码里用两行注释把它切成了三组。逐个讲。

### 通用组（8 个）

| 字段 | 类型 | 作用 | 注意 |
|---|---|---|---|
| `Temperature` | `*float32` | 采样温度，控制随机性 | 与 `TopP` 通常只调一个 |
| `Model` | `*string` | 模型名，运行时覆盖 | 适配器可拒绝不支持的模型 |
| `TopP` | `*float32` | 核采样 | 同上 |
| `Tools` | `[]*schema.ToolInfo` | 工具列表 | 这是 Agent 传工具的实际通道 |
| `DeferredTools` | `[]*schema.ToolInfo` | 延迟加载的工具 | 见下 |

| `Stop` | `[]string` | 停止词 | 各厂商行为有差异 |

**`DeferredTools` 是什么**（`option.go:28` 的注释）：

```go
// DeferredTools 是一批以 defer_loading=true 注册的工具，
// 用于模型内置的（服务端）工具搜索能力。
// 这些工具会发给模型 API，但不会预先载入上下文——
// 模型只能看到它们的名称和描述。模型的
// 内置工具搜索工具会在其中检索，并按需
// 加载匹配的工具。
```

**这是解决"工具太多塞不下"的关键能力**。假设你有 500 个工具：

- 传统做法：全部塞进 `Tools`，光工具定义就吃掉几万 token，而且模型容易选错；
- `DeferredTools`：只把工具名和描述发过去（不占正式 context），模型用内置的搜索工具按需拉取完整定义。

**前置条件**：模型必须支持服务端工具搜索（目前是 Anthropic 和部分 OpenAI 模型）。不支持的模型会忽略这两个字段，你的工具就全部不可见了——**这是个静默失败**。

**`ToolSearchTool`** 是那个"搜索工具"本身的 schema。如果模型有内置的，通常不用自己提供；提供它意味着你要自定义搜索行为。

### ChatModel 专属组（2 个）

```go
// ToolChoice 控制模型调用哪个工具。
ToolChoice *schema.ToolChoice

// AllowedToolNames 指定模型允许调用的工具名列表。
// 这样可以把模型约束在可用工具的一个特定子集上。
AllowedToolNames []string
```

`ToolChoice` 是枚举，见 [2.5](#25-toolchoice三个值)。

`AllowedToolNames` 是**白名单**：即使 `Tools` 里有 10 个，只有名单里的能被调用。

**为什么这个字段重要？** 因为它提供了"软性工具权限控制"：

```go
model.WithToolChoice(schema.ToolChoiceAllowed, "search", "read_file")
```

模型看得到全部工具（因为 `Tools` 没变），但只能调这两个。相比"从 `Tools` 里删掉"的做法，白名单的优势是：

- 不破坏 prompt 缓存（工具列表没变）；
- 模型仍然知道其他工具存在，可能主动说"我需要 X 能力但我没权限"。

**注意 `WithToolChoice` 是一个函数同时设两个字段**（`option.go:157`）：

```go
func WithToolChoice(toolChoice schema.ToolChoice, allowedToolNames ...string) Option
```

### Agentic 专属组（1 个）

```go
// AgenticToolChoice 控制 agentic 模型如何调用工具。
AgenticToolChoice *schema.AgenticToolChoice
```

`schema/tool.go:67`：

```go
type AgenticToolChoice struct {
    // Type 是工具选择模式。
    Type ToolChoice

    // Allowed 可选，指定模型允许调用的工具列表。
    Allowed *AgenticAllowedToolChoice

    // Forced 可选，指定模型必须调用的工具列表。
    Forced *AgenticForcedToolChoice
}
```

比 `ToolChoice` + `AllowedToolNames` 两个字段的组合更强：它支持 `Forced` 指定**必须调用哪些工具**（可以有参数约束）。

### 为什么所有标量都是指针

`Temperature *float32` 而不是 `float32`。原因：

**零值歧义**。`Temperature = 0` 是合法值（完全确定性输出），和"未设置"无法区分。

用指针：
- `nil` = 未设置，用模型默认值；
- `&0` = 明确要求 0。

`MaxTokens *int` 同理，`0` 不是合法的最大 token 数，但"未设置"和"设成 0"语义不同。

`Tools []*schema.ToolInfo` 是切片，`nil` 和 `[]` 天然可区分，所以不需要指针。

**这个设计有个副作用**：你写代码时要取地址：

```go
temp := float32(0.7)
opts := []model.Option{model.WithTemperature(temp)}
```

`WithTemperature` 内部做了取址（`option.go:71`）：

```go
func WithTemperature(temperature float32) Option {
    return Option{
        apply: func(opts *Options) {
            opts.Temperature = &temperature
        },
    }
}
```

**注意这里 `&temperature` 是取参数变量的地址**。函数返回后这个变量逃逸到堆上，所以是安全的。但它也意味着每次调用都分配一次——高频路径上要注意。

### WithTools 的一个细节

`option.go:116`：

```go
func WithTools(tools []*schema.ToolInfo) Option {
    if tools == nil {
        tools = []*schema.ToolInfo{}
    }
    return Option{
        apply: func(opts *Options) {
            opts.Tools = tools
        },
    }
}
```

**`nil` 被转成空切片**。这是为了区分"没调用 WithTools"（`Tools` 保持 `nil`）和"明确要求无工具"（`Tools` 是空切片）。

为什么这个区别重要？因为 Agent 可能配置了工具，但某个中间件想临时禁用全部工具：

```go
// 中间件里
return model.WithTools([]*schema.ToolInfo{})  // 明确无工具
```

如果传 `nil`，就会被转成空切片——结果一样。但如果你**不调用** `WithTools`，`Tools` 保持 `nil`，Agent 的默认工具会生效。

所以：**想禁用工具，必须显式传空切片或 `nil` 并调用 `WithTools`**。

### WithToolChoice 的签名演进

```go
func WithToolChoice(toolChoice schema.ToolChoice, allowedToolNames ...string) Option
```

第二个参数是可变参数。这意味着：

```go
model.WithToolChoice(schema.ToolChoiceForbidden)          // 禁用工具
model.WithToolChoice(schema.ToolChoiceForced)             // 强制调工具
model.WithToolChoice(schema.ToolChoiceAllowed, "a", "b")  // 允许调 a/b
```

**`ToolChoiceForced` 配 `AllowedToolNames` 才有意义**——否则模型可以调任何工具，只是"必须调至少一个"。

## 2.4 Option 的双通道机制

`components/model/option.go:64`：

```go
// Option 是 ChatModel 的调用期选项。选项不可变且可组合：
// 每个 Option 要么携带通用选项设置函数（经
// [GetCommonOptions] 应用），要么携带实现特定设置函数（经
// [GetImplSpecificOptions] 应用），两者互斥。
type Option struct {
    apply func(opts *Options)
    implSpecificOptFn any
}
```

两个字段，**互斥**——一个 `Option` 要么带 `apply`（通用选项），要么带 `implSpecificOptFn`（实现特定选项）。

### 为什么要双通道

通用选项是**跨实现**的：`Temperature`、`MaxTokens` 这些所有模型都有。

但每个厂商有自己独有的参数：

- OpenAI：`reasoning_effort`、`response_format`、`seed`
- Anthropic：`thinking.budget_tokens`、`top_k`
- Ark：`thinking.type`

如果把这些都塞进 `Options`，结构体会膨胀成几百个字段，而且每加一个厂商就要改核心库。

**解法**：让适配器定义自己的选项类型，通过 `implSpecificOptFn` 通道传递。

### 使用方式

适配器侧定义一个自己的 options 结构：

```go
// 假设这是某个适配器的内部类型
type myImplOptions struct {
    Seed         *int
    ResponseFormat string
}

// 暴露一个构造函数
func WithSeed(seed int) model.Option {
    return model.WrapImplSpecificOptFn(func(o *myImplOptions) {
        o.Seed = &seed
    })
}
```

调用方无感——混在一起传：

```go
resp, err := m.Generate(ctx, msgs,
    model.WithTemperature(0.7),   // 通用
    mypkg.WithSeed(42),            // 实现特定
)
```

### 分发逻辑

`components/model/option.go:211`：

```go
func GetCommonOptions(base *Options, opts ...Option) *Options
```

`components/model/option.go:239`：

```go
func GetImplSpecificOptions[T any](base *T, opts ...Option) *T
```

**每个 Option 只会被其中一个消费**：

- `GetCommonOptions` 只处理 `apply != nil` 的；
- `GetImplSpecificOptions[T]` 只处理 `implSpecificOptFn` 能断言成 `func(*T)` 的。

所以通用选项不会"泄漏"到实现特定通道，反之亦然。

### 陷阱：类型不匹配时静默忽略

`GetImplSpecificOptions[T]` 的 `T` 由调用方指定。如果适配器内部写错了类型：

```go
// 适配器内部
opts := model.GetImplSpecificOptions(&myImplOptions{}, opts...)
```

而用户传的是另一个包的 `WithSeed`（假设有同名但不同类型），断言失败，**这个选项被静默丢弃**。

没有报错，没有警告。你的 `Seed=42` 就这么没了。

**排查方法**：如果某个实现特定选项"没生效"，先确认它的 `implSpecificOptFn` 闭包参数类型和 `GetImplSpecificOptions` 的 `T` 一致。

## 2.5 ToolChoice：三个值

`schema/tool.go:48`：

```go
type ToolChoice string

const (
    // ToolChoiceForbidden 指示模型不要调用任何工具，即使已绑定工具。
    // 此时模型改为返回纯文本消息。
    // 对应 OpenAI Chat Completion 中的 "none"。
    ToolChoiceForbidden ToolChoice = "forbidden"

    // ToolChoiceAllowed 由模型自行决定：可以生成纯文本消息，
    // 也可以调用一个或多个工具。这是提供工具时的默认值。
    // 对应 OpenAI Chat Completion 中的 "auto"。
    ToolChoiceAllowed ToolChoice = "allowed"

    // ToolChoiceForced 要求模型至少调用一个工具。
    // 需要借助工具调用保证结构化输出时使用。
    // 对应 OpenAI Chat Completion 中的 "required"。
    ToolChoiceForced ToolChoice = "forced"
)
```

| Eino 值 | OpenAI 对应 | 行为 |
|---|---|---|
| `forbidden` | `"none"` | 不调工具，纯文本回复 |
| `allowed` | `"auto"` | 模型自己决定（**默认**） |
| `forced` | `"required"` | 必须调至少一个工具 |

### forbidden 的实际用途

不是"我想让模型别调工具"这么简单。真正的用途是**强制收尾**。

Agent 循环里，模型可能一直调工具不停（尤其工具返回"失败，请重试"时）。你可以：

1. 检测迭代次数接近上限；
2. 用 `WithToolChoice(ToolChoiceForbidden)` 强制模型给文字回答；
3. 避免撞上 `ErrExceedMaxIterations`。

**这比直接让 Agent 报错要好得多**——用户至少能得到一个"我尝试了但没成功"的回答。

### forced 的实际用途

**结构化输出**。想要模型返回一个严格 JSON，但不想依赖 `response_format`（各厂商支持不一）：

```go
// 定义一个只有一个参数的"工具"
type ReportArgs struct {
    Title   string   `json:"title" jsonschema:"description=报告标题"`
    Summary string   `json:"summary" jsonschema:"description=摘要"`
    Tags    []string `json:"tags" jsonschema:"description=标签列表"`
}

reportTool := utils.NewTool(&schema.ToolInfo{
    Name: "submit_report",
    Desc: "提交最终报告",
    ParamsOneOf: schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
        "title":   {Type: schema.String, Desc: "报告标题", Required: true},
        "summary": {Type: schema.String, Desc: "摘要", Required: true},
        "tags":    {Type: schema.Array, ElemInfo: &schema.ParameterInfo{Type: schema.String}, Desc: "标签列表"},
    }),
}, func(ctx context.Context, args *ReportArgs) (string, error) {
    // args 就是结构化结果
    return "ok", nil
})
```

配 `WithToolChoice(schema.ToolChoiceForced)`，模型必然调用它，`Arguments` 就是你要的 JSON。

**代价**：多一轮请求（模型调工具 → 你返回结果 → 模型再总结）。除非你像上面那样在工具里直接拿到结果就结束。

### 默认值是 allowed

源码注释明确："This is the default when tools are provided."

所以你不设置 `ToolChoice` 时，模型可以自由决定调不调工具。这通常是期望行为。

**但要注意**：`ToolChoice` 为 `nil`（未设置）和 `&ToolChoiceAllowed` 不完全等价——前者让适配器用自己的默认值，后者明确要求 `auto`。对绝大多数适配器结果相同，但严格来说前者更"不干涉"。

## 2.6 Generate vs Stream：什么时候用哪个

`components/model/interface.go:37`：

```go
Generate(ctx context.Context, input []M, opts ...Option) (M, error)
Stream(ctx context.Context, input []M, opts ...Option) (*schema.StreamReader[M], error)
```

### 语义差异

| | `Generate` | `Stream` |
|---|---|---|
| 返回 | 完整消息 | 消息流 |
| 阻塞 | 直到生成完毕 | 立即返回 reader |
| 首字延迟 | = 总生成时间 | 很短 |
| 内存 | 一次性 | 逐片 |
| 错误位置 | 返回值 | 流里的 error |
| 工具调用 | `Message.ToolCalls` 完整 | 分片，需 `ConcatMessages` |

### 该用哪个

**用 `Generate`，如果**：

- 后台任务（批处理、定时总结），不需要实时反馈；
- 你只需要最终结果；
- 结果要落库，流式没有收益。

**用 `Stream`，如果**：

- 有前端在等（聊天界面）；
- 生成时间长（长文、代码），用户需要看到进度；
- 你想尽早开始处理（比如边生成边 TTS）。

### Agent 里怎么选

`adk.Runner` 的 `EnableStreaming` 决定（见 [4.2](#42-runner-的五项职责)）：

```go
runner := adk.NewRunner(ctx, adk.RunnerConfig{
    Agent:           agent,
    EnableStreaming: true,   // 模型输出走 Stream
})
```

**注意这个开关影响的是"模型输出"，不是"工具输出"**。工具是否流式由工具自己实现哪个接口决定。

### 流式下的三个陷阱

**陷阱 1：`IsStreaming == true` 时 `Message` 必为 nil**

`adk/interface.go:73` 的 `TypedMessageVariant`：

```go
type TypedMessageVariant[M MessageType] struct {
    IsStreaming bool
    Message       M
    MessageStream *schema.StreamReader[M]
    // ...
}
```

`typedEventFromMessage`（`adk/interface.go:247`）的构造：

```go
&TypedMessageVariant[M]{
    IsStreaming:   msgStream != nil,
    Message:       msg,
    MessageStream: msgStream,
}
```

流式时 `msgStream != nil`，而调用方传的 `msg` 通常是 `nil`（内容还没生成完）。

```go
// 错误：panic: nil pointer dereference
fmt.Println(ev.Output.MessageOutput.Message.Content)

// 正确
mv := ev.Output.MessageOutput
if mv.IsStreaming {
    msg, err := mv.GetMessage()   // 内部调 ConcatMessages
} else {
    msg := mv.Message
}
```

**陷阱 2：流必须消费完才能拿到工具调用**

流式下，`ToolCalls` 是分片到达的（见 [1.5](#15-concatmessages流式拼接的全部真相)）。你不读完流，就不知道模型要调什么工具。

这意味着：**流式 Agent 在工具调用场景下，首字延迟优势会打折扣**。用户看到"我来查一下"，然后等工具执行完才有下一段输出。

**陷阱 3：流式下错误在流里**

```go
sr, err := m.Stream(ctx, msgs)
if err != nil {
    return err   // 这是"建立流"的错误（参数错误、连接失败）
}

for {
    chunk, err := sr.Recv()
    if errors.Is(err, io.EOF) {
        break
    }
    if err != nil {
        // 这是"流中途"的错误（超时、服务端断开）
        return err
    }
    // ...
}
```

两类错误必须分开处理。`Stream` 返回的 error 只覆盖第一类。

```go
	"context"
	"errors"
	"fmt"
	"io"

	"github.com/cloudwego/eino/components/model"

type fakeModel struct {
	name  string
	tools []*schema.ToolInfo
	// 实现特定选项

// 编译期断言：必须实现接口
var _ model.ToolCallingChatModel = (*fakeModel)(nil)

func (f *fakeModel) Generate(ctx context.Context, input []*schema.Message,
	opts ...model.Option) (*schema.Message, error) {

	o := model.GetCommonOptions(nil, opts...)
	impl := model.GetImplSpecificOptions(&fakeImplOptions{}, opts...)

	// WithTools 绑定的工具作为默认值；调用时 WithTools 选项可覆盖

	}
	if len(o.AllowedToolNames) > 0 {
		content += fmt.Sprintf(" allowed=%v", o.AllowedToolNames)
	}
	if impl.Seed != nil {
		content += fmt.Sprintf(" seed=%d", *impl.Seed)
	}

	return schema.AssistantMessage(content, nil), nil
}

func (f *fakeModel) Stream(ctx context.Context, input []*schema.Message,
	opts ...model.Option) (*schema.StreamReader[*schema.Message], error) {

	full, err := f.Generate(ctx, input, opts...)
	if err != nil {
		return nil, err
	}

	sr, sw := schema.Pipe[*schema.Message](1)
	go func() {
		defer sw.Close()
		// 拆成三片发送
		runes := []rune(full.Content)
		n := len(runes) / 3
		for i := 0; i < 3; i++ {
			start, end := i*n, (i+1)*n
			if i == 2 {
				end = len(runes)
			}
			sw.Send(schema.AssistantMessage(string(runes[start:end]), nil), nil)
		}
	}()
	return sr, nil
}

// WithTools 返回新实例，不改接收者
func (f *fakeModel) WithTools(tools []*schema.ToolInfo) (model.ToolCallingChatModel, error) {
	clone := *f
	clone.tools = tools
	return &clone, nil
}

// ---- 实现特定选项 ----
type fakeImplOptions struct {
	Seed *int
}

func WithSeed(seed int) model.Option {
	return model.WrapImplSpecificOptFn(func(o *fakeImplOptions) {
		o.Seed = &seed
	})
}

	base := &fakeModel{name: "fake-1"}

	// 2. 通用选项 + 实现特定选项混用
	fmt.Println("选项混用:", mustGenerate(ctx, base,
		model.WithTools([]*schema.ToolInfo{searchTool}),
		model.WithTemperature(0.3),
		model.WithToolChoice(schema.ToolChoiceForced),

		model.WithToolChoice(schema.ToolChoiceForbidden),

	sr, err := base.Stream(ctx, []*schema.Message{schema.UserMessage("hi")},

		panic(err)

	for {
		c, err := sr.Recv()
		if errors.Is(err, io.EOF) {
			break
		}
		if err != nil {
			sr.Close()
			panic(err)
		}
		chunks = append(chunks, c)
	}
	sr.Close()

	full, err := schema.ConcatMessages(chunks)
	if err != nil {
		panic(err)
	}
	fmt.Printf("流式 %d 片 -> %q\n", len(chunks), full.Content)
}

func mustGenerate(ctx context.Context, m model.ToolCallingChatModel, opts ...model.Option) string {

	if err != nil {
		panic(err)
	}
	return msg.Content
}
```

**`Name`**（`chatmodel.go:262`）：

- 要作为子 Agent（`NewAgentTool`）：**必须非空**，否则 `NewAgentTool` 返回的 tool 名是空的，模型无法调用。

**`Description`**（`chatmodel.go:266`）：

```go
// Agent 能力的描述。
// 帮助其他 Agent 判断是否把任务转交给本 Agent。
```

写 `Description` 的原则：**描述能力边界，不描述实现**。

```go
// 差：模型不知道什么时候该用
```

### 边的定义

`adk/react.go:487` 起：

```go
_ = g.AddEdge(compose.START, initNode_)
_ = g.AddEdge(initNode_, chatModel_)
```

进入模型。

`react.go:499` 的分支：

```go
toolCallCheck := func(ctx context.Context, sMsg MessageStream) (string, error) {
    defer sMsg.Close()
    for {
        chunk, err_ := sMsg.Recv()
        if err_ != nil {
            if err_ == io.EOF {
                return terminalNode, nil     // 无工具调用 → 终止
            }
            return "", err_
        }
        if len(chunk.ToolCalls) > 0 {
            return cancelCheckNode_, nil     // 有工具调用 → 继续
        }
    }
}
branch := compose.NewStreamGraphBranch(toolCallCheck, map[string]bool{
    terminalNode:      true,
    cancelCheckNode_:  true,
})
_ = g.AddBranch(chatModel_, branch)
```

**这是整个 Agent 的核心决策点**。三个细节值得注意：

1. **流式扫描**。它接收 `MessageStream`，边收边判断。一旦发现 `ToolCalls` 就立即返回，**不消费剩余流**（`defer sMsg.Close()` 关闭）。
2. **`io.EOF` 才终止**。流正常结束且没有工具调用 → 终止。
3. **流错误直接向上抛**。`return "", err_` 让整个图失败。

**为什么用流式扫描而不是等完整消息？**

因为性能。如果等完整消息，模型生成完整回答后才判断"要不要调工具"——但带工具调用的响应通常很短（只是工具调用，没有长文本）。流式扫描能让"决定调工具"这一步提前完成。

`react.go:520` 起：

```go
_ = g.AddEdge(cancelCheckNode_, toolNode_)
_ = g.AddEdge(toolNode_, afterToolCallsNode_)
_ = g.AddEdge(afterToolCallsNode_, afterToolCallsCancelCheckNode_)
```

工具执行链。

`react.go:525` 起的 `ReturnDirectly` 分支：

```go
if len(config.toolsReturnDirectly) > 0 {
    cvt := func(ctx context.Context, toolResults []Message) (Message, error) {
        id, _ := getReturnDirectlyToolCallID(ctx)
        for _, msg := range toolResults {
            if msg != nil && msg.ToolCallID == id {
                return msg, nil
            }
        }
        return nil, errors.New("return directly tool call result not found")
    }
    _ = g.AddLambdaNode(toolNodeToEndConverter, compose.InvokableLambda(cvt), ...)
    _ = g.AddEdge(toolNodeToEndConverter, terminalNode)

    checkReturnDirect := func(ctx context.Context, toolResults []Message) (string, error) {
        _, ok := getReturnDirectlyToolCallID(ctx)
        if ok {
            return toolNodeToEndConverter, nil
        }
        return chatModel_, nil
    }
    returnDirectBranch := compose.NewGraphBranch(checkReturnDirect, map[string]bool{
        toolNodeToEndConverter: true,
        chatModel_:             true,
    })
    _ = g.AddBranch(afterToolCallsCancelCheckNode_, returnDirectBranch)
} else {
    _ = g.AddEdge(afterToolCallsCancelCheckNode_, chatModel_)   // 无 ReturnDirectly，直接回环
}
```

**`ReturnDirectly` 的机制**：如果某个工具被配置为"直接返回"，它执行完后不回到模型，而是直接把工具结果作为最终回答。

这省了一次模型调用。适合"查数据库返回原始记录"这类场景——模型总结反而是多余的。

## 3.4 迭代上限的实现

### 默认值 20

`adk/react.go:345`：

```go

if config.maxIterations > 0 {
    maxIter = config.maxIterations
}
st.setRemainingIterations(maxIter)
```

在 `genReactState` 里初始化 state 时设置。

**注意 `config.maxIterations > 0` 的判断**：设成负数或 0 都会用默认值 20，不是"无限"或"零次"。想限制到很少的迭代，最少设 1。

### 检查位置

`adk/react.go:390`：

```go
_ = g.AddChatModelNode(chatModel_, wrappedModel, compose.WithStatePreHandler(
    func(ctx context.Context, input []Message, st *State) ([]Message, error) {
        if st.getRemainingIterations() <= 0 {
            return nil, ErrExceedMaxIterations
        }
        st.decrementRemainingIterations()
        return input, nil
    }), compose.WithNodeName(chatModel_))
```

**在调用模型之前检查并递减**。所以：

- 第 1 次调用：`RemainingIterations = 20`，检查通过，减到 19；
- 第 20 次调用：`RemainingIterations = 1`，检查通过，减到 0；
- 第 21 次调用：`RemainingIterations = 0`，返回 `ErrExceedMaxIterations`。

所以 `MaxIterations = 20` 意味着**最多 20 次模型调用**。

### 错误类型

`adk/react.go:33`：

```go
var ErrExceedMaxIterations = errors.New("exceeds max iterations")
```

**这是一个可以直接 `errors.Is` 判断的哨兵错误**：

```go
if errors.Is(err, adk.ErrExceedMaxIterations) {
    // 迭代超限，通常是工具陷入死循环
}
```

### 什么时候会撞上限

典型场景：

1. **工具总是失败**，模型反复重试。比如搜索 API 挂了，模型看到"错误"就再试一次。
2. **工具返回空结果**，模型以为是参数问题，换个参数再试。
3. **任务本身需要很多步**（比如逐文件处理 30 个文件），20 次不够。

**应对策略**：

```go
// 策略 1：调大上限（治标）
MaxIterations: 50,

// 策略 2：用中间件在接近上限时强制收尾（治本）
Handlers: []adk.ChatModelAgentMiddleware{
    &forceFinishHandler{threshold: 15},
},
```

策略 2 的中间件实现（`BeforeModelRewriteState` 里检查剩余迭代数，接近上限时设 `ToolChoiceForbidden`）——但这需要拿到 `RemainingIterations`，而它在 `typedState` 里是导出的（`react.go:35`）：

```go
type typedState[M MessageType] struct {
    // ...
    RemainingIterations int // 为兼容既有检查点而保持导出。
    // ...
}
```

**注意源码注释**："Kept exported for backward compatibility with existing checkpoints. Do not access directly."

所以官方不建议你读它。更稳妥的做法是自己在中间件里计数。

## 3.6 defaultGenModelInput：每轮重拼的代价

这是本章**最重要的性能陷阱**。

### 实现

`adk/chatmodel.go:167`：

```go
func defaultGenModelInput(ctx context.Context, instruction string, input *AgentInput) ([]Message, error) {
    msgs := make([]Message, 0, len(input.Messages)+1)

    if instruction != "" {
        sp := schema.SystemMessage(instruction)

        vs := GetSessionValues(ctx)
        if len(vs) > 0 {
            ct := prompt.FromMessages(schema.FString, sp)
            ms, err := ct.Format(ctx, vs)
            if err != nil {
                return nil, fmt.Errorf("defaultGenModelInput: failed to format instruction using FString template. "+
                    "This formatting is triggered automatically when SessionValues are present. "+
                    "If your instruction contains literal curly braces (e.g., JSON), provide a custom GenModelInput that uses another format. If you are using "+
                    "SessionValues for purposes other than instruction formatting, provide a custom GenModelInput that does no formatting at all: %w", err)
            }
            sp = ms[0]
        }

        msgs = append(msgs, sp)
    }

    msgs = append(msgs, input.Messages...)

    return msgs, nil
}
```

### 三个行为

**（1）每轮都重新构造 system 消息**

`sp := schema.SystemMessage(instruction)` 在**每次模型调用**时执行。Agent 循环 5 轮，就构造 5 次。

内容相同，但它是**新的对象**。这对 prompt 缓存有影响吗？

**取决于缓存实现**：

- 如果缓存按"消息内容"做前缀匹配（大多数实现，包括 Anthropic 的 `cache_control`、OpenAI 的自动缓存）→ 内容相同，缓存命中，没问题；
- 如果缓存按"消息对象 ID"或"指针"匹配 → 每次都是新对象，永远不命中。

**主流实现是按内容匹配的**，所以单纯的重新构造不影响缓存。真正的问题在下一条。

**（2）有 SessionValues 时，instruction 被 FString 格式化**

```go
vs := GetSessionValues(ctx)
if len(vs) > 0 {
    ct := prompt.FromMessages(schema.FString, sp)
    ms, err := ct.Format(ctx, vs)
    // ...
}
```

**只要 `SessionValues` 非空，就会走 FString 格式化**——哪怕你的 instruction 里根本没有占位符。

这带来两个后果：

**后果 A：instruction 里有 JSON 就报错**

```go
Instruction: `你是一个助手。请返回 JSON：{"status": "ok"}`,
```

配 `WithSessionValues(map[string]any{"user": "张三"})`，报错：

```
defaultGenModelInput: failed to format instruction using FString template. ...
```

因为 `{` 被当成占位符起始符。

**修法**：双写花括号 `{{"status": "ok"}}`，或者提供自定义 `GenModelInput`。

**后果 B：SessionValues 里每个 key 都成为潜在占位符**

```go
Instruction: "用户 {user} 提问",
WithSessionValues(map[string]any{
    "user":    "张三",
    "traceID": "abc123",   // 这个也会被格式化上下文读取，但 instruction 里没引用
    "now":     time.Now(),
})
```

只有 `{user}` 被替换。其他 key 不影响格式化（除非 instruction 里有对应占位符）。

**但如果 instruction 里恰好有 `{traceID}`，它也会被替换**。这意味着：`SessionValues` 的 key 和 instruction 里的占位符共享一个命名空间。

### （3）真正摧毁缓存的情况

**情况一：instruction 本身每轮变化**

```go
// 反模式
Instruction: fmt.Sprintf("当前时间：%s。你是助手。", time.Now().Format(time.RFC3339)),
```

每次构造 Agent 都不同——但 Agent 通常只构造一次，所以这不是主要问题。

真正的问题是**通过 SessionValues 注入易变值**：

```go
// 反模式
WithSessionValues(map[string]any{
    "now": time.Now().Format(time.RFC3339),
})
```

配 `Instruction: "当前时间 {now}。你是助手。"`，每一轮的 system 消息都不同：

```
第 1 轮: "当前时间 2026-11-25T10:00:00+08:00。你是助手。"
第 2 轮: "当前时间 2026-11-25T10:00:03+08:00。你是助手。"
```

**prompt 缓存的前缀匹配在第一轮就失效了**。整个 system prompt（可能几千 token）每轮都要重新计费。

**情况二：历史消息每轮变长**

这不算"破坏缓存"——这是正常的。缓存机制通常能处理"前缀相同 + 后缀追加"的模式。只要你**不在前面插入新内容**，缓存仍然有效。

**破坏缓存的操作是在 messages 开头插入或修改内容**。典型错误：

```go
// 反模式：每轮在最前面插入一条"当前时间"
state.Messages = append([]M{schema.SystemMessage("现在是 " + now)}, state.Messages...)
```

这样每轮整个历史的前缀都变了，缓存全废。

### 正确做法

**做法 1：把易变数据放最后**

不要把时间、请求 ID 这类数据放进 system prompt。放在最后一条 user 消息里：

```go
// 好：稳定前缀 + 追加易变内容
msgs := []*schema.Message{
    schema.SystemMessage(stableInstruction),   // 稳定
    // ... 历史 ...
    schema.UserMessage(fmt.Sprintf("[当前时间 %s] %s", now, query)),  // 易变内容在最后
}
```

**做法 2：自定义 GenModelInput**

如果你不需要 f-string 格式化，但需要 `SessionValues` 做别的事：

```go
GenModelInput: func(ctx context.Context, instruction string, input *adk.AgentInput) ([]*schema.Message, error) {
    msgs := make([]*schema.Message, 0, len(input.Messages)+1)
    if instruction != "" {
        msgs = append(msgs, schema.SystemMessage(instruction))  // 不格式化
    }
    msgs = append(msgs, input.Messages...)
    return msgs, nil
},
```

源码的报错信息里明确推荐了这个做法：

> If you are using SessionValues for purposes other than instruction formatting, provide a custom GenModelInput that does no formatting at all.
>
> **译**：如果你用 SessionValues 是为了别的事而非格式化 instruction，请提供一个完全不做格式化的自定义 GenModelInput。

**做法 3：监控 CachedTokens**

见 [1.6](#16-responsemeta-与-tokenusage)。`PromptTokenDetails.CachedTokens` 持续为 0，就说明缓存没生效。

### 一个容易忽略的细节

`msgs := make([]Message, 0, len(input.Messages)+1)` —— 预分配了 `+1` 的容量，说明作者预期"最多加一条 system 消息"。

如果 `instruction == ""`，实际只用了 `len(input.Messages)` 的容量，多分配了一个 slot。这是可忽略的浪费，但反映了设计假设：**一个 Agent 只有一条 system 消息**。

## 3.7 GenModelInput：自定义模型输入

### 类型定义

`adk/chatmodel.go:162`：

```go
type TypedGenModelInput[M MessageType] func(ctx context.Context, instruction string, input *TypedAgentInput[M]) ([]M, error)

// GenModelInput 把 Agent 的 instruction 和输入转换成适合模型的格式。
type GenModelInput = TypedGenModelInput[*schema.Message]
```

三个参数：

- `ctx`：运行上下文，可以读 `SessionValues`；
- `instruction`：已经过 `BeforeAgent` 钩子修改后的最终 instruction（见 `handler.go:87` 的 `ChatModelAgentContext`）；
- `input`：Agent 输入，含 `Messages` 和 `EnableStreaming`。

### 什么时候必须自定义

| 场景 | 为什么默认实现不行 |
|---|---|
| instruction 含 JSON 字面量 + 用了 SessionValues | FString 报错 |
| 要用 GoTemplate / Jinja2 | 默认写死 FString |
| 要注入额外的 system 消息 | 默认只加一条 |
| 要修改历史消息（裁剪、合并） | 默认原样透传 |
| 要用 SessionValues 做别的事 | 默认会尝试格式化 |

### 什么时候不该自定义

**如果你只是想改 system prompt 内容，改 `Instruction` 字段就够了**。

自定义 `GenModelInput` 是重操作：它接管了整个"消息装配"环节，你需要自己处理所有边界（空 instruction、消息顺序、多模态透传）。

### 一个完整的自定义实现

```go
func customGenModelInput(ctx context.Context, instruction string,
    input *adk.AgentInput) ([]*schema.Message, error) {

    msgs := make([]*schema.Message, 0, len(input.Messages)+2)

    // 1. 主 system prompt（不格式化，支持任意字面量）
    if instruction != "" {
        msgs = append(msgs, schema.SystemMessage(instruction))
    }

    // 2. 附加的运行时上下文（放第二条 system，某些模型支持多条）
    if v, ok := adk.GetSessionValue(ctx, "env"); ok {
        msgs = append(msgs, schema.SystemMessage(
            fmt.Sprintf("运行环境：%v", v)))
    }

    // 3. 历史消息原样透传
    msgs = append(msgs, input.Messages...)

    return msgs, nil
}
```

**注意 `adk.GetSessionValue(ctx, "env")` 返回 `(any, bool)`**（`adk/runctx.go:234`），第二个返回值表示 key 是否存在。

## 3.8 ToolsConfig：工具配置

`adk/chatmodel.go:136`：

```go
type ToolsConfig struct {
```

**它内嵌了 `compose.ToolsNodeConfig`**，所以工具节点的所有配置都能用。

### 内嵌的字段

`compose/tool_node.go` 的 `ToolsNodeConfig`：

```go
type ToolsNodeConfig struct {
    Tools []tool.BaseTool
    ToolAliases map[string]ToolAliasConfig
    UnknownToolsHandler func(ctx context.Context, name, input string) (string, error)
    ExecuteSequentially bool
    ToolArgumentsHandler func(ctx context.Context, name, arguments string) (string, error)
    ToolCallMiddlewares []ToolMiddleware

```

逐个讲最常用的几个。

**`ExecuteSequentially`**：

```go
// ExecuteSequentially 决定工具调用是串行（按顺序）还是并行执行。
// 设为 true 时，工具调用按其在输入消息中出现的顺序
// 逐个执行。设为 false（默认）时并行执行。

```

默认**并行**。模型一次要求调 3 个工具，3 个并发执行。

**什么时候要改成串行？**

- 工具之间有依赖（先创建目录再写文件）；
- 工具共享状态（都写同一个文件）；
- 有速率限制（并行会撞限流）。

**`UnknownToolsHandler`**：

```go
// UnknownToolsHandler 处理 LLM 幻觉出不存在的工具时的调用。
// 该字段可选。未设置时，调用不存在的工具会报错。
UnknownToolsHandler func(ctx context.Context, name, input string) (string, error)
```

模型幻觉出一个不存在的工具时，默认行为是**报错**，整个 Agent 失败。

配上这个 handler，可以优雅降级：

```go
UnknownToolsHandler: func(ctx context.Context, name, input string) (string, error) {
    return fmt.Sprintf("工具 %s 不存在。可用的工具请查看工具列表。", name), nil
},
```

返回的字符串会作为工具结果回填给模型，模型看到后通常会纠正自己。

**这是生产环境强烈建议配的**——模型幻觉工具名是常见现象，一个错别字不该让整个请求失败。

**`ToolAliases`**：

```go
type ToolAliasConfig struct {
    // NameAliases 是该工具的备用名称。
    NameAliases []string
    // ArgumentsAliases 把规范参数名映射到其别名列表。
    // key=规范名，value=[]别名。在工具执行前作用于顶层 JSON 键。
    ArgumentsAliases map[string][]string
}
```

两层别名：

- **工具名别名**：模型调 `web_search`，实际执行 `search`；
- **参数名别名**：模型传 `{"q": "..."}`，实际工具签名要 `{"query": "..."}`。

**用途**：兼容不同模型的工具调用习惯。比如某些模型倾向于用简写参数名。

源码注释里的执行顺序很重要：

```go
// 执行顺序：ArgumentsAliases 重映射 → ToolArgumentsHandler → 工具执行
```

**`ToolArgumentsHandler`**：

```go
// ToolArgumentsHandler 允许在工具执行前处理工具参数。
ToolArgumentsHandler func(ctx context.Context, name, arguments string) (string, error)
```

在工具执行前，对原始 JSON 字符串做处理。典型用途：

- 修正模型生成的非法 JSON（比如多了尾随逗号）；
- 注入默认参数；
- 记录日志。

**注意它拿到的是原始字符串，不是解析后的对象**。所以你可以做"字符串级修复"，但也要自己保证输出是合法 JSON。

### ReturnDirectly 的实现细节

前面 [3.3](#33-react-图拓扑) 讲了它的图实现。这里讲用法：

```go
ToolsConfig: adk.ToolsConfig{
    ToolsNodeConfig: compose.ToolsNodeConfig{
        Tools: []tool.BaseTool{queryDBTool, searchTool},
    },
    ReturnDirectly: map[string]bool{
        "query_db": true,   // query_db 执行完直接返回
    },
},
```

**什么工具适合 ReturnDirectly？**

- 返回结构化数据，不需要模型总结的（数据库查询、API 调用）；
- 返回内容很长，模型总结会丢信息的（完整文档）；
- 想让用户直接看到原始结果的（调试工具）。

**什么工具不适合？**

- 需要模型解读的（错误信息需要翻译成用户能懂的话）；
- 需要和其他工具结果合并的；
- 返回值本身没有意义的（"操作成功"）。

### EmitInternalEvents：子 Agent 的流式透传

```go
EmitInternalEvents bool
```

当工具是**子 Agent**（通过 `NewAgentTool` 包装）时，子 Agent 的事件默认**不会**传到父 Agent 的事件流。开启这个开关，子 Agent 的事件会被转发。

源码注释里的三个要点：

1. **不写入父 Agent 的 runSession**。只是转发给消费者，不影响状态和检查点。
2. **`Interrupted` 会传播**（通过 `CompositeInterrupt`），因为中断恢复需要。
3. **`Exit` / `TransferToAgent` / `BreakLoop` 在子 Agent 边界外被忽略**。子 Agent 不能通过 `Exit` 终止父 Agent。

**为什么需要这个开关？** 因为子 Agent 可能有很长的执行过程，用户想看到进度（"正在搜索..."、"找到 3 条结果"）。不开的话，用户只能等子 Agent 整体完成。

## 3.9 EnableStreaming 的传播路径

`EnableStreaming` 是 `AgentInput` 的字段（`adk/interface.go:440`）：

```go
type TypedAgentInput[M MessageType] struct {
    Messages        []M
    EnableStreaming bool
}
```

它决定模型输出走 `Generate` 还是 `Stream`。但它还有一个**副作用**：传播到工具。

`adk/chatmodel.go:1212`：

```go
if mp.input.EnableStreaming {
    runOpts = append(runOpts, compose.WithToolsNodeOption(
        compose.WithToolOption(withAgentToolEnableStreaming(true))))
}
```

`withAgentToolEnableStreaming`（`adk/agent_tool.go:63`）：

```go
func withAgentToolEnableStreaming(enabled bool) tool.Option {
    return tool.WrapImplSpecificOptFn(func(opt *agentToolOptions) {
        opt.enableStreaming = enabled
    })
}
```

**含义**：父 Agent 开了流式，子 Agent 工具也会开流式。

**为什么要传播？** 因为流式是端到端的——如果父 Agent 在流式输出，子 Agent 却用 `Generate` 阻塞，那流式就断了。

**注意这个传播只影响 AgentTool，不影响普通工具**。普通工具是否流式，由它实现 `InvokableTool` 还是 `StreamableTool` 决定。

### 一个实践建议

**除非有明确的流式需求，否则不要开 `EnableStreaming`**。原因：

1. 流式下错误处理更复杂（错误在流里）；
2. 流式下工具调用需要额外拼接；
3. 流式的性能优势只在"有消费者实时读取"时体现。

如果只是后台跑 Agent 拿最终结果，`EnableStreaming: false` 更简单、更可靠。

## 3.10 ModelRetryConfig：重试

`adk/retry_chatmodel.go`：

```go
type TypedModelRetryConfig[M MessageType] struct {
    // MaxRetries 指定最大重试次数。
    // 值为 0 表示不重试。
    // 值为 3 表示最多重试 3 次（含首次调用共 4 次）。
    MaxRetries int

    // ShouldRetry 决定如何处理一次模型调用的结果。
    // 它接收当前尝试的上下文信息，包括输出消息和/或错误，
    // 并返回是否重试、要修改什么等决策。
    // 返回 nil 等价于 &RetryDecision{Retry: false}（原样接受）。
    ShouldRetry func(ctx context.Context, retryCtx *TypedRetryContext[M]) *TypedRetryDecision[M]

    // 已弃用：请改用 ShouldRetry，它提供更丰富的重试控制，
    // 包括消息检查、输入修改和选项调整。
    // 设置了 ShouldRetry 时，IsRetryAble 会被忽略。
    IsRetryAble func(ctx context.Context, err error) bool

    // BackoffFunc 计算下一次重试前的延迟。
    // attempt 参数从 1 开始（第一次重试）。
    // 当 RetryDecision.Backoff 为零时作为默认值使用。
    // 为 nil 时使用带抖动的默认指数退避：
    // 基础延迟 100ms，指数增长至最大 10s，
    // 并加随机抖动（延迟的 0-50%）以防止惊群。
    BackoffFunc func(ctx context.Context, attempt int) time.Duration
}
```

### MaxRetries 的语义

**`MaxRetries = 3` 意味着总共 4 次调用**（1 次初始 + 3 次重试）。源码注释明确说了。

**`MaxRetries = 0` 表示不重试**。这也是默认值（零值）。

### ShouldRetry vs IsRetryAble

`IsRetryAble` 已弃用，只接收 `error`。`ShouldRetry` 接收完整的 `RetryContext`，包含：

- 输出消息（可能部分内容）；
- 错误；
- 尝试次数。

**能力差异**：

```go
// 旧：只能根据 error 判断
IsRetryAble: func(ctx context.Context, err error) bool {
    return errors.Is(err, context.DeadlineExceeded)
},

// 新：可以看输出内容
ShouldRetry: func(ctx context.Context, rc *adk.RetryContext) *adk.RetryDecision {
    if rc.Err != nil {
        return &adk.RetryDecision{Retry: true}
    }
    // 没有错误，但输出不合格 —— 也可以重试
    if rc.Output != nil && rc.Output.Content == "" {
        return &adk.RetryDecision{
            Retry:   true,
            ModifyInput: func(msgs []*schema.Message) []*schema.Message {
                // 加强提示后重试
                return append(msgs, schema.UserMessage("请给出实质性回答"))
            },
        }
    }
    return nil
},
```

**`ShouldRetry` 里可以修改输入**，这是 `IsRetryAble` 做不到的。

### 流式重试的陷阱

源码注释：

```go
// 注意：流式模式下，整个流被消费完之后才会调用 ShouldRetry。
// 事件流无论如何都会实时发给客户端；只有重试
// 决策会推迟到完整响应可用之后。
```

**这意味着流式重试是"事后重试"**：

1. 流式输出已经发给前端了（用户看到了）；
2. 流结束，判断要重试；
3. 重新调用模型，输出**又发一遍**。

用户会看到内容重复。

**所以流式场景下不要用重试**，除非：

- 你的事件契约里有"重试开始"的信号，前端能清屏；
- 或者重试只针对"流根本没开始"的情况（连接失败）。

### 默认退避策略

源码注释：

> base delay 100ms, exponentially increasing up to 10s max, with random jitter (0-50% of delay)
>
> **译**：基础延迟 100ms，指数增长至最大 10s，并加随机抖动（延迟的 0-50%）。

即：

| 尝试 | 基础延迟 | 加抖动后范围 |
|---|---|---|
| 1 | 100ms | 100–150ms |
| 2 | 200ms | 200–300ms |
| 3 | 400ms | 400–600ms |
| 4 | 800ms | 800–1200ms |
| ... | ... | ... |
| 上限 | 10s | 10–15s |

**抖动（jitter）的作用**是防止"惊群"：多个客户端同时失败、同时重试，会在同一时刻再次打爆服务端。

### WillRetryError

`adk/retry_chatmodel.go:81`：

```go
type WillRetryError struct {
    ErrStr       string
    RetryAttempt int
}
```

这个错误表示"即将重试"。它会被发送到事件流里，让你知道发生了重试。

**用途**：在前端显示"网络不稳定，正在重试（第 2 次）"。

## 3.11 ModelFailoverConfig：故障转移

`adk/failover_chatmodel.go`：

```go
type ModelFailoverConfig[M MessageType] struct {
    // MaxRetries 指定最大故障转移次数。
    // 值为 0 表示不做故障转移（不会调用 GetFailoverModel）。
    // 值为 1 表示 GetFailoverModel 可能被调用一次。
    MaxRetries uint

    // ShouldFailover 决定发生错误时是否转移到下一个模型。
    // 注意：同时配置了 ModelRetryConfig 时，outputErr 会是 *RetryExhaustedError
    // （若重试已耗尽），而不是原始的模型错误。
    ShouldFailover func(ctx context.Context, outputMessage M, outputErr error) bool

    // GetFailoverModel 在模型调用失败且 ShouldFailover 返回 true 时被调用。
    GetFailoverModel func(ctx context.Context, failoverCtx *FailoverContext[M]) (
        failoverModel model.BaseModel[M], failoverModelInputMessages []M, failoverErr error)
}
```

### 与 Retry 的区别

| | Retry | Failover |
|---|---|---|
| 重试对象 | **同一个**模型 | **换一个**模型 |
| 适用 | 瞬时故障（网络抖动、限流） | 模型不可用（服务宕机、区域故障） |
| 配置 | `MaxRetries int` | `MaxRetries uint` |

**可以叠加使用**：先重试同一个模型 N 次，全失败后再 failover 到备用模型。

### 叠加时的错误类型

源码注释：

> When ModelRetryConfig is also configured, outputErr will be a `*RetryExhaustedError` (if retries were exhausted) rather than the original model error. Use errors.As to extract the RetryExhaustedError and access RetryExhaustedError.LastErr for the original error.
>
> **译**：同时配置了 ModelRetryConfig 时，outputErr 会是 `*RetryExhaustedError`（若重试已耗尽），而非原始模型错误。用 errors.As 取出 RetryExhaustedError，再访问 RetryExhaustedError.LastErr 拿到原始错误。

```go
ShouldFailover: func(ctx context.Context, msg *schema.Message, err error) bool {
    var reErr *adk.RetryExhaustedError
    if errors.As(err, &reErr) {
        // 重试耗尽了，看看原始错误是什么
        return errors.Is(reErr.LastErr, context.DeadlineExceeded)
    }
    return err != nil
},
```

### lastSuccessModel 的优化

源码注释提到：

> Note: if lastSuccessModel is set (from a previous successful call), it will be tried first before calling GetFailoverModel.
>
> **译**：注意：若 lastSuccessModel 已设置（来自上一次成功的调用），会先试它，然后再调用 GetFailoverModel。

**含义**：如果之前 failover 到模型 B 成功过，下次失败时会**先试 B**，而不是从主模型开始。

这是个聪明的优化：主模型挂了之后，后续请求直接走 B，省掉一次失败尝试。

### 什么时候该用

**用 failover，如果**：

- 有多个可用的模型供应商（OpenAI + Anthropic + 国内模型）；
- 业务不能接受"模型服务挂了就整体不可用"。

**不要用，如果**：

- 只有一个模型（那该用 retry）；
- 不同模型的行为差异很大（failover 后输出风格突变，用户体验差）。

```go
func (h *permHandler) WrapInvokableToolCall(ctx context.Context,
    endpoint adk.InvokableToolCallEndpoint, tCtx *adk.ToolContext) (
    adk.InvokableToolCallEndpoint, error) {

    return func(ctx context.Context, args string, opts ...tool.Option) (string, error) {
        // 1. 权限检查
        if !h.allowed(ctx, tCtx.Name) {
            return "", fmt.Errorf("工具 %s 无权限", tCtx.Name)
        }

        // 2. 参数校验
        if err := h.validate(tCtx.Name, args); err != nil {
            return "", err
        }

        // 3. 执行并计时
        start := time.Now()
        result, err := endpoint(ctx, args, opts...)
        h.metrics.Observe(tCtx.Name, time.Since(start), err)

        return result, err
    }, nil
}
```

**这是实现"工具权限控制"的标准位置**。比在工具内部检查更好，因为：

- 一处代码管所有工具；
- 不侵入工具实现；
- 可以统一日志、计时、限流。

### 组 4：模型包装（1 个）

**`WrapModel`**：

```go
// WrapModel 用自定义行为包裹实际的模型调用。
// 注意：参数类型是 model.BaseModel[M]（不是 ToolCallingChatModel），因为包装器
// 只需要拦截 Generate/Stream 调用。工具绑定（WithTools）由框架
// 单独处理，不经过用户的包装器。
//
// 推荐用途（围绕模型调用本身的行为）：
// - 模型调用重试逻辑
// - 模型故障转移（切换到备用模型）
// - 发送事件（例如流式进度）
// - 处理或转换响应流
// - 修改调用配置（temperature、top_p 等）
//
// 不推荐的用法（请改用 BeforeModelRewriteState）：
// - 修改输入消息：此处的改动不会持久化到 state，只影响
// 单次模型调用，且会破坏跨迭代的 prompt 缓存。
// - 修改工具列表：请改用 BeforeModelRewriteState 中的
// state.ToolInfos / state.DeferredToolInfos，它们才是工具配置的真相源。
WrapModel(ctx context.Context, m model.BaseModel[M], mc *TypedModelContext[M]) (model.BaseModel[M], error)
```

**源码注释直接给了"推荐"和"劝阻"两个清单**，这是最有价值的文档。原文翻译：

**推荐用途**（都是"围绕调用本身"的行为）：

- 模型调用重试逻辑
- 模型故障转移
- 发送事件（比如流式进度）
- 处理或转换响应流
- 修改调用配置（temperature、top_p 等）

**劝阻用途**（应该用 `BeforeModelRewriteState`）：

- **修改输入消息**：改动不会持久化到 state，只影响单次调用，且**破坏跨迭代的 prompt 缓存**
- **修改工具列表**：用 `state.ToolInfos` / `state.DeferredToolInfos`

**为什么改消息会破坏缓存？** 因为 `WrapModel` 是在**模型调用那一刻**改的，而 `BeforeModelRewriteState` 是在**state 层面**改的。前者每次调用都重新改一遍（可能产生细微差异），后者改一次就持久化了。

### 执行顺序与 fail-fast

源码注释（`handler.go:139`）：

```go
// AfterAgent handler 的调用顺序与 BeforeAgent 相同
// （先注册先调用）。与其他所有中间件钩子一致，
// 任一 handler 返回错误时，后续 handler 不再调用（fail-fast），
// 该错误会被发送到事件流。
```

**三条规则**：

1. **顺序 = 注册顺序**（`Handlers` 切片顺序）；
2. **fail-fast**：任何一个返回 error，后面的不执行；
3. **error 进事件流**（不是直接返回，因为 `Run` 不返回 error）。

`adk/chatmodel.go:239`：

五个字段，对比 `Handlers` 的九个方法。

### 完整对照表

| `AgentMiddleware` 字段 | `Handlers` 对应 | 能力差异 |
|---|---|---|
| `AdditionalInstruction` | `BeforeAgent` 改 `Instruction` | 后者可条件化、可完全替换 |
| `AdditionalTools` | `BeforeAgent` 改 `Tools` | 后者可动态增减、可改 `ReturnDirectly` |
| `BeforeChatModel` | `BeforeModelRewriteState` | 后者返回新 state，可改工具列表 |
| `AfterChatModel` | `AfterModelRewriteState` | 同上 |
| `WrapToolCall`（`compose.ToolMiddleware`） | 4 个 `Wrap*ToolCall` | 后者按接口类型精确匹配 |
| （无） | `BeforeAgent` 返回 ctx | 可向下传递派生 ctx |
| （无） | `AfterAgent` | 成功终止的钩子 |
| （无） | `WrapModel` | 包裹模型调用本身 |

### 三个关键升级

**升级 1：可以返回修改后的 state**

老接口 `BeforeChatModel func(context.Context, *ChatModelAgentState) error` 是**原地修改**：

```go
BeforeChatModel: func(ctx context.Context, st *adk.ChatModelAgentState) error {
    st.Messages = append(st.Messages, extra)   // 只能原地改
    return nil
},
```

新接口返回新 state：

```go
BeforeModelRewriteState: func(ctx context.Context, st *adk.ChatModelAgentState, mc *adk.ModelContext) (
    context.Context, *adk.ChatModelAgentState, error) {
    return ctx, &adk.ChatModelAgentState{   // 可以整体替换
        Messages:  newMessages,
        ToolInfos: newTools,
    }, nil
},
```

**实际影响**：可以返回一个全新的 state，而不只是修改传入的那个。这对"完全重建上下文"的场景有用。

**升级 2：可以返回 ctx**

新接口每个方法都返回 `context.Context`。这让你能把派生 ctx 传递下去：

```go
BeforeModelRewriteState: func(ctx context.Context, st *adk.ChatModelAgentState, mc *adk.ModelContext) (
    context.Context, *adk.ChatModelAgentState, error) {
    ctx = context.WithValue(ctx, myKey{}, "value")   // 派生
    return ctx, st, nil
},
```

老接口没有这个能力。

**升级 3：工具包装按接口精确匹配**

老接口只有一个 `WrapToolCall compose.ToolMiddleware`，内部再分 `Invokable` / `Streamable`。

新接口拆成四个独立方法，框架按工具实际实现的接口调用。好处是**类型安全**——你写 `WrapInvokableToolCall` 就只处理 `InvokableTool`，不用在函数内部判断。

### 迁移建议

**新代码一律用 `Handlers`**。`Middlewares` 会在未来版本移除。

如果现有代码用了 `Middlewares`，迁移步骤：

1. 建一个 `struct` 嵌入 `*adk.BaseChatModelAgentMiddleware`；
2. `AdditionalInstruction` → 实现 `BeforeAgent`，追加到 `rc.Instruction`；
3. `AdditionalTools` → 实现 `BeforeAgent`，append 到 `rc.Tools`；
4. `BeforeChatModel` → 实现 `BeforeModelRewriteState`；
5. `AfterChatModel` → 实现 `AfterModelRewriteState`；
6. `WrapToolCall` → 按实际工具类型实现 `WrapInvokableToolCall` 或 `WrapStreamableToolCall`。

## 3.15 AgentTool：子 Agent 作为工具

`adk/agent_tool.go:93`：


把一个 Agent 包装成 `tool.BaseTool`，这样它可以被另一个 Agent 当工具调用。

**注意第一个参数是 `_`**——和 `NewRunner` 一样，ctx 被丢弃。

### 选项

`adk/agent_tool.go:42`：

```go
type AgentToolOptions struct {
    fullChatHistoryAsInput bool
    agentInputSchema       *schema.ParamsOneOf
}

// WithFullChatHistoryAsInput 启用完整对话历史作为输入。
func WithFullChatHistoryAsInput() AgentToolOption

// WithAgentInputSchema 为 agent tool 设置自定义输入 schema。
func WithAgentInputSchema(schema *schema.ParamsOneOf) AgentToolOption
```

**`WithFullChatHistoryAsInput`**：

默认行为：父 Agent 只把**当前这条用户消息**传给子 Agent。子 Agent 看不到完整对话历史。

开启后：父 Agent 把**完整历史**传过去。

**什么时候开？**

- 子 Agent 需要理解上下文才能工作（比如"接着刚才的话题继续"）；
- 子 Agent 的输出需要和之前的内容一致。

**什么时候不开？**

- 子 Agent 是独立任务（"帮我算一下 123 * 456"）；
- 历史很长，传过去浪费 token。

**`WithAgentInputSchema`**：

默认情况下，子 Agent 工具的参数只有一个 `input`（字符串），模型传的是自然语言任务描述。

自定义 schema 可以让参数结构化：

```go
adk.NewAgentTool(ctx, subAgent,
    adk.WithAgentInputSchema(schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
        "city":     {Type: schema.String, Desc: "城市名", Required: true},
        "date":     {Type: schema.String, Desc: "日期 YYYY-MM-DD", Required: true},
        "detailed": {Type: schema.Boolean, Desc: "是否返回详细数据"},
    })),
)
```

**好处**：模型传参更准确，子 Agent 拿到的是结构化输入而不是一段话。

**代价**：你要自己处理 schema 到子 Agent 输入的转换（在子 Agent 的 `GenModelInput` 里）。

### 前置条件

前面说过：`Name` 和 `Description` 必须非空，否则工具名/描述是空的，模型无法调用。

**源码不强制校验**，但实际使用会失败。这是"约定优于配置"的代价。

# 第 4 章　Runner：为什么不能直接调 Agent

## 4.1 Agent.Run 的签名说明了什么

`adk/interface.go:453`：

```go
type TypedAgent[M MessageType] interface {
    Name(ctx context.Context) string
    Description(ctx context.Context) string

    // Run 运行 Agent。
    // AsyncIterator 中返回的 AgentEvent 必须是可安全修改的。
    // 若 AsyncIterator 中返回的 AgentEvent 含有 MessageStream，
    // 该 MessageStream 必须是独占的，且可被直接接收。
    // 注意：建议对 AsyncIterator 发出的 AgentEvent 中的 MessageStream
    // 调用 SetAutomaticClose()，这样即使事件未被处理，MessageStream
    // 也能被关闭。
    Run(ctx context.Context, input *TypedAgentInput[M], options ...AgentRunOption) *AsyncIterator[*TypedAgentEvent[M]]
}
```

**三个关键点**：

1. **不返回 `error`**。所有错误都在事件流里。
2. **返回异步迭代器**。调用后立即返回，实际执行在后台 goroutine。
3. **`MessageStream` 的所有权转移给你**。你必须负责 `Close()`。

**为什么这样设计？**

因为流式。如果 `Run` 返回 `([]AgentEvent, error)`，就必须等整个 Agent 跑完才能返回——那流式就没意义了。

返回迭代器是唯一能让"边执行边消费"成立的签名。

## 4.2 Runner 的五项职责

既然 `Agent.Run` 已经能跑，`Runner` 存在的意义是什么？

`adk/runner.go:55`：

```go

    a               TypedAgent[M]
    enableStreaming bool
    store           CheckPointStore

```

三个字段，但承担五项职责。

### 职责 1：建立 runContext

`typedRunnerRunImpl`（`adk/runner.go:39`）：


`ctxWithNewTypedRunCtx`（`adk/runctx.go:537`）创建 `runSession` 和 `runContext`，并把 `input` 设为 `RootInput`。

**这是 `SessionValues` 能工作的前提**。没有 runContext，`GetSessionValues` 返回空 map。

### 职责 2：注入 SessionValues

```go

```

`WithSessionValues(map[string]any{...})` 传的值，在这里写进 session。

**注意执行顺序**：先建 runContext，再写 session values。反过来会失败（session 还不存在）。

### 职责 3：包装 CheckPointStore

```go

    fa.checkPointStore = store
}
```

把 Runner 的 store 注入到 Agent 内部。

**为什么要包装？** 因为 Agent 内部的 compose 图需要 store 来做中断/恢复。Agent 自己不知道 store，由 Runner 提供。

### 职责 4：包装取消

```go
if store == nil && o.cancelCtx == nil {
    return any(iter).(*AsyncIterator[*TypedAgentEvent[M]])   // 快路径，不额外起 goroutine
}

niter, gen := NewAsyncIteratorPair[*TypedAgentEvent[M]]()
go typedRunnerHandleIterImpl(enableStreaming, store, ctx,
    any(iter).(*AsyncIterator[*TypedAgentEvent[M]]), gen, o.checkPointID, o.cancelCtx)
return niter
```

**这里有个重要的性能优化**：

- 如果**没有** store 也**没有** cancel，直接返回 Agent 的迭代器（零开销）；
- 否则，起一个 goroutine 做中转，处理检查点保存和取消。

**含义**：不用检查点、不用取消的场景，Runner 几乎是零成本的。

### 职责 5：错误包装

`Query` 方法（`adk/runner.go:108`）：

```go
func (r *TypedRunner[M]) Query(ctx context.Context,
    query string, opts ...AgentRunOption) *AsyncIterator[*TypedAgentEvent[M]] {
    msgs, err := newUserMessage[M](query)
    if err != nil {
        return errorIterator[M](err)
    }
    // ...
}
```

`errorIterator`（`adk/runner.go:31`）：

```go
func errorIterator[M MessageType](err error) *AsyncIterator[*TypedAgentEvent[M]] {
    iter, gen := NewAsyncIteratorPair[*TypedAgentEvent[M]]()
    gen.Send(&TypedAgentEvent[M]{Err: err})
    gen.Close()
    return iter
}
```

**把构造错误塞进一个只有一个错误事件的事件流**。

这样调用方只需要处理一种情况："消费事件流，遇到 error 就失败"。不用区分"构造失败"和"执行失败"。

**代价**：调用方必须完整消费流才能发现错误。如果你 `Query` 之后直接返回，不读事件，错误就被吞了。

`adk/runner.go:89`：

`adk/runner.go:147`：

```go
    params *ResumeParams, opts ...AgentRunOption) (*AsyncIterator[*TypedAgentEvent[M]], error)
```

`ResumeParams`（`adk/runner.go:81`）：

```go
type ResumeParams struct {
    // Targets 的 key 是待恢复组件的地址，
    // value 是对应的恢复数据
    Targets map[string]any
    // 未来可在此添加可扩展字段而不破坏兼容性
}
```

### 两种恢复的区别

源码注释说得很清楚（`adk/runner.go:127` 起）：

> **Implicit Resume All**（`Resume`）：所有中断点都恢复。
>
> **ResumeWithParams**：只恢复 `Targets` 里指定的中断点。

具体规则：

> - Components whose addresses are in the params.Targets map will receive `isResumeFlow = true`.
> - Interrupted components whose addresses are NOT in the params.Targets map must decide how to proceed:
>   - "Leaf" components (the actual root causes of the original interrupt) MUST re-interrupt themselves to preserve their state.
>   - "Composite" agents (like SequentialAgent or ChatModelAgent) should generally proceed with their execution. They act as conduits, allowing the resume signal to flow to their children.
>
> **译**：
> - 地址在 `params.Targets` 里的组件会收到 `isResumeFlow = true`。
> - 地址不在 `params.Targets` 里的被中断组件必须自行决定如何处理：
>   - "叶子"组件（原始中断的真正根因）**必须重新中断自己**，以保住自身状态。
>   - "复合" Agent（如 SequentialAgent 或 ChatModelAgent）一般应继续执行。它们扮演传导者的角色，让恢复信号流向其子组件。

**翻译**：

- 在 `Targets` 里的组件：收到 `isResumeFlow = true`，正常恢复；
- 不在 `Targets` 里的**叶子组件**（真正中断的那个）：**必须重新中断自己**，否则状态丢失；
- 不在 `Targets` 里的**复合组件**（父 Agent）：继续执行，把恢复信号往下传。

**为什么叶子组件必须重新中断？**

假设 Agent 在工具 A 处中断，你在 `Targets` 里只指定了工具 B。那工具 A 被"恢复"但没有数据，它不能假装自己完成了——只能重新中断，等下一次恢复。

这个设计让"部分恢复"成为可能：你可以分多次、逐步恢复多个中断点。

## 4.5 CheckPointStore：两个方法的接口

`adk/runner.go:64`：

```go
type CheckPointStore = core.CheckPointStore
```

定义在 `compose` 包（`core` 是别名）：

```go
type CheckPointStore interface {
    Set(ctx context.Context, key string, value []byte) error
    Get(ctx context.Context, key string) ([]byte, bool, error)
}
```

**只有两个方法**。极简。

### 为什么是 `[]byte`

因为检查点是 gob 编码的。Store 只管存取字节，不管序列化。

**好处**：你可以用任何存储——Redis、MySQL、S3、本地文件。只要能存字节。

**坏处**：你无法查询检查点内容（比如"找所有包含某工具的检查点"）。

### CheckPointDeleter：可选接口

`adk/runner.go:66`：

```go
type CheckPointDeleter = core.CheckPointDeleter
```

```go
type CheckPointDeleter interface {
    Delete(ctx context.Context, key string) error
}
```

**可选**。如果实现了，框架会在"执行正常完成"后删除检查点（避免积累垃圾）。

不实现的话，检查点会一直留着，需要你自己清理。

### 一个内存实现

```go
type memStore struct {
    mu sync.RWMutex
    m  map[string][]byte
}

func newMemStore() *memStore {
    return &memStore{m: make(map[string][]byte)}
}

func (s *memStore) Set(ctx context.Context, key string, value []byte) error {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.m[key] = value
    return nil
}

func (s *memStore) Get(ctx context.Context, key string) ([]byte, bool, error) {
    s.mu.RLock()
    defer s.mu.RUnlock()
    v, ok := s.m[key]
    return v, ok, nil
}

// 实现 CheckPointDeleter
func (s *memStore) Delete(ctx context.Context, key string) error {
    s.mu.Lock()
    defer s.mu.Unlock()
    delete(s.m, key)
    return nil
}
```

**生产环境不要用内存实现**——进程重启就丢了。用 Redis 或数据库。

`adk/runctx.go`：

### 无 session 时的行为

`GetSessionValues`（`runctx.go:204`）：

```go
func GetSessionValues(ctx context.Context) map[string]any {
    session := getSession(ctx)
    if session == nil {
        return map[string]any{}
    }
    return session.getValues()
}
```

**返回空 map，不 panic**。

`AddSessionValue`（`runctx.go:214`）：

```go
func AddSessionValue(ctx context.Context, key string, value any) {
    session := getSession(ctx)
    if session == nil {
        return    // 静默忽略
    }
    session.addValue(key, value)
}
```

**静默忽略，不报错**。

**这是个容易踩的坑**：如果你在 Agent 外面调 `AddSessionValue`（比如直接在 handler 里），它什么也不做，也不告诉你。

**必须在 Runner 建立的 ctx 内调用**。也就是说：

```go
// 错误：这个 ctx 没有 session
adk.AddSessionValue(c.Request.Context(), "key", "value")

// 正确：在中间件里，ctx 来自 Run
func (h *H) BeforeAgent(ctx context.Context, rc *adk.ChatModelAgentContext) (...) {
    adk.AddSessionValue(ctx, "key", "value")   // ctx 有 session
}
```

### 并发安全

`runSession` 内部有 `valuesMtx *sync.Mutex`（`runctx.go:195` 的 `newRunSession`），所以 `AddSessionValue` 是并发安全的。

但 `GetSessionValues` 返回的是**副本还是引用**？看 `getValues()` 的实现——它加锁并返回。具体是否深拷贝取决于实现，但**你不应该依赖返回的 map 是活的**：要修改就调 `AddSessionValue`。

### OutputKey 的联动

`Config.OutputKey`（见 [3.1](#慎用3-个源码标了-not-recommended)）设置后，Agent 结束时执行：

```go
AddSessionValue(ctx, outputKey, msg.Content)
```

所以父 Agent 可以通过 `GetSessionValue(ctx, "child_output")` 拿到子 Agent 的结果。

## 4.8 取消：三种粒度

`adk/cancel.go:44`：

```go
type CancelMode int

const (
    // CancelImmediate 在收到信号后立即取消 Agent，
    CancelImmediate CancelMode = 0
    // CancelAfterChatModel 在根 Agent 下一次 chat model 调用后取消
    CancelAfterChatModel CancelMode = 1 << iota
    // CancelAfterToolCalls 在根 Agent 下一批工具调用后取消
    CancelAfterToolCalls
)
```

**注意 `CancelImmediate = 0` 是零值**，后面的用 `1 << iota` 做位掩码。

实际值：

| 常量 | 值 | 二进制 |
|---|---|---|
| `CancelImmediate` | 0 | `00` |
| `CancelAfterChatModel` | 2 | `10` |
| `CancelAfterToolCalls` | 4 | `100` |

（`iota` 在 `CancelAfterChatModel` 那行是 1，所以 `1 << 1 = 2`；下一行 `iota` 是 2，`1 << 2 = 4`。`CancelImmediate` 在 `iota=0` 那行但值是字面量 0。）

### 位掩码可以组合

源码注释：

```go
// 例如 CancelAfterChatModel | CancelAfterToolCalls 表示取消 Agent
```

组合后值 = 2 | 4 = 6。图里的两个检查点都会检查：

`adk/react.go:390` 的 `CancelCheck` 节点：

```go
if cancelCtx != nil && cancelCtx.shouldCancel() {
    if cancelCtx.getMode()&CancelAfterChatModel != 0 {
        return nil, compose.Interrupt(ctx, "CancelAfterChatModel")
    }
}
```

`react.go:475` 的 `AfterToolCallsCancelCheck`：

```go
if cancelCtx != nil && cancelCtx.shouldCancel() {
    if cancelCtx.getMode()&CancelAfterToolCalls != 0 {
        return nil, compose.Interrupt(ctx, "CancelAfterToolCalls")
    }
}
```

**用 `&` 做位检查**。所以组合模式会让两个点都生效。

### WithCancel

`adk/cancel.go:239`：

```go
func WithCancel() (AgentRunOption, AgentCancelFunc)
```

**返回两个值**：

1. `AgentRunOption`：传给 `Run`；
2. `AgentCancelFunc`：调用来触发取消。

用法：

```go
cancelOpt, cancelFunc := adk.WithCancel()

iter := runner.Run(ctx, msgs, cancelOpt)

// 另一个 goroutine 或用户操作
go func() {
    time.Sleep(2 * time.Second)
    handle, ok := cancelFunc(adk.WithCancelMode(adk.CancelAfterToolCalls))
    if ok {
        err := handle.Wait()   // 等取消完成
        fmt.Println("取消结果:", err)
    }
}()
```

### CancelHandle.Wait 的三种结果

`adk/cancel.go:84`：

```go
func (h *CancelHandle) Wait() error
```

源码注释：

> - nil: the cancellation completed successfully
> - CancelError: ... was absorbed into CancelError while cancellation was active
> - ErrCancelTimeout: the requested safe-point cancellation timed out and was
> - ErrExecutionEnded: ...
>
> **译**：
> - `nil`：取消已成功完成
> - `CancelError`：取消进行期间产生的错误被吸收进了 CancelError
> - `ErrCancelTimeout`：请求的安全点取消已超时
> - `ErrExecutionEnded`：执行已结束

三种结果：

| 返回值 | 含义 |
|---|---|
| `nil` | 取消成功完成 |
| `*CancelError` | 取消过程中产生的错误被吸收进 CancelError |
| `ErrCancelTimeout` | 安全点取消超时（Agent 没有到达检查点） |
| `ErrExecutionEnded` | 执行已结束，无需取消 |

**`ErrCancelTimeout` 是最需要处理的**：你请求"在工具调用后取消"，但 Agent 可能已经跑完了，或者卡在某个长工具里。超时后要决定是强制取消还是放弃。

### ctx 取消 vs WithCancel

**两种取消机制并存**，区别：

| | ctx 取消 | `WithCancel` |
|---|---|---|
| 触发 | `ctx.Done()` | `cancelFunc()` |
| 粒度 | 立即 | 可指定安全点 |
| 检查点 | ❌ 不保存 | ✅ 保存（如果配了 store） |
| 恢复 | ❌ 不能恢复 | ✅ 可以 `Resume` |

**ctx 取消是"硬中断"**：立即停止，不保存状态，不能恢复。

**`WithCancel` 是"软中断"**：在安全点停止，保存检查点，可以恢复。

**什么时候用哪个？**

- 用户点"停止"按钮 → `WithCancel`（可能想恢复）；
- HTTP 请求断开 → ctx 取消（不需要恢复，用户已经走了）；
- 服务关闭 → ctx 取消（不需要恢复）。

### 检查点保存的时机

`typedRunnerHandleIterImpl`（`adk/runner.go`）里：

```go
if errors.As(err, &cancelErr) && store != nil {
    // 保存检查点
}
```

**只在 `CancelError` 时保存**。普通的错误（模型报错、工具报错）不保存检查点——因为那些错误重试也不会有不同结果。

## 4.9 TurnLoop：多轮排队（进阶）

`adk/turn_loop.go:896` 定义了 `TurnLoop`。这是 v0.9 新增的高级能力。

### 它解决什么问题

假设你在做一个"用户可能连续发消息"的聊天应用。用户发第一条，Agent 开始跑；用户又发第二条，怎么办？

**朴素做法**：为每条消息起一个独立的 `Run`。问题：

- 两个 Agent 实例并发跑，上下文互相看不到；
- 第二个请求可能覆盖第一个的状态；
- 无法"打断当前回答，先处理新消息"。

**`TurnLoop` 的做法**：一个持续运行的循环，消息进队列（`Push`），循环按策略决定"这一轮处理哪些消息"。

### 核心配置

`adk/turn_loop.go:562`：

```go
type TurnLoopConfig[T any, M MessageType] struct {
    // GenInput 接收 TurnLoop 实例和所有已缓冲的条目，并决定处理哪些。
    // 它返回哪些条目现在消费、哪些留到后续轮次。
    GenInput func(ctx context.Context, loop *TurnLoop[T, M], items []T) (*GenInputResult[T, M], error)

    // GenResume 在 Run() 期间最多被调用一次。
    GenResume func(ctx context.Context, loop *TurnLoop[T, M], interruptedItems, unhandledItems, newItems []T) (*GenResumeResult[T, M], error)

    // PrepareAgent 返回一个配置好用于处理已消费条目的 Agent。
    PrepareAgent func(ctx context.Context, loop *TurnLoop[T, M], consumed []T) (TypedAgent[M], error)

    // OnAgentEvents 用于处理 Agent 发出的事件。
    OnAgentEvents func(ctx context.Context, tc *TurnContext[T, M], events *AsyncIterator[*TypedAgentEvent[M]]) error

    Store CheckPointStore
    CheckpointID string
}
```

四个回调 + 两个存储配置。

### 方法

`adk/turn_loop.go`：

```go
// 1350 行
func (l *TurnLoop[T, M]) Run(ctx context.Context)

// 1381 行
func (l *TurnLoop[T, M]) Push(item T, opts ...PushOption[T, M]) (bool, <-chan struct{})

// 1524 行

// 1565 行

```

**`Push` 返回 `(bool, <-chan struct{})`**：第一个表示是否成功入队，第二个 channel 在消息被处理完后关闭。

### 抢占（Preempt）

`adk/turn_loop.go:1225`：

```go
func WithPreempt[T any, M MessageType](safePoint SafePoint) PushOption[T, M]
```

**这是 `TurnLoop` 最有价值的能力**：新消息可以抢占正在执行的那一轮。

场景：Agent 正在生成一个长回答，用户突然发了新消息。用 `WithPreempt`，当前回答会在安全点停下，先处理新消息。

`SafePoint`（`turn_loop.go:1056`）定义了可以抢占的位置。

### 优雅停止

`adk/turn_loop.go:1097`：

```go
func WithGraceful() StopOption
```

`Stop(WithGraceful())` 会等当前这一轮跑完再停。

对比：

- `Stop()` 默认：立即停；
- `Stop(adk.WithGraceful())`：等当前轮结束；
- `Stop(adk.WithGracefulTimeout(30*time.Second))`：最多等 30 秒。

### 什么时候用

**用 `TurnLoop`，如果**：

- 需要处理"用户连续发消息"的排队；
- 需要"新消息打断旧回答"；
- 需要持久化的多轮会话（配 `CheckpointID`）。

**不用，如果**：

- 单次请求-响应（绝大多数 HTTP 服务）；
- 你自己在上层已经做了队列。

**本章不展开 `TurnLoop` 的实现细节**——它是一个独立的高级主题，涉及抢占、状态机、检查点桥接等。这里只需要知道它存在、解决什么问题。

## 5.1 结构：五个字段

`adk/interface.go:419`：

```go

    AgentName string

    // RunPath 表示从根 Agent 到当前事件源的执行路径。
    // 该字段完全由框架管理，最终用户无法设置。

    // 不推荐：RunPath 主要与 agent transfer 和 workflow agent 相关，
    // 而这些在实证上并未证明更有效。对使用 AgentTool 或 DeepAgent 的
```

五个字段，但**任何时刻只有一个"有效载荷"**：

| 组合 | 含义 |
|---|---|
| `Output != nil` | 消息事件 |
| `Action != nil` | 控制事件 |
| `Err != nil` | 错误事件 |
| 全 nil | 空事件（心跳/占位） |

**这不是互斥的**。理论上可以同时有 `Output` 和 `Action`——比如"最后一个回答 + Exit"。所以判定顺序很重要（见 [5.6](#56-四类事件的判定顺序)）。

### AgentName

当前产生事件的 Agent 名。

单 Agent 场景：恒等于你的 Agent 的 `Name`。**没什么用**。

多 Agent 场景：用来区分事件来源。

### RunPath

```go
type RunStep struct {
    agentName string   // 私有！
}
```

`adk/interface.go:377`。**字段全私有**，你只能调它的 `String()` 方法。

**为什么私有？** 因为源码说它是"managed entirely by the framework and cannot be set by end-users"——框架内部用于追踪执行路径，不打算让用户读写。

**什么时候有用？**

单 Agent：`RunPath` 长度为 1，没意义。

多 Agent：能看出"这个事件来自根 Agent 的第 2 个子 Agent"。

**但源码标了 NOT RECOMMENDED**：

>
> **译**：RunPath 主要与 agent transfer 和 workflow agent 相关，而这些实证上并未证明更有效。对使用 AgentTool 或 DeepAgent 的 ChatModelAgent 而言，RunPath 基本没有内容。

**实践建议**：不要依赖 `RunPath` 做业务逻辑。

## 5.3 TypedMessageVariant：消息的交付形态

`adk/interface.go:73`：

```go
type TypedMessageVariant[M MessageType] struct {
    IsStreaming bool

    Message       M
    MessageStream *schema.StreamReader[M]

    // Role 表示本事件在 Agent 的 ReAct 循环中的来源。
    // 仅对 *schema.Message 事件有意义：
    // - schema.Assistant：事件携带模型输出（生成或流）。
    // - schema.Tool：事件携带工具执行结果。
    // 对 *schema.AgenticMessage 事件恒为零值；请改用 AgenticRole。
    Role schema.RoleType

    // AgenticRole 表示 agentic 消息的角色（assistant、user、system）。
    // 仅对 *schema.AgenticMessage 事件有意义。
    // 流式模式下，该值在消费流之前就可用。
    // 对 *schema.Message 事件恒为零值；请改用 Role。
    AgenticRole schema.AgenticRoleType

    // ToolName 是产生本事件的工具名。
    // 仅对 *schema.Message 事件有意义：Role == schema.Tool 时非空。
    // 流式模式下，这是在消费流之前唯一能确认来源工具的方式。
    // （流被消费之前）
    // 对 *schema.AgenticMessage 事件恒为空。
    ToolName string
}
```

**六个字段，两套并存的元数据**：

| Message 路径 | Agentic 路径 |
|---|---|
| `Role`（4 值） | `AgenticRole`（3 值） |
| `ToolName`（有） | `ToolName`（恒空） |

**为什么要并存？** 因为 `TypedMessageVariant[M]` 是泛型的，同一个结构体要服务两条路径。用"哪个有值"来区分。

**判定方法**：

```go
mv := ev.Output.MessageOutput

// 方式 1：看 Role 还是 AgenticRole
if mv.AgenticRole != "" {
    // Agentic 路径
} else if mv.Role != "" {
    // Message 路径
}

// 方式 2：看 Message 的实际类型（需要类型断言）
switch any(mv.Message).(type) {
case *schema.Message:
case *schema.AgenticMessage:
}
```

### IsStreaming 的严格含义

```go
IsStreaming: msgStream != nil
```

（`adk/interface.go:247` 的 `typedEventFromMessage`）

**`IsStreaming == true` 时 `Message` 必定是 nil**。这是构造时保证的：

```go
&TypedMessageVariant[M]{
    IsStreaming:   msgStream != nil,
    Message:       msg,          // 流式时传 nil
    MessageStream: msgStream,
}
```

**但反过来不成立**：`IsStreaming == false` 时 `MessageStream` 也可能是 nil，`Message` 也可能是 nil（空事件）。

**所以安全的读法是 `GetMessage()`**（`adk/interface.go:107`）：

```go
func (mv *TypedMessageVariant[M]) GetMessage() (M, error) {
    if mv.IsStreaming {
        return concatMessageStream(mv.MessageStream)
    }
    return mv.Message, nil
}
```

**这个方法做了两件事**：

1. 流式时自动 `ConcatMessages`；
2. 非流式时直接返回。

**但它会消费流**。如果你想同时推给前端和处理，必须 `Copy`（见 [1.9](#19-streamreader流式消费协议)）。

### Role 的取值语义

`Role` 只有两个可能值（在 AgentEvent 里）：

| Role | 来源 | 含义 |
|---|---|---|
| `schema.Assistant` | ChatModel 节点 | 模型输出 |
| `schema.Tool` | ToolNode 节点 | 工具结果 |

**不会有 `system` 或 `user`**。因为这两个角色是输入，不是输出。

**这是个重要认知**：`AgentEvent` 里的消息永远是"模型说的"或"工具返回的"，不会是"你传进去的"。

### ToolName 的来源

源码注释：

> In streaming mode, this is the only way to identify the source tool before the stream is consumed.
>
> **译**：流式模式下，这是在消费流之前唯一能确认来源工具的方式。

**流式下，你必须靠 `ToolName` 知道这是哪个工具的结果**，因为 `Message` 是 nil。

但**非流式下，`ToolName` 也可能为空**：

- 如果你构造 `ToolMessage` 时没传 `schema.WithToolName()`（见 [1.4](#14-构造函数不要手写结构体)），`Message.ToolName` 为空；
- 框架的 `ToolName` 是从 `ToolCallID` 反查填的，如果反查不到也为空。

**所以判定"工具名"要两处都看**：

```go
name := mv.ToolName
if name == "" && mv.Message != nil {
    name = mv.Message.ToolName
}
```

## 5.5 AsyncIterator：无界缓冲的机制

`adk/utils.go:31`：


### 底层是 UnboundedChan

`internal/channel.go:22`：

```go
type UnboundedChan[T any] struct {
    buffer   []T // 内部缓冲区，用于存放数据
    mutex    sync.Mutex // 互斥锁，保护缓冲区访问
    notEmpty *sync.Cond // 条件变量，用于等待数据
    closed   bool // 标识通道是否已关闭
}

func (ch *UnboundedChan[T]) Send(value T) {
    ch.mutex.Lock()
    defer ch.mutex.Unlock()

    if ch.closed {
        panic("send on closed channel")
    }

    ch.buffer = append(ch.buffer, value)
    ch.notEmpty.Signal()
}

func (ch *UnboundedChan[T]) Receive() (T, bool) {
    ch.mutex.Lock()
    defer ch.mutex.Unlock()

    for len(ch.buffer) == 0 && !ch.closed {
        ch.notEmpty.Wait()
    }

    if len(ch.buffer) == 0 {
        var zero T
        return zero, false
    }

    val := ch.buffer[0]
    // ... 出队
}
```

**核心机制**：`[]T` 切片 + `sync.Cond` 条件变量。

### 三个重要后果

**后果 1：生产者永不阻塞**

`Send` 只是 append 到切片，不会等待消费者。所以 Agent 可以尽可能快地产生事件。

**这是设计上的必然选择**：如果通道有界，Agent 在消费者慢的时候会被阻塞，整个执行卡住。

**后果 2：内存无上限**

消费者慢、生产快 → `buffer` 无限增长。

**真实风险场景**：

- 前端卡了（网络慢），Agent 在流式生成 10 万 token；
- 你在事件处理里做了慢操作（写数据库、调外部 API）。

**监控建议**：如果发现内存增长异常，检查是不是消费速度跟不上。

**后果 3：`Send` 到已关闭的 channel 会 panic**

```go
if ch.closed {
    panic("send on closed channel")
}
```

所以**生产者必须先确认不会在 `Close()` 之后 `Send`**。

框架的解法是 `TrySend`（`channel.go:51`）：

```go
func (ch *UnboundedChan[T]) TrySend(value T) bool {
    ch.mutex.Lock()
    defer ch.mutex.Unlock()

    if ch.closed {
        return false   // 不 panic，返回 false
    }
    // ...
    return true
}
```

`AsyncGenerator.trySend`（`adk/utils.go:43`）包装了它：

```go
func (ag *AsyncGenerator[T]) trySend(v T) bool {
    return ag.ch.TrySend(v)
}
```

**你自己写 Agent 时，如果有并发发送，用 `trySend` 更安全**——但它是私有的。公开的 `Send` 会 panic，所以必须确保生命周期正确：

```go
go func() {
    defer gen.Close()   // 确保先关闭
    // 所有 Send 都在 Close 之前
}()
```

### 错误处理：`errorIterator`


## 5.6 四类事件的判定顺序

因为字段可能同时非 nil，判定顺序决定了行为。

### 推荐顺序

```go
for {
    ev, ok := iter.Next()
    if !ok {
        break   // 流结束
    }

    // 1. 错误优先 —— 错误时其他字段可能不可靠
    if ev.Err != nil {
        handleError(ev.Err)
        continue
    }

    // 2. 控制信号 —— Action 可能需要终止循环
    if ev.Action != nil {
        if ev.Action.Exit {
            return   // 提前退出
        }
        if ev.Action.Interrupted != nil {
            handleInterrupt(ev.Action.Interrupted)
            continue
        }
    }

    // 3. 消息输出
    if ev.Output != nil && ev.Output.MessageOutput != nil {
        handleMessage(ev.Output.MessageOutput)
        continue
    }

    // 4. 空事件，忽略
}
```

### 为什么错误优先

`Err != nil` 时，`Output` 和 `Action` 的内容可能是**部分完成的**。比如流中途出错，`Output` 里可能有半个消息。

**先处理错误，再决定要不要处理残留数据**。

### 为什么 Action 在 Output 之前

因为 `Action.Exit` 表示"结束"。如果先处理 `Output` 再检查 `Action`，你可能会处理一个本该被丢弃的消息。

**实际上框架很少同时发 `Output` 和 `Action`**，但防御性写法更稳。

### 空事件要忽略

**空事件是正常的**。框架在某些路径会发送空事件作为占位。

不要假设"每个事件都有内容"：

```go
// 错误：可能 panic
msg := ev.Output.MessageOutput.Message

// 正确
if ev.Output == nil || ev.Output.MessageOutput == nil {
    continue
}
```

### Interrupted

```go
type InterruptInfo struct {
    Data any

    // InterruptContexts 提供中断链的结构化、面向用户的视图。
    // 每个 context 代表 Agent 层级中被中断的一层。
    InterruptContexts []*InterruptCtx

```

**来源**：业务代码调用 `compose.Interrupt(ctx, data)`，或取消触发的安全点中断。

**`Data`** 是你传给 `compose.Interrupt` 的任意数据。典型用途：请求人工审批时，传"要审批什么"。

**`InterruptContexts`** 是结构化的中断链，从根 Agent 到实际中断点。用来做"定向恢复"（见 [4.4](#resumewithparams)）。

每个 `InterruptCtx`（`internal/core/interrupt.go:128`，通过 `compose.InterruptCtx` 导出）有五个字段：

| 字段 | 说明 |
|---|---|
| `ID` | 完全限定的中断点地址，格式如 `agent:A;node:graph_a;tool:tool_call_123`。**这就是 `ResumeWithParams` 里 `Targets` 的 key** |
| `Address` | 结构化的地址段序列，`ID` 是它的字符串化形式 |
| `Info` | 触发中断的组件提供的用户可见信息（就是 `compose.Interrupt(ctx, data)` 里的 `data`） |
| `IsRootCause` | 是否是**根本原因**中断点（叶子组件） |
| `Parent` | 中断链上的父组件，顶层为 nil |

**`IsRootCause` 是定向恢复的关键**：只有 `IsRootCause == true` 的中断点，才需要在 `Targets` 里显式恢复。父组件是"传导者"，会自动跟随。

### BreakLoop

```go

```

`adk/workflow.go:300`：

```go
type BreakLoopAction struct {
```

**同样标了 NOT RECOMMENDED**：

**来源**：自定义 Agent 或某些中间件产生的自定义信号。

**典型例子**：`summarization` 中间件在触发上下文摘要时会产生一个 `CustomizedAction`，携带摘要元数据。

### 私有字段 internalInterrupted


## 5.8 一次带工具调用的完整事件序列

这是理解事件流最直观的方式。

假设用户问"北京天气如何"，Agent 有一个 `get_weather` 工具，`EnableStreaming: false`。

### 事件 1：Assistant（空内容 + 工具调用）

```go
AgentEvent{
    AgentName: "weather_agent",
    Output: &AgentOutput{
        MessageOutput: &MessageVariant{
            IsStreaming: false,
            Message: &schema.Message{
                Role:      schema.Assistant,
                Content:   "",                        // ← 空！
                ToolCalls: []schema.ToolCall{{
                    ID:   "call_abc",
                    Type: "function",
                    Function: schema.FunctionCall{
                        Name:      "get_weather",
                        Arguments: `{"city":"北京"}`,
                    },
                }},
            },
            Role: schema.Assistant,
        },
    },
}
```

**关键观察：`Content` 是空字符串**。

模型决定调工具时，通常不生成文本（或者只生成很少的引导语）。**这是最容易踩的坑**——如果你只取第一个 Assistant 事件的 `Content`，会拿到空字符串。

### 事件 2：Tool（工具结果）

```go
AgentEvent{
    Output: &AgentOutput{
        MessageOutput: &MessageVariant{
            IsStreaming: false,
            Message: &schema.Message{
                Role:       schema.Tool,
                Content:    `{"temp":18,"desc":"晴"}`,
                ToolCallID: "call_abc",
                ToolName:   "get_weather",
            },
            Role:     schema.Tool,
            ToolName: "get_weather",
        },
    },
}
```

**两个 `ToolName`**：

- `Message.ToolName`：你构造 `ToolMessage` 时设的；
- `MessageVariant.ToolName`：框架从 `ToolCallID` 反查填的。

**通常两者相同**，但来源不同。

### 事件 3：Assistant（真正的答案）

```go
AgentEvent{
    Output: &AgentOutput{
        MessageOutput: &MessageVariant{
            Message: &schema.Message{
                Role:    schema.Assistant,
                Content: "北京今天晴，气温 18°C。",
            },
            Role: schema.Assistant,
        },
    },
}
```

**这才是用户要的答案**。

### 序列总结

```
Assistant(Content="", ToolCalls=[get_weather])
    ↓
Tool(ToolName="get_weather", Content="{...}")
    ↓
Assistant(Content="北京今天晴，气温 18°C。")   ← 最终答案
    ↓
（迭代器关闭）
```

**注意没有 `Exit` 事件**。正常终止就是迭代器关闭。

### 流式下的差异

`EnableStreaming: true` 时，事件 1 和 3 的 `IsStreaming` 为 `true`，`Message` 为 nil，`MessageStream` 有值。

**事件 2（工具结果）通常仍是 `IsStreaming: false`**——除非工具本身实现了 `StreamableTool`。

**这就是为什么事件处理要统一用 `GetMessage()`**：

```go
msg, err := mv.GetMessage()   // 自动处理流式/非流式
if err != nil {
    return err
}
fmt.Println(msg.Content)
```

### 三个场景

| 场景 | `GetToolCallID` 返回 |
|---|---|
| 工具经 `ToolsNode` 执行（Agent 正常流程） | 调用 ID |
| 直接调 `tool.InvokableRun(ctx, args)` | `""` |
| 在中间件的 `WrapInvokableToolCall` 里 | 调用 ID（通过 `tCtx.CallID`） |

**第三条**：`adk.ToolContext`（`handler.go:45`）直接给你 `CallID`：

```go
    endpoint adk.InvokableToolCallEndpoint, tCtx *adk.ToolContext) (
    adk.InvokableToolCallEndpoint, error) {
```

**这比 `compose.GetToolCallID(ctx)` 更可靠**——因为它不依赖 ctx 的内部结构。

### 为什么工具需要知道自己的 CallID

**用途 1：日志关联**。把工具执行日志和模型调用关联起来。

**用途 2：中断恢复**。工具要中断（`compose.Interrupt`），恢复时需要知道"恢复到哪次调用"。

**用途 3：幂等**。如果工具被重试，用 CallID 做去重键。

## 5.10 翻译成 SSE

`AgentEvent` 是框架视角，SSE 是前端视角。中间需要一个翻译层。

### 事件契约

先定契约：

| SSE 事件 | 数据 | 触发时机 |
|---|---|---|
| `message` | `{"text": "增量文本"}` | Assistant 流式帧 |
| `tool_start` | `{"name": "search", "call_id": "..."}` | 模型返回 ToolCalls |
| `tool_end` | `{"name": "search", "result": "..."}` | Tool 事件 |
| `error` | `{"message": "..."}` | `ev.Err != nil` |
| `done` | `{"status": "completed"}` | 迭代器关闭 |

### 翻译层实现

```go
type sseEvent struct {
    Name string
    Data any
}

func pump(ctx context.Context, iter *adk.AsyncIterator[*adk.AgentEvent],
    emit func(sseEvent) error) error {

    for {
        ev, ok := iter.Next()
        if !ok {
            return nil                  // 正常结束，由调用方发 done
        }

        // 客户端断开：ctx 取消，尽早停止，别继续烧模型 token
        if err := ctx.Err(); err != nil {
            return err
        }

        if ev.Err != nil {
            return ev.Err
        }

        // 控制事件：Exit 表示 Agent 主动收尾
        if ev.Action != nil && ev.Action.Exit {
            return nil
        }

        if ev.Output == nil || ev.Output.MessageOutput == nil {
            continue
        }

        mv := ev.Output.MessageOutput
        switch mv.Role {
        case schema.Tool:
            text, err := drainStream(mv)
            if err != nil {
                return err
            }
            if err := emit(sseEvent{Name: "tool_end", Data: map[string]any{
                "name": mv.ToolName, "result": text,
            }}); err != nil {
                return err
            }

        case schema.Assistant:
            if !mv.IsStreaming {
                if mv.Message != nil && mv.Message.Content != "" {
                    if err := emit(sseEvent{Name: "message", Data: map[string]any{
                        "text": mv.Message.Content,
                    }}); err != nil {
                        return err
                    }
                }
                continue
            }
            if mv.MessageStream == nil {
                continue
            }
            for {
                chunk, err := mv.MessageStream.Recv()
                if errors.Is(err, io.EOF) {
                    break
                }
                if err != nil {
                    mv.MessageStream.Close()
                    return err
                }
                if chunk.Content == "" {
                    continue                // 空帧不推给前端
                }
                if err := emit(sseEvent{Name: "message", Data: map[string]any{
                    "text": chunk.Content,
                }}); err != nil {
                    mv.MessageStream.Close()
                    return err
                }
            }
            mv.MessageStream.Close()
        }
    }
}
```

### 三个设计要点

**要点一：`emit` 返回 `error`，用它做背压。**

当 `emit` 写 SSE 失败（通常是客户端断开），立即返回错误让 `pump` 停止。这样 Agent 不会在无人接收的情况下继续跑完整个流程、白烧 token。

**要点二：`ctx.Err()` 每轮检查。**

这是第二道保险。`emit` 失败可能滞后（比如缓冲还没满），主动检查 ctx 能更早退出。

**要点三：空帧过滤。**

流式分片里经常有 `Content == ""` 的帧（携带元数据或 role 信息）。推给前端会让 UI 闪烁，`continue` 掉。

### tool_start 从哪来

注意上面的实现里没有 `tool_start`。因为**框架没有单独的"工具开始"事件**——它体现在 Assistant 事件的 `ToolCalls` 字段里：

```go
case schema.Assistant:
    // 流式时 ToolCalls 可能分片到达，完整版在非流式的 Message 里
    if mv.Message != nil {
        for _, tc := range mv.Message.ToolCalls {
            emit(sseEvent{Name: "tool_start", Data: map[string]any{
                "name":    tc.Function.Name,
                "call_id": tc.ID,
            }})
        }
    }
```

流式模式下 `ToolCalls` 会在多个 chunk 里按 `Index` 分片，需要累积。如果只需要「工具被调用了」这个信号，用 `tool_end` 就够了——它一定在工具执行完之后出现，且带有 `ToolName`。

**更可靠的做法**：在中间件的 `WrapInvokableToolCall` 里发 `tool_start`。因为那里一定有 `tCtx.Name` 和 `tCtx.CallID`，且时序准确（工具真正开始执行）。

# 第 6 章　完整可运行示例

本章给出三个渐进式示例，全部可直接 `go run`。代码风格参考官方 `eino-examples`：**泛型骨架 + 具体模型注入**。

## 6.1 关于泛型骨架

官方示例大量使用这种写法：

```go
func runTyped[M adk.MessageType](ctx context.Context, ...) error
```

**为什么？** 因为 `adk.MessageType` 是封闭联合（见 [阅读约定](#泛型约定)），框架内部需要同时支持两条消息路径。官方示例为了演示两条路径，写成泛型；具体项目通常只走一条，不需要泛型。

**但有一类 helper 必须泛型**——比如"打印并收集消息"：

```go
func printAndCollect[M adk.MessageType](mv *adk.TypedMessageVariant[M]) (M, error) {
    msg, err := mv.GetMessage()
    if err != nil {
        var zero M
        return zero, err
    }
    return msg, nil
}
```

这是因为 `GetMessage()` 的返回类型依赖 `M`。

**如果你的项目只用 `*schema.Message`，直接写具体类型，不要泛型**。泛型会带来大量 `any(...)` 转换和类型断言，可读性下降。

## 6.2 示例一：纯 ChatModel（最小可用）

**目标**：验证模型配置正确，理解 `Generate` / `Stream` 的差异。

```go
package main

	"io"
	"os"

	"github.com/cloudwego/eino-ext/components/model/openai"
	"github.com/cloudwego/eino/components/model"

func main() {
	ctx := context.Background()

	m, err := openai.NewChatModel(ctx, &openai.ChatModelConfig{
		BaseURL: os.Getenv("OPENAI_BASE_URL"),
		APIKey:  os.Getenv("OPENAI_API_KEY"),
		Model:   os.Getenv("OPENAI_MODEL"),
	})
	if err != nil {
		panic(err)
	}

	msgs := []*schema.Message{
		schema.SystemMessage("你是一个简洁的助手，回答不超过两句话。"),
		schema.UserMessage("用一句话解释什么是 Go 的 goroutine。"),
	}

	// ---- Generate：阻塞式 ----
	fmt.Println("=== Generate ===")
	resp, err := m.Generate(ctx, msgs, model.WithTemperature(0.3))
	if err != nil {
		panic(err)
	}
	fmt.Println("内容:", resp.Content)
	if resp.ResponseMeta != nil {
		fmt.Printf("FinishReason=%s\n", resp.ResponseMeta.FinishReason)
		if u := resp.ResponseMeta.Usage; u != nil {
			fmt.Printf("tokens: prompt=%d completion=%d total=%d cached=%d\n",
				u.PromptTokens, u.CompletionTokens, u.TotalTokens,
				u.PromptTokenDetails.CachedTokens)
		}
	}

	// ---- Stream：流式 ----
	fmt.Println("=== Stream ===")
	sr, err := m.Stream(ctx, msgs, model.WithTemperature(0.3))
	if err != nil {
		panic(err)
	}

	var chunks []*schema.Message
	for {
		chunk, err := sr.Recv()
		if errors.Is(err, io.EOF) {
			break
		}
		if err != nil {
			sr.Close()
			panic(err)
		}
		fmt.Print(chunk.Content)   // 逐片打印
		chunks = append(chunks, chunk)
	}
	sr.Close()
	fmt.Println()

	// 用 ConcatMessages 还原，验证和 Generate 结果结构一致
	full, err := schema.ConcatMessages(chunks)
	if err != nil {
		panic(err)
	}
	fmt.Println("拼接后长度:", len([]rune(full.Content)), "分片数:", len(chunks))
}
```

**关键点**：

1. 环境变量读配置，不硬编码；
2. `Generate` 直接拿完整消息，`Stream` 需要循环 + `ConcatMessages`；
3. 打印 `CachedTokens`——如果第二次调用它还是 0，说明缓存没生效。

## 6.3 示例二：加 Tool 的 Agent

**目标**：理解工具定义、工具调用事件序列、`ReturnDirectly`。

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"os"

	"github.com/cloudwego/eino-ext/components/model/openai"
	"github.com/cloudwego/eino/adk"
	"github.com/cloudwego/eino/components/tool"
	"github.com/cloudwego/eino/components/tool/utils"
	"github.com/cloudwego/eino/compose"
	"github.com/cloudwego/eino/schema"
)

// ---------- 工具定义 ----------

type weatherArgs struct {
	City string `json:"city" jsonschema:"description=城市名称，如 北京、上海"`
	Unit string `json:"unit,omitempty" jsonschema:"description=温度单位，celsius 或 fahrenheit，默认 celsius,enum=celsius,enum=fahrenheit"`
}

type weatherResult struct {
	City string  `json:"city"`
	Temp float64 `json:"temp"`
	Desc string  `json:"desc"`
	Unit string  `json:"unit"`
}

func newWeatherTool() tool.BaseTool {
	t, err := utils.InferTool("get_weather",
		"查询指定城市的实时天气。当用户询问天气、温度、下雨、晴天等信息时使用。",
		func(ctx context.Context, args *weatherArgs) (*weatherResult, error) {
			// 真实项目这里调天气 API；示例返回固定数据
			unit := args.Unit
			if unit == "" {
				unit = "celsius"
			}
			temp := 18.0
			if unit == "fahrenheit" {
				temp = temp*9/5 + 32
			}
			return &weatherResult{
				City: args.City,
				Temp: temp,
				Desc: "晴",
				Unit: unit,
			}, nil
		})
	if err != nil {
		panic(err)
	}
	return t
}

func main() {
	ctx := context.Background()

	model, err := openai.NewChatModel(ctx, &openai.ChatModelConfig{
		BaseURL: os.Getenv("OPENAI_BASE_URL"),
		APIKey:  os.Getenv("OPENAI_API_KEY"),
		Model:   os.Getenv("OPENAI_MODEL"),
	})
	if err != nil {
		panic(err)
	}

	// ---------- 构造 Agent ----------
	agent, err := adk.NewChatModelAgent(context.Background(), &adk.ChatModelAgentConfig{
		Name:        "weather_agent",
		Description: "查询天气的助手",
		Instruction: "你是一个天气助手。用户问天气时，调用 get_weather 工具查询。",
		Model:       model,
		MaxIterations: 10,
		ToolsConfig: adk.ToolsConfig{
			ToolsNodeConfig: compose.ToolsNodeConfig{
				Tools: []tool.BaseTool{newWeatherTool()},

				// 模型幻觉工具名时优雅降级，而不是整体失败
				UnknownToolsHandler: func(ctx context.Context, name, input string) (string, error) {
					return fmt.Sprintf("工具 %q 不存在，请从可用工具列表中选择。", name), nil
				},
			},
			// 天气查询结果是结构化的，不需要模型总结
			// ReturnDirectly: map[string]bool{"get_weather": true},
		},
	})
	if err != nil {
		panic(err)
	}

	runner := adk.NewRunner(context.Background(), adk.RunnerConfig{
		Agent:           agent,
		EnableStreaming: false,
	})

	// ---------- 执行并逐事件打印 ----------
	iter := runner.Run(ctx, []*schema.Message{
		schema.UserMessage("北京今天天气怎么样？"),
	})

	step := 0
	for {
		ev, ok := iter.Next()
		if !ok {
			break
		}
		step++

		if ev.Err != nil {
			fmt.Printf("[%d] 错误: %v\n", step, ev.Err)
			if errors.Is(ev.Err, adk.ErrExceedMaxIterations) {
				fmt.Println("  → 工具调用陷入循环，考虑调大 MaxIterations 或优化工具返回")
			}
			continue
		}

		if ev.Action != nil {
			fmt.Printf("[%d] Action: Exit=%v Interrupted=%v\n",
				step, ev.Action.Exit, ev.Action.Interrupted != nil)
			if ev.Action.Exit {
				break
			}
		}

		if ev.Output == nil || ev.Output.MessageOutput == nil {
			continue
		}

		mv := ev.Output.MessageOutput
		msg, err := mv.GetMessage()
		if err != nil {
			fmt.Printf("[%d] 取消息失败: %v\n", step, err)
			continue
		}

		switch mv.Role {
		case schema.Assistant:
			if len(msg.ToolCalls) > 0 {
				fmt.Printf("[%d] Assistant 请求调用工具:\n", step)
				for _, tc := range msg.ToolCalls {
					fmt.Printf("      name=%s args=%s id=%s\n",
						tc.Function.Name, tc.Function.Arguments, tc.ID)
				}
				if msg.Content != "" {
					fmt.Printf("      附带文本: %q\n", msg.Content)
				}
			} else {
				fmt.Printf("[%d] Assistant 最终回答: %s\n", step, msg.Content)
			}

		case schema.Tool:
			var wr weatherResult
			if err := json.Unmarshal([]byte(msg.Content), &wr); err == nil {
				fmt.Printf("[%d] Tool 结果: %s %v° %s (callID=%s)\n",
					step, wr.City, wr.Temp, wr.Desc, msg.ToolCallID)
			} else {
				fmt.Printf("[%d] Tool 原始结果: %s\n", step, msg.Content)
			}
		}
	}

	fmt.Println("=== 完成 ===")
}
```

**观察要点**：

1. 事件序列是 `Assistant(空内容+ToolCalls)` → `Tool` → `Assistant(答案)`，和 [5.8](#58-一次带工具调用的完整事件序列) 一致；
2. `UnknownToolsHandler` 让幻觉工具名不至于整体失败；
3. `ErrExceedMaxIterations` 可以 `errors.Is` 判断。

**试试改成流式**：把 `EnableStreaming` 设为 `true`，观察 `mv.IsStreaming` 和 `mv.MessageStream` 的变化。注意工具结果事件通常仍是 `IsStreaming: false`。

## 6.4 示例三：完整生产骨架（事件流 + 取消 + 检查点）

**目标**：把前面所有能力组合成一个可用的骨架。

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"io"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"

	"github.com/cloudwego/eino-ext/components/model/openai"
	"github.com/cloudwego/eino/adk"
	"github.com/cloudwego/eino/schema"
)

// ---------- 检查点存储（生产环境换成 Redis / MySQL） ----------
type memStore struct {
	mu sync.RWMutex
	m  map[string][]byte
}

func newMemStore() *memStore { return &memStore{m: make(map[string][]byte)} }

func (s *memStore) Set(_ context.Context, key string, v []byte) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[key] = append([]byte(nil), v...)
	return nil
}

func (s *memStore) Get(_ context.Context, key string) ([]byte, bool, error) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[key]
	return v, ok, nil
}

func (s *memStore) Delete(_ context.Context, key string) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	delete(s.m, key)
	return nil
}

// ---------- SSE 事件 ----------
type sseEvent struct {
	Name string
	Data map[string]any
}

// ---------- 事件泵 ----------
func pump(ctx context.Context, iter *adk.AsyncIterator[*adk.AgentEvent],
	emit func(sseEvent) error) error {

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		ev, ok := iter.Next()
		if !ok {
			return nil
		}

		if ev.Err != nil {
			return ev.Err
		}

		if ev.Action != nil {
			if ev.Action.Exit {
				return nil
			}
			if ev.Action.Interrupted != nil {
				if err := emit(sseEvent{"interrupt", map[string]any{
					"data": ev.Action.Interrupted.Data,
				}}); err != nil {
					return err
				}
				continue
			}
		}

		if ev.Output == nil || ev.Output.MessageOutput == nil {
			continue
		}

		mv := ev.Output.MessageOutput

		switch mv.Role {
		case schema.Tool:
			text, err := drain(mv)
			if err != nil {
				return err
			}
			if err := emit(sseEvent{"tool_end", map[string]any{
				"name":   mv.ToolName,
				"result": text,
			}}); err != nil {
				return err
			}

		case schema.Assistant:
			if !mv.IsStreaming {
				if mv.Message == nil {
					continue
				}
				// 非流式：工具调用意图
				for _, tc := range mv.Message.ToolCalls {
					if err := emit(sseEvent{"tool_start", map[string]any{
						"name": tc.Function.Name, "call_id": tc.ID,
					}}); err != nil {
						return err
					}
				}
				if mv.Message.Content != "" {
					if err := emit(sseEvent{"message", map[string]any{
						"text": mv.Message.Content,
					}}); err != nil {
						return err
					}
				}
				continue
			}

			// 流式：逐帧推送
			if mv.MessageStream == nil {
				continue
			}
			for {
				chunk, err := mv.MessageStream.Recv()
				if errors.Is(err, io.EOF) {
					break
				}
				if err != nil {
					mv.MessageStream.Close()
					return err
				}
				if chunk.Content == "" {
					continue
				}
				if err := emit(sseEvent{"message", map[string]any{
					"text": chunk.Content,
				}}); err != nil {
					mv.MessageStream.Close()
					return err
				}
			}
			mv.MessageStream.Close()
		}
	}
}

func drain(mv *adk.MessageVariant) (string, error) {
	msg, err := mv.GetMessage()
	if err != nil {
		return "", err
	}
	return msg.Content, nil
}

// ---------- main ----------
func main() {
	// 根 ctx：响应 Ctrl+C
	rootCtx, stop := signal.NotifyContext(context.Background(),
		syscall.SIGINT, syscall.SIGTERM)
	defer stop()

	m, err := openai.NewChatModel(rootCtx, &openai.ChatModelConfig{
		BaseURL: os.Getenv("OPENAI_BASE_URL"),
		APIKey:  os.Getenv("OPENAI_API_KEY"),
		Model:   os.Getenv("OPENAI_MODEL"),
	})
	if err != nil {
		panic(err)
	}

	agent, err := adk.NewChatModelAgent(context.Background(), &adk.ChatModelAgentConfig{
		Name:          "assistant",
		Description:   "通用助手",
		Instruction:   "你是一个严谨、简洁的助手。",
		Model:         m,
		MaxIterations: 15,
	})
	if err != nil {
		panic(err)
	}

	store := newMemStore()
	runner := adk.NewRunner(context.Background(), adk.RunnerConfig{
		Agent:           agent,
		EnableStreaming: true,
		CheckPointStore: store,
	})

	// 模拟用户 3 秒后点"停止"
	runCtx, cancelRun := context.WithCancel(rootCtx)
	go func() {
		time.Sleep(3 * time.Second)
		fmt.Println("\n[模拟用户点击停止]")
		cancelRun()
	}()

	emit := func(e sseEvent) error {
		fmt.Printf("SSE %-12s %v\n", e.Name, e.Data)
		return nil
	}

	iter := runner.Run(runCtx, []*schema.Message{
		schema.UserMessage("请用三句话介绍 Go 语言的并发模型。"),
	})

	err = pump(runCtx, iter, emit)
	switch {
	case err == nil:
		_ = emit(sseEvent{"done", map[string]any{"status": "completed"}})
	case errors.Is(err, context.Canceled):
		_ = emit(sseEvent{"done", map[string]any{"status": "canceled"}})
	default:
		_ = emit(sseEvent{"error", map[string]any{"message": err.Error()}})
	}
}
```

**这段骨架包含**：

1. **信号处理**：Ctrl+C 取消根 ctx；
2. **检查点存储**：实现了 `Set`/`Get`/`Delete`（`Delete` 让框架自动清理）；
3. **事件泵**：处理四类事件，翻译成 SSE；
4. **流式**：`EnableStreaming: true`，逐帧推送；
5. **取消**：ctx 取消时立即停止，不发 `done: completed`。

**生产环境还要补**：

- 检查点存储换成 Redis（带 TTL）；
- `emit` 换成真正的 SSE writer（`http.ResponseWriter` + `Flush`）；
- 加 `WithCallbacks` 上报指标；
- 加 `UnknownToolsHandler`；
- 加 `ModelRetryConfig`。

## 6.5 关于 eino-examples 里的 msgops

```go
func ToMessage[M adk.MessageType](m M) (*schema.Message, error) {
    switch v := any(m).(type) {
    case *schema.Message:
        return v, nil
    case *schema.AgenticMessage:

    }

func FromMessage(msg *schema.Message) adk.Message {
    return msg
}
```

## 7.8 一个诊断流程

遇到 Agent 行为异常，按这个顺序排查：

```
1. 事件流完整吗？
   └─ 消费到最后 Next() 返回 false 了吗？错误事件处理了吗？

2. 事件序列符合预期吗？
   └─ 打印每个事件的 Role / IsStreaming / ToolCalls 数量 / Action

3. 模型看到的是什么？
   └─ 在 BeforeModelRewriteState 里打印 state.Messages 和 state.ToolInfos

4. 工具真的执行了吗？
   └─ 在 WrapInvokableToolCall 里打日志（有 tCtx.Name 和 tCtx.CallID）

5. 是不是撞了上限？
   └─ errors.Is(err, adk.ErrExceedMaxIterations)

6. token 花在哪了？
   └─ 检查 ResponseMeta.Usage 的细分字段，特别是 CachedTokens
```

**第 3 步是最有价值的一步**。绝大多数"Agent 行为不对"的问题，在打印出模型实际收到的消息后就能定位——要么是历史没传对，要么是工具定义有问题，要么是 system prompt 被意外修改。

## D.3 一个必须记住的原则

**源码里的 `Deprecated` 注释是权威的，官网不是。**

判断一个 API 该不该用：

```bash
# 查源码注释
grep -B 5 "func WithTools" $(go env GOMODCACHE)/github.com/cloudwego/eino@v0.9.23/components/model/option.go

# 查类型是否弃用
grep -B 10 "type ChatModel interface" $(go env GOMODCACHE)/github.com/cloudwego/eino@v0.9.23/components/model/interface.go
```

源码注释里会明确写：
- `Deprecated: ...` —— 别用；
- `NOT RECOMMENDED: ...` —— 能用但不推荐，通常带原因和替代方案；
- `Recommended use cases` / `Discouraged use cases` —— 直接告诉你边界。

# 本章小结

## 五个组件的职责边界

| 组件 | 职责 | 不负责 |
|---|---|---|
| `Message` | 对话数据载体 | 校验合法性、管理历史 |
| `ChatModel` | 和模型通信 | 工具执行、循环、状态 |
| `ChatModelAgent` | 循环 + 工具编排 | 检查点、取消、事件中转 |
| `Runner` | 执行入口 + 生命周期 | 消息构造、业务逻辑 |
| `AgentEvent` | 执行过程投影 | 序列化、SSE 翻译 |

## 十条必须记住的规则

1. **`IsStreaming == true` 时 `Message` 必为 nil** —— 用 `GetMessage()`，别直接解引用。
2. **`StreamReader` 必须 `defer Close()`** —— `SetAutomaticClose()` 只是兜底。
3. **`Copy(n)` 之后原 reader 失效** —— 需要多处消费时才 `Copy`。
4. **带工具调用时第一个 Assistant 事件 `Content` 为空** —— 取最后一个。
5. **`Run` / `Query` 不返回 error** —— 必须完整消费事件流。
6. **`NewRunner` 的 ctx 被丢弃** —— 用应用级 ctx；`Run` 的 ctx 才生效。
7. **`SessionValues` 非空会触发 FString 格式化** —— instruction 里的 `{` 要双写。
8. **易变内容放最后** —— 否则 prompt 缓存全废，看 `CachedTokens` 验证。
9. **`BeforeModelRewriteState` 是唯一官方的 state 修改点** —— `WrapModel` 里改不持久化且破坏缓存。
10. **`AfterAgent` 只在成功时调用** —— 清理用 `defer`。
