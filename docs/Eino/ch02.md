# 第二章：Tool——让 Agent 真正具备「做事」的能力

> **依据**：`github.com/cloudwego/eino v0.9.23` 源码。所有 API 描述均引自该版本源码，代码均在本机编译验证。
> 官网文档在本版本上已有滞后，**以源码为准**（参见第一章[附录 D](ch01.md#附录-d-与旧版-api-的差异清单)）。

## 为什么需要 Tool

第一章的 Agent 只会「说话」。它能理解你的问题、组织语言回答，但它无法知道今天北京的天气、无法查数据库、无法读写文件——**模型的知识止于训练数据**。

`Tool` 就是把这堵墙凿开的机制：把外部能力描述给模型，模型在需要时「请求调用」，框架执行后把结果回填，模型基于真实结果继续推理。

这一章要回答四个问题：

1. **Tool 是什么**——接口定义与它的四个变体
2. **Tool 怎么被调用**——ToolsNode 与 ToolCall 的关系
3. **怎么自定义 Tool**——从最简单的到最灵活的
4. **怎么传给 Agent**——三种场景，选错会浪费或失效

---

## 一、Tool 的定义

### 1.1 接口层次

`eino/components/tool/interface.go` 定义了四个接口，呈树状结构：

```go
// BaseTool 只提供元信息，不能执行
type BaseTool interface {
    Info(ctx context.Context) (*schema.ToolInfo, error)
}

// 标准：入参是 JSON 字符串，出参是字符串
type InvokableTool interface {
    BaseTool
    InvokableRun(ctx context.Context, argumentsInJSON string, opts ...Option) (string, error)
}

// 标准流式
type StreamableTool interface {
    BaseTool
    StreamableRun(ctx context.Context, argumentsInJSON string, opts ...Option) (*schema.StreamReader[string], error)
}

// 增强型：出参是结构化多模态结果
type EnhancedInvokableTool interface {
    BaseTool
    InvokableRun(ctx context.Context, toolArgument *schema.ToolArgument, opts ...Option) (*schema.ToolResult, error)
}

// 增强型流式
type EnhancedStreamableTool interface {
    BaseTool
    StreamableRun(ctx context.Context, toolArgument *schema.ToolArgument, opts ...Option) (*schema.StreamReader[*schema.ToolResult], error)
}
```

几个关键点：

- **`BaseTool` 不能执行**。它只够把工具「介绍」给模型（用于 `WithTools`）。要真正跑起来，必须实现 `InvokableTool` 或 `StreamableTool`。
- **标准与增强型的区别只有两点**：入参从 `string` 变成 `*schema.ToolArgument`，出参从 `string` 变成 `*schema.ToolResult`（可携带图片、音频、文件）。
- **`EnhancedInvokableTool` 与 `InvokableTool` 方法名相同**（都叫 `InvokableRun`），但签名不同。所以一个类型**不可能同时实现两者**——Go 不允许方法重载。想同时支持只能写两个类型，或者依赖 `ToolResult.ToMessageInputParts()` 在标准接口里返回文本。

### 1.2 ToolInfo：模型看到的全部信息

```go
type ToolInfo struct {
    Name string   // 工具名，模型用它来「点名」
    Desc string   // 何时、为何、如何用这个工具
    Extra map[string]any
    *ParamsOneOf  // 参数 schema
}
```

**`Desc` 是最容易写废的字段。** 模型完全依赖它决定要不要调、怎么调。写「查询天气」和写「查询指定城市未来 7 天的天气，返回温度与降水概率；用户问『今天热不热』时使用」，效果差一个量级。

参数 schema 有两种构造方式：

```go
// 方式一：手写 ParameterInfo（简单参数）
schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
    "city": {Type: schema.String, Desc: "城市名", Required: true},
    "days": {Type: schema.Integer, Desc: "天数", Required: false},
})

// 方式二：完整 JSON Schema（复杂约束：anyOf、oneOf、$defs）
schema.NewParamsOneOfByJSONSchema(js)
```

**两者只能选一个**，同时设置是无效的。`ParamsOneOf` 为 `nil` 表示工具无入参。

> 官网文档里出现过 `schema.NewParamsOneOfByOpenAPIV3`，**该方法在 v0.9.23 中并不存在**。以源码为准，只有 `ByParams` 和 `ByJSONSchema` 两个构造函数。

`DataType` 支持七种：`Object`、`Number`、`Integer`、`String`、`Array`、`Null`、`Boolean`。

## 二、Tool 的调用

### 2.1 调用链：模型只「申请」，ToolsNode 才「执行」

这是最容易混淆的地方。完整链路是：

```
用户提问
   ↓
ChatModel.Generate(msgs, WithTools(toolInfos))
   ↓
模型返回 AssistantMessage{Content: "", ToolCalls: [{ID, Function{Name, Arguments}}]}
   ↑ 注意：模型只生成「调用意图」，没有执行任何东西
   ↓
ToolsNode.Invoke(ctx, 这条 assistant 消息)
   ↓
逐个执行 ToolCall → 每个结果包成 ToolMessage{Content, ToolCallID}
   ↓
把 ToolMessage 追加回 messages，再次调用 ChatModel
   ↓
模型基于工具结果生成最终回答
```

**模型不会执行任何代码。** 它只是输出一段 JSON 表达「我想调用 get_weather，参数是 {city:北京}」。真正执行的是 `ToolsNode`。

### 2.2 ToolsNode

```go
type ToolsNodeConfig struct {
    Tools []tool.BaseTool

    // 模型幻觉出不存在的工具名时，默认报错；配置它可优雅降级
    UnknownToolsHandler func(ctx context.Context, name, input string) (string, error)

    // true = 按 ToolCalls 顺序串行；false（默认）= 并行
    ExecuteSequentially bool

    // 执行前改写参数
    ToolArgumentsHandler func(ctx context.Context, name, arguments string) (string, error)

    // 工具名/参数别名，容忍模型用别名调用
    ToolAliases map[string]ToolAliasConfig

    ToolCallMiddlewares []ToolMiddleware
}
```

### 2.3 直接使用 ToolsNode

不用 Agent 也能跑工具：

```go
node, err := compose.NewToolNode(ctx, &compose.ToolsNodeConfig{
    Tools: []tool.BaseTool{weatherTool},
})
if err != nil {
    return err
}

msgs, err := node.Invoke(ctx, &schema.Message{
    Role: schema.Assistant,
    ToolCalls: []schema.ToolCall{{
        ID:   "call_abc",
        Type: "function",
        Function: schema.FunctionCall{
            Name:      "get_weather",
            Arguments: `{"city":"北京"}`,
        },
    }},
})
```

返回的 `msgs` 是 `[]*schema.Message`，每个 `Role` 都是 `schema.Tool`，`ToolCallID` 与输入对应。

**输出顺序与 `ToolCalls` 顺序一致**，即使内部并行执行。这个保证很重要——回填给模型时必须按序，否则 `ToolCallID` 对不上。

### 2.4 未知工具的处理

我实测了两种行为：

```go
// 不配置 handler：直接报错
_, err := node.Invoke(ctx, msgWithUnknownTool)
// err: tool nope not found in toolsNode indexes

// 配置 handler：降级为文本返回
node, _ := compose.NewToolNode(ctx, &compose.ToolsNodeConfig{
    Tools: []tool.BaseTool{weatherTool},
    UnknownToolsHandler: func(_ context.Context, name, _ string) (string, error) {
        return "没有这个工具: " + name, nil
    },
})
```

**生产环境务必配置这个 handler。** 模型偶尔会编造工具名（尤其工具数量多时），不配置会直接中断整轮对话。返回一句「该工具不存在」让模型自己纠正，体验好得多。

### 2.5 获取本次调用的 CallID

工具内部有时需要知道自己的 call id（写日志、去重、关联回调）：

```go
func(ctx context.Context, in *Query) (string, error) {
    callID := compose.GetToolCallID(ctx)
    // ...
}
```

**这个值只在经 ToolsNode 执行时才有。** 我实测直接调 `tool.InvokableRun(ctx, args)` 拿到的是空字符串——因为 context 里没被注入。需要 call id 的测试必须走 ToolsNode。

## 三、自定义 Tool

### 3.1 方式一：InferTool（推荐，覆盖 90% 场景）

从 Go struct 的 tag 自动推导 JSON Schema：

```go
type WeatherInput struct {
    City string `json:"city" jsonschema:"required,description=城市名，如 北京"`
    Date string `json:"date,omitempty" jsonschema:"description=日期，留空表示今天"`
}

type WeatherOutput struct {
    City string `json:"city"`
    Temp int    `json:"temp"`
    Desc string `json:"desc"`
}

weatherTool, err := utils.InferTool("get_weather", "查询指定城市的天气",
    func(ctx context.Context, in *WeatherInput) (*WeatherOutput, error) {
        return &WeatherOutput{City: in.City, Temp: 26, Desc: "晴"}, nil
    })
```

**`InferTool` 做了什么**：自动 JSON 解码模型给参数字符串到 `T`，自动 JSON 编码返回值 `D` 成结果字符串。你只管写业务逻辑。

无入参的工具用空 struct：

```go
timeTool, _ := utils.InferTool("get_time", "获取服务器当前时间",
    func(ctx context.Context, _ struct{}) (string, error) {
        return time.Now().Format(time.RFC3339), nil
    })
```

### 3.2 jsonschema tag 的坑（实测）

我实际跑了一遍 schema 生成，发现 `required` 的规则**与直觉相反**：

| struct 写法 | 生成结果 |
|---|---|
| `json:"a"` | **required** |
| `json:"b,omitempty"` | 可选 |
| `json:"c,omitempty" jsonschema:"required,..."` | **required**（显式覆盖 omitempty） |

也就是说：**字段默认必填，加 `omitempty` 才变可选。** 这和常见的「必填要显式声明」相反，很容易写出模型永远填不全的 schema。

支持的 tag：

```go
type Query struct {
    Keyword string   `json:"keyword" jsonschema:"required,description=搜索关键词"`
    Limit   int      `json:"limit,omitempty" jsonschema:"description=返回条数,default=10"`
    Lang    string   `json:"lang,omitempty" jsonschema:"enum=zh,enum=en,description=语言"`
    Tags    []string `json:"tags,omitempty" jsonschema:"description=标签过滤"`
    Deep    *Nested  `json:"deep,omitempty" jsonschema:"description=嵌套参数"`
}
```

生成：

```json
{
  "properties": {
    "keyword": {"description": "搜索关键词", "type": "string"},
    "limit": {"description": "返回条数", "default": 10, "type": "integer"},
    "lang": {"enum": ["zh", "en"], "description": "语言", "type": "string"},
    "tags": {"items": {"type": "string"}, "description": "标签过滤", "type": "array"},
    "deep": {"properties": {"level": {"type": "integer"}}, "type": "object", "required": ["level"]}
  },
  "required": ["keyword"],
  "type": "object"
}
```

可用的 tag 键：`required`、`description`、`enum`（可重复）、`default`、`example`。

### 3.3 方式二：NewTool（手写 ToolInfo）

schema 无法从 struct 推导时（动态字段、需要精细控制）用这个：

```go
toolInfo := &schema.ToolInfo{
    Name: "file_generator",
    Desc: "生成并返回文件",
    ParamsOneOf: schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
        "file_name": {Type: schema.String, Desc: "文件名", Required: true},
        "content":   {Type: schema.String, Desc: "文件内容", Required: true},
    }),
}

t := utils.NewTool[*FileInput, string](toolInfo,
    func(ctx context.Context, in *FileInput) (string, error) {
        return "生成成功", nil
    })
```

**注意**：`NewTool` 没有编译期检查，你必须自己保证 `ParamsOneOf` 的字段与 `T` 的字段一致。写错了只会在运行时解码失败。

### 3.4 方式三：手写实现接口（最大控制权）

需要动态 `Info()`（比如按用户权限过滤可用参数）时用这个：

```go
type EchoTool struct{ info *schema.ToolInfo }

func (t *EchoTool) Info(ctx context.Context) (*schema.ToolInfo, error) {
    return t.info, nil
}

func (t *EchoTool) InvokableRun(ctx context.Context, args string, opts ...tool.Option) (string, error) {
    // 自己处理 JSON 解码
    var in struct{ Text string `json:"text"` }
    if err := json.Unmarshal([]byte(args), &in); err != nil {
        return "", fmt.Errorf("参数解析失败: %w", err)
    }
    return "echo: " + in.Text, nil
}

func NewEchoTool() tool.InvokableTool {
    return &EchoTool{info: &schema.ToolInfo{
        Name: "echo",
        Desc: "回显参数",
        ParamsOneOf: schema.NewParamsOneOfByParams(map[string]*schema.ParameterInfo{
            "text": {Type: schema.String, Desc: "要回显的文本", Required: true},
        }),
    }}
}
```

三种方式的取舍：

| 方式 | 适用 | 代价 |
|---|---|---|
| `InferTool` | 绝大多数场景 | 无，schema 自动生成 |
| `NewTool` | schema 需精细控制 | 手动保证 schema 与 struct 一致 |
| 手写接口 | 动态 Info、自定义解码 | 全部自己写 |

### 3.5 增强型工具：返回图片/文件

标准工具只能返回字符串。要返回图片、音频、文件，用增强型：

```go
type ImageInput struct {
    Query string `json:"query" jsonschema:"required,description=搜索关键词"`
}

imageTool, err := utils.InferEnhancedTool("image_search", "搜索图片",
    func(ctx context.Context, in *ImageInput) (*schema.ToolResult, error) {
        url := "https://example.com/a.png"
        return &schema.ToolResult{Parts: []schema.ToolOutputPart{
            {Type: schema.ToolPartTypeText, Text: "找到图片"},
            {Type: schema.ToolPartTypeImage, Image: &schema.ToolOutputImage{
                MessagePartCommon: schema.MessagePartCommon{URL: &url},
            }},
        }}, nil
    })
```

`ToolOutputPart.Type` 可取 `text`、`image`、`audio`、`video`、`file`。多模态部分用 `MessagePartCommon` 承载，`URL`、`Base64Data`、`FileID` **三选一**。

**重要限制**：`ToolResult` 的媒体部分最终会被转成 `MessageInputPart` 回填给模型。也就是说**只有支持多模态输入的模型才能真正消费这些图片**。字段存在不代表模型支持——接入前务必核对所用模型的能力。

### 3.6 流式工具

```go
searchTool, err := utils.InferStreamTool("stream_search", "流式搜索",
    func(ctx context.Context, in *SearchInput) (*schema.StreamReader[string], error) {
        return schema.StreamReaderFromArray([]string{"片段1", "片段2"}), nil
    })
```

流式工具适合「边产生边返回」的长任务（比如抓取网页逐段解析）。**调用方负责 `Close()` 返回的 `StreamReader`**。

### 3.7 错误处理包装

工具返回 error 会让整轮对话失败。多数时候你希望把错误变成文本反馈给模型，让它自己纠正：

```go
safeTool := utils.WrapToolWithErrorHandler(rawTool,
    func(ctx context.Context, err error) string {
        return "工具执行失败: " + err.Error()
    })
```

包装后工具**不再返回 error**，而是把错误信息当结果字符串返回。模型看到「工具执行失败: 连接超时」会尝试换个参数或换个策略，比直接中断好。

它自动适配 `InvokableTool`、`StreamableTool` 及两者兼备的类型，不用你判断。

## 四、把 Tool 传给 Agent

### 4.1 标准做法：ToolsConfig

```go
agent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
    Name:        "demo",
    Description: "带工具的 Agent",
    Instruction: "你是一个可以调用工具的助手。",
    Model:       cm,
    ToolsConfig: adk.ToolsConfig{
        ToolsNodeConfig: compose.ToolsNodeConfig{
            Tools: []tool.BaseTool{weatherTool, timeTool},
            UnknownToolsHandler: func(_ context.Context, name, _ string) (string, error) {
                return fmt.Sprintf("工具 %q 不存在，请只使用已提供的工具。", name), nil
            },
        },
    },
})
```

**`Model` 必须是支持工具调用的类型。** 源码注释写得很明确：

> If your ChatModelAgent uses any tools, this model must support the `model.WithTools` call option, as that's how ChatModelAgent configures the model with tool information.

也就是 `model.ToolCallingChatModel`，不是 `model.BaseChatModel`。

### 4.2 三种传递方式，别用错

| 场景 | 做法 | 结果 |
|---|---|---|
| **Agent 内部执行** | `ToolsConfig.Tools` | ✅ 模型能看到、框架会执行 |
| **只要模型「说」不执行** | `cm.WithTools([]*schema.ToolInfo{info})` | ⚠️ 模型会返回 ToolCalls，但没人执行 |
| **单次调用临时挂工具** | `cm.Generate(ctx, msgs, model.WithTools(infos))` | ⚠️ 同上，仅当次有效 |

第一种是生产用法。后两种只在你**自己接管执行**时才用——比如把工具调用转发给前端、或做 human-in-the-loop 确认。

### 4.3 ReturnDirectly：调用完立即返回

```go
ToolsConfig: adk.ToolsConfig{
    ToolsNodeConfig: compose.ToolsNodeConfig{Tools: tools},
    ReturnDirectly: map[string]bool{
        "submit_answer": true,
    },
},
```

标记的工具一旦被调用，Agent 立刻结束，不再把结果回喂模型。适合「终止型」工具：提交答案、确认订单、结束流程。

不设它的话，Agent 会继续把工具结果喂给模型，模型可能又调一次——形成无意义循环。

### 4.4 动态调整工具列表

工具很多时（几十个），全塞给模型会：
- 消耗大量 token（每个 schema 都是 prompt 的一部分）
- 降低选择准确率

Eino 提供中间件在运行时过滤。`BeforeAgent` 里改 `ChatModelAgentContext.Tools`：

```go
func (m *toolFilter) BeforeAgent(ctx context.Context, runCtx *adk.ChatModelAgentContext) (context.Context, *adk.ChatModelAgentContext, error) {
    // 按用户权限裁剪可用工具
    runCtx.Tools = filterByPermission(runCtx.Tools, principalFrom(ctx))
    return ctx, runCtx, nil
}
```

更细粒度的是 `BeforeModelRewriteState` 里改 `state.ToolInfos`——它只影响「模型看到什么」，不影响实际可执行的工具。源码里明确说这是**推荐的动态过滤方式**：

> This is the recommended approach for dynamic tool filtering/selection based on conversation context.

而**在 `WrapModel` 里用 `model.WithTools` 是明确不推荐的**：

> Modifying tools in WrapModel is discouraged: changes there are NOT persisted in state, only affect a single model call, and break prompt cache.

### 4.5 工具命名规范

模型靠名字匹配意图。几条实践：

- **用动词开头的 snake_case**：`get_weather`、`search_docs`、`write_file`
- **避免歧义前缀**：`tool_1`、`func_a` 完全无意义
- **同名会覆盖**：两个工具同名时，后者静默覆盖前者，不报错
- **不要用模型自己会做的名字**：`think`、`reason` 这类会干扰推理

## 五、完整可运行示例

```go
package main

import (
    "context"
    "errors"
    "fmt"
    "io"
    "os"
    "time"

    "github.com/cloudwego/eino-ext/components/model/openai"
    "github.com/cloudwego/eino/adk"
    "github.com/cloudwego/eino/compose"
    "github.com/cloudwego/eino/components/model"
    "github.com/cloudwego/eino/components/tool"
    "github.com/cloudwego/eino/components/tool/utils"
    "github.com/cloudwego/eino/schema"
)

type WeatherInput struct {
    City string `json:"city" jsonschema:"required,description=城市名，如 北京"`
}

type WeatherOutput struct {
    City string `json:"city"`
    Temp int    `json:"temp"`
    Desc string `json:"desc"`
}

func main() {
    ctx := context.Background()

    cm, err := newModel(ctx)
    if err != nil {
        panic(err)
    }

    weatherTool, err := utils.InferTool("get_weather", "查询指定城市的当前天气，返回温度与天气描述",
        func(ctx context.Context, in *WeatherInput) (*WeatherOutput, error) {
            return &WeatherOutput{City: in.City, Temp: 26, Desc: "晴"}, nil
        })
    if err != nil {
        panic(err)
    }

    timeTool, err := utils.InferTool("get_time", "获取服务器当前时间",
        func(ctx context.Context, _ struct{}) (string, error) {
            return time.Now().Format(time.RFC3339), nil
        })
    if err != nil {
        panic(err)
    }

    agent, err := adk.NewChatModelAgent(ctx, &adk.ChatModelAgentConfig{
        Name:        "demo",
        Description: "带工具的助手",
        Instruction: "你可以调用工具获取真实信息。回答前先确认是否需要工具。",
        Model:       cm,
        ToolsConfig: adk.ToolsConfig{
            ToolsNodeConfig: compose.ToolsNodeConfig{
                Tools: []tool.BaseTool{weatherTool, timeTool},
                UnknownToolsHandler: func(_ context.Context, name, _ string) (string, error) {
                    return fmt.Sprintf("工具 %q 不存在，请只使用已提供的工具。", name), nil
                },
            },
        },
    })
    if err != nil {
        panic(err)
    }

    runner := adk.NewRunner(ctx, adk.RunnerConfig{Agent: agent, EnableStreaming: false})

    iter := runner.Query(ctx, "北京现在天气怎么样？")
    for {
        ev, ok := iter.Next()
        if !ok {
            break
        }
        if ev.Err != nil {
            panic(ev.Err)
        }
        if ev.Output == nil || ev.Output.MessageOutput == nil {
            continue
        }

        mv := ev.Output.MessageOutput
        switch mv.Role {
        case schema.Assistant:
            if mv.Message != nil && mv.Message.Content != "" {
                fmt.Println("[assistant]", mv.Message.Content)
            }
            for _, tc := range mv.Message.ToolCalls {
                fmt.Printf("[tool_call] %s(%s) id=%s\n",
                    tc.Function.Name, tc.Function.Arguments, tc.ID)
            }
        case schema.Tool:
            fmt.Printf("[tool_result] %s: %s\n", mv.ToolName, mv.Message.Content)
        }
    }
}

func newModel(ctx context.Context) (model.ToolCallingChatModel, error) {
    return openai.NewChatModel(ctx, &openai.ChatModelConfig{
        BaseURL: os.Getenv("OPENAI_BASE_URL"),
        APIKey:  os.Getenv("OPENAI_API_KEY"),
        Model:   os.Getenv("OPENAI_MODEL"),
```

## 六、常见问题

**Q：模型为什么不调用我的工具？**

按顺序排查：① `Desc` 是否说明了「何时用」而不只是「是什么」；② 参数 `description` 是否清楚；③ 是否传了 `ToolsConfig`（而不是只在 `WithTools` 里挂了 info）；④ 模型本身是否支持 tool calling；⑤ `required` 是否把可选参数写成了必填，导致模型放弃调用。

**Q：工具返回中文/长文本会被截断吗？**

框架不截断。但工具结果会进入下一轮 prompt，过长的结果会挤占上下文。长结果建议在工具内部做摘要，或返回分页标记让模型自己翻页。

**Q：多个工具能并发执行吗？**

能，默认就是并行（`ExecuteSequentially` 默认 `false`）。如果你的工具有共享状态（比如都写同一个文件），设 `ExecuteSequentially: true`。**输出顺序始终与 `ToolCalls` 一致**，不受并发影响。

**Q：工具里能拿到当前用户身份吗？**

能，通过 `context` 传。Eino 工具签名第一个参数就是 `ctx`，你把身份放进 context，工具内部取出即可：

```go
func(ctx context.Context, in *Query) (string, error) {
    p, ok := principalFrom(ctx)
    if !ok {
        return "", errors.New("缺少身份")
    }
    // 用 p.UserID 做权限校验
}
```

**但绝不能信任模型传来的 user_id。** 模型可以被诱导编造参数，权限必须来自 context 里的可信身份，不能来自工具入参。

**Q：`InferTool` 和 `InferOptionableTool` 有什么区别？**

后者让你在工具内部收到调用方传入的 `tool.Option`。只有在需要「每次调用参数不同」时才用（比如动态超时）。日常用 `InferTool`。

**Q：工具能不能自己再调 Agent？**

能。把 Agent 包成工具用 `adk.NewAgentTool`。但官方注释明确提醒：多 Agent 全上下文共享的场景「尚未被证明更有效」，优先考虑单 Agent + 更多工具，或 `DeepAgent`。

## 七、本章小结

| 概念 | 职责 | 关键 API |
|---|---|---|
| `BaseTool` | 只描述，不执行 | `Info()` |
| `InvokableTool` | 标准执行 | `InvokableRun(ctx, json, opts...)` |
| `EnhancedInvokableTool` | 多模态输出 | `InvokableRun(ctx, *ToolArgument, opts...)` |
| `ToolsNode` | 唯一执行器 | `compose.NewToolNode` / `Invoke` |
| `utils.InferTool` | 从 struct 生成工具 | tag 驱动 schema |

五条必须记住的规则：

1. **模型只生成 `ToolCalls`，不执行任何代码**——执行发生在 `ToolsNode`。
2. **`required` 的默认是「必填」，加 `omitempty` 才可选**——与直觉相反，写错会让模型永远填不全。
3. **`UnknownToolsHandler` 必须配置**——否则模型编造工具名会直接中断对话。
4. **`ReturnDirectly` 用于终止型工具**——不设会导致无意义循环。
5. **`ToolCallID` 只在经 ToolsNode 执行时才存在**——直接调 `InvokableRun` 拿到的是空串。

一个安全底线：**权限校验用 context 里的身份，绝不用模型传来的参数。**

下一章会讲 Middleware，届时可以看到如何在工具调用前后插入横切逻辑——鉴权、审计、限流、重试，都不需要改工具本身。
