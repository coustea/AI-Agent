# 全系统统一 Markdown 渲染器设计

日期：2026-07-02
状态：已批准，待实施

## 1. 背景与问题

系统当前由 `src/shared/utils/markdown.ts` 集中拼装 Markdown-It、KaTeX、
Highlight.js 和多组文本修复正则，但部分业务组件仍包含自己的预处理逻辑。
智能辅导页面在加载历史消息时会同步执行这条链路。

`repairBrokenMultilineInlineMath` 中的正则会在同时包含多个行内公式和块公式的文本上
产生灾难性回溯。渲染发生在 Vue 主线程，因此从导航栏进入智能辅导时，历史消息一旦命中
该输入，浏览器主线程就会持续占满，表现为整个 Web 页面卡死。`keep-alive` 激活后再次加载
当前会话，会重复触发同一问题。

这不是通过调整一条正则可以长期解决的问题。当前实现还存在以下结构性风险：

- Markdown 语法修复、解析、代码高亮和 HTML 输出耦合在一个大型工具文件中。
- 业务组件可以在统一入口之外继续加工 Markdown，行为无法保持一致。
- 解析和高亮同步占用主线程，任何极端输入都可能冻结整个应用。
- 旧实现以猜测方式“修复”不规范公式，容易改变代码、货币符号和原文本含义。
- 代码展示能力围绕 Highlight.js 零散配置，缺少面向计算机教学的统一交互规范。

## 2. 目标

1. 全系统仅保留一套 Markdown 规范和一个公共渲染入口。
2. 代码展示优先：提供可靠的语法高亮、行号、语言标识、复制和横向滚动。
3. 支持行内与块级数学公式，公式和代码语法互不干扰。
4. 无论输入内容多复杂，Markdown 处理都不能冻结浏览器主线程。
5. 对 HTML 输出执行明确的安全边界，禁止模型输出注入任意 HTML。
6. 通过统一的 AI 输出契约减少脏数据，同时由渲染器安全降级，而不是猜测修复。
7. 迁移所有现有调用方后彻底删除旧解析器、旧正则修复链和业务专用预处理。

## 3. 非目标

- 不兼容旧解析器的非标准语法和错误修复行为。
- 不为历史脏 Markdown 建立兼容层或双渲染通道。
- 不在 Markdown 代码块中执行代码。
- 不自动猜测未标注代码块的编程语言。
- 不合并 `resource` 与 `path` 的记录、详情页、状态或持久化模型。
- 不重构与 Markdown 展示无关的业务页面。

## 4. 统一语法契约

全系统采用 CommonMark + GitHub Flavored Markdown，增加数学公式扩展。

### 4.1 代码

- 行内代码使用单反引号：`` `const value = 1` ``。
- 多行代码使用三个反引号围栏，并显式提供语言：

  ````markdown
  ```python
  def greet(name: str) -> str:
      return f"Hello, {name}"
  ```
  ````

- 代码围栏中的全部内容按代码处理，`$`、`$$`、Markdown 标记和 HTML 都不再解析。
- 未声明语言或语言不受支持时，以无高亮纯文本代码块展示。
- 不启用自动语言检测，避免错误高亮和不必要的计算开销。

### 4.2 数学公式

- 行内公式使用 `$...$`，不得跨段落。
- 块级公式使用独占行的 `$$` 开始和结束：

  ```markdown
  $$
  E = mc^2
  $$
  ```

- 普通美元符号使用 `\$`。
- 不规范或无法解析的公式保留可读原文，不执行跨行猜测性修复。

### 4.3 HTML 与链接

- 原始 HTML 默认关闭并按普通文本处理。
- 仅输出渲染器生成且通过安全策略允许的标签和属性。
- 链接协议只允许安全的 Web、邮件和相对地址；危险协议不进入最终 DOM。

### 4.4 AI 输出契约

所有会产生 Markdown 的模型系统提示统一引用同一份格式契约，至少明确：

- 代码必须使用带语言名的围栏代码块。
- 数学公式仅使用上述 `$...$` 和独占行 `$$` 形式。
- 不输出原始 HTML。
- 不把普通说明文字放入代码围栏。
- 流式输出时允许暂时未闭合围栏，最终消息必须闭合。

该契约只统一输出格式，不共享或合并 `chat`、`resource`、`path` 的业务数据。

## 5. 技术方案

### 5.1 解析与渲染栈

采用 Unified 生态建立显式 AST 管线：

1. `remark-parse`：解析 CommonMark。
2. `remark-gfm`：表格、任务列表、删除线和自动链接。
3. `remark-math`：识别行内与块级数学节点。
4. `remark-rehype`：将 Markdown AST 转为 HTML AST；不启用原始 HTML。
5. `rehype-sanitize`：在公式和高亮插件生成受信任标记前清理用户输入节点。
6. `rehype-katex`：将数学节点渲染为 KaTeX。
7. Shiki Rehype 集成：将围栏代码转换为语法高亮结构。
8. 自有轻量 Rehype 插件：增加代码块语言标签、行号和复制所需元数据。
9. `rehype-stringify`：生成最终 HTML。

不保留 Markdown-It 或 Highlight.js 的并行通道。

### 5.2 代码高亮

使用 Shiki 的细粒度浏览器构建，按需加载语言语法和亮暗主题。首批正式支持：

- Python
- C
- C++
- Java
- JavaScript
- TypeScript
- Vue
- HTML
- CSS
- SQL
- Bash
- Go
- Rust
- JSON
- YAML

语言别名在共享映射表中归一化，例如 `js` → `javascript`、`ts` → `typescript`、
`sh` → `bash`、`cpp` → `c++`。不在白名单中的语言直接使用纯文本。

每个代码块统一提供：

- 语言名称；
- 行号；
- 复制按钮和复制成功反馈；
- 保留缩进、换行和空白；
- 小屏幕横向滚动；
- 与系统亮色/暗色主题同步的高亮配色；
- 键盘可操作的复制控件和可访问标签。

单个代码块超过 50,000 个字符或 2,000 行时跳过语法高亮，但完整保留文本、行号和复制。
系统不截断教学内容。

### 5.3 主线程隔离

Markdown AST 解析、KaTeX 转换和 Shiki 高亮全部在专用 Web Worker 中执行。

主线程只负责：

1. 发送 `{ requestId, markdown, theme }`；
2. 展示当前安全结果或加载占位；
3. 接收 `{ requestId, html }`；
4. 仅应用最新请求的结果；
5. 绑定复制按钮事件。

Worker 请求设置 2 秒看门狗。超时或 Worker 异常时：

- 终止并重新创建 Worker；
- 丢弃过期请求；
- 当前内容降级为经过 HTML 转义的纯文本；
- 页面继续响应，且下一次渲染仍可正常工作。

流式消息更新进行 80 毫秒尾沿合并。新任务开始时取消旧请求的 UI 结果；Worker 无法中断
正在执行的单次同步插件时，由看门狗终止整个 Worker。该设计从架构上消除解析器把主线程
拖死的可能。

### 5.4 公共组件与模块边界

新增唯一公共入口：

```vue
<MarkdownRenderer
  :content="markdown"
  :streaming="isStreaming"
/>
```

职责拆分如下：

- `MarkdownRenderer.vue`：Vue 生命周期、加载/错误/降级状态、复制交互。
- `markdown.worker.ts`：Worker 消息协议和统一渲染管线。
- `pipeline.ts`：纯渲染管线工厂，不依赖 Vue 或业务状态。
- `languages.ts`：受支持语言、别名和按需加载逻辑。
- `schema.ts`：Sanitize 白名单。
- `types.ts`：Worker 请求、响应和渲染状态类型。
- `markdown.css`：文章、表格、公式、行内代码和代码块的唯一共享样式。

所有业务组件只传入原始 Markdown 字符串。禁止调用方：

- 直接导入 Unified、Remark、Rehype、KaTeX 或 Shiki；
- 通过正则修改公式或代码围栏；
- 使用 `v-html` 展示模型 Markdown；
- 建立模块专用 Markdown 渲染器。

首轮迁移至少覆盖当前已知入口：

- 智能辅导消息 `TutorMessageContent.vue`；
- 公共 Markdown 预览 `MarkdownPreview.vue`；
- 资源测验内容 `QuizView.vue`；
- 仓库搜索发现的其他 Markdown 解析、高亮和模型内容 `v-html` 调用点。

迁移完成后删除：

- `src/shared/utils/markdown.ts`；
- Markdown-It、Highlight.js 及 Markdown-It KaTeX 相关依赖和样式导入；
- `TutorMessageContent.vue` 等业务组件中的 Markdown 正则预处理；
- 其他被统一组件替代的旧渲染辅助函数。

不存在旧实现 facade、特性开关或双轨回退。

## 6. 数据流

```text
业务模块原始 Markdown
        |
        v
MarkdownRenderer.vue
        |
        | requestId + content + theme
        v
专用 Web Worker
        |
        v
Remark AST -> Sanitize -> KaTeX -> Shiki -> HTML
        |
        | requestId + safe HTML / error
        v
MarkdownRenderer.vue
        |
        v
统一样式与复制交互
```

后端模型输出通过共享提示契约约束格式，前端仍将每一段输出视为不可信输入。数据归属、
会话存储和各领域 API 不因格式统一而变化。

## 7. 错误处理

- Markdown 普通语法错误：按 CommonMark 容错规则渲染。
- 未闭合代码围栏：流式阶段稳定显示为代码；最终内容原样保留，不猜测业务含义。
- KaTeX 解析失败：显示转义后的公式源码并添加错误样式，不抛出到组件树。
- 未支持语言：纯文本代码块。
- 超大代码块：完整纯文本代码块，跳过高亮。
- Worker 超时、崩溃或初始化失败：重建 Worker，当前内容显示安全纯文本。
- 组件卸载：清除计时器、事件监听和待处理请求，避免 `keep-alive` 重复激活造成泄漏。
- 快速路由切换或流式更新：用递增 `requestId` 忽略过期结果。

任何单条消息的错误都只能影响该消息的展示，不能阻塞会话列表、导航或其他页面。

## 8. 安全设计

- 模型和用户 Markdown 始终视为不可信输入。
- `remark-rehype` 不启用 `rehype-raw`。
- Sanitize schema 只允许标准 Markdown 标签、必要链接属性及公式输入节点标记。
- KaTeX 和 Shiki 只处理清理后的 AST，并仅生成应用自身信任的结构。
- 外部链接统一补充 `rel="noopener noreferrer"`。
- 复制功能读取原始代码文本，不执行生成的 HTML。
- 降级纯文本路径必须先做 HTML 转义。

## 9. 测试策略

前端新增 Vitest 测试基础设施，并采用测试驱动开发。

### 9.1 管线单元测试

- CommonMark、GFM 表格与列表。
- 每一种受支持语言及语言别名。
- 未知语言纯文本降级。
- 代码中的 `$`、`$$` 和 HTML 不被当作公式或标签处理。
- 行内公式、块公式和无效公式。
- 原始 HTML、脚本、事件属性和危险链接被阻止。
- 超大代码块跳过高亮且内容不丢失。
- 包含旧卡死样本的回归测试在限定时间内完成。

### 9.2 Worker 协议测试

- 请求与响应 `requestId` 对应。
- 过期结果被忽略。
- 超时后 Worker 被终止并重建。
- Worker 错误触发安全纯文本降级。
- 连续流式更新只提交最新结果。

### 9.3 组件测试

- 加载、成功、公式失败和 Worker 失败状态。
- 复制按钮、成功反馈和键盘操作。
- 亮暗主题切换。
- 组件卸载和 `keep-alive` 激活不泄漏监听器或重复应用结果。

### 9.4 集成回归

- 从导航栏进入智能辅导并加载包含公式与代码的历史消息，页面保持可交互。
- 聊天流式输出未闭合与闭合代码围栏时均能稳定展示。
- 公共预览和资源测验与智能辅导使用同一组件。
- 仓库中不存在旧渲染器导入、业务 Markdown 修复正则或模型内容的非受控 `v-html`。
- `npm run build` 通过。

## 10. 验收标准

1. `src/` 中模型 Markdown 只有 `MarkdownRenderer.vue` 一个渲染入口。
2. 旧 Markdown 工具及其正则修复链被删除，无兼容代码残留。
3. Markdown-It、Highlight.js 和旧 KaTeX 适配依赖从前端依赖中移除。
4. 指定的 15 类教学语言可正确高亮，未知语言安全降级。
5. 数学公式正常显示，代码块中的公式标记不被解析。
6. 原始 HTML 和危险链接无法注入可执行 DOM。
7. 原卡死历史消息不再占用主线程；Worker 超时也不会导致导航失去响应。
8. 所有已知 Markdown 消费方迁移到公共组件。
9. 所有 Markdown 生产方遵循共享输出契约，同时 `resource` 与 `path` 数据边界保持不变。
10. 新增测试及 `npm run build` 全部通过。

## 11. 实施顺序

实施计划应按以下垂直顺序细化：

1. 建立测试基础设施并写出旧卡死样本和安全边界的失败测试。

3. 实现 Worker 协议、超时恢复和流式请求去重。
4. 实现唯一公共 Vue 组件和共享样式。
5. 逐一迁移全部调用方，并用仓库级检查封死旁路。
6. 统一后端 Markdown 输出契约。
7. 删除旧实现和旧依赖。
8. 执行构建、单元测试、集成回归和浏览器卡死验证。
