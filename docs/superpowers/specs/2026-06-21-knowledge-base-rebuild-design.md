# 知识库重建与相对路径稳健化设计

> 日期：2026-06-21  
> 状态：待评审  
> 范围：重建 Markdown→Chroma 知识库，保留语义切块，并对检索侧做小幅兼容增强  
> 约束：沿用原目录与原调用链，不重做整套 RAG 架构

## 1. 背景与目标

当前知识库已积累旧书籍内容，用户已更新原始书籍文件，希望删除旧知识库并基于新书重新构建。已有代码中，知识库构建、语义切块、Chroma 持久化、检索与路由逻辑都已存在，只是历史上经历过目录迁移与模块重组。

本次目标不是重写系统，而是在现有 `server/app/rag/*` 结构上完成一次“稳健的重建整理”：

1. 删除旧的 Chroma 持久化数据并重建新库。
2. 原始书籍目录保持不变，继续放在原来的位置。
3. 继续使用 Markdown 语义切块，而不是退回固定长度硬切块。
4. 持久化到 Chroma 的 `source` 元数据必须保存为相对路径，避免依赖机器绝对路径。
5. 检索侧做小幅兼容增强，避免因书名、目录层级或 `source` 表达变化导致召回与过滤失效。
6. 最终使用方式保持简单：以后书籍更新后，只需替换原书并重跑重建脚本。

## 2. 非目标

本次不做以下事项：

- 不重做知识路由体系。
- 不改造聊天、API 或前端交互链路。
- 不引入新的外部向量库或远程服务。
- 不设计增量建库、定时任务或后台自动同步。
- 不系统性重写评测框架，只做与本次重建直接相关的最小验证。

## 3. 现状基线

当前代码中的关键事实如下：

- 主构建入口已经迁移到 `server/app/rag/build_chroma.py`。
- 语义切块主逻辑位于 `server/app/rag/markdown_splitter.py`。
- 构建期路径常量由 `server/app/rag/rag_config.py` 提供。
- 运行时知识库目录由 `server/app/config.py` 与 `server/config.yaml` 共同解析。
- 当前构建逻辑中已经存在 `normalize_chunk_sources()`，会把 chunk 的 `metadata["source"]` 归一化为相对文档根目录的路径。
- 运行时检索依赖 `source` / canonical source identity 做路由过滤与结果融合，因此重建时 metadata 结构如果变化，检索侧必须同步适配。

因此，本次最合理的路线不是“另起炉灶”，而是：保留现有 builder 和 semantic splitter，只补齐 metadata 稳定性与检索兼容性。

## 4. 设计原则

### 4.1 保持原位置与原习惯

原始 Markdown 文档继续放在原来的目录，不要求用户调整目录结构。重建后的日常流程保持为：

1. 替换书籍文件；
2. 执行重建脚本；
3. 使用新的知识库。

### 4.2 相对路径优先，绝对路径禁入库

所有最终写入 Chroma 的 chunk 必须保证：

- `metadata["source"]` 为相对于文档根目录的路径；
- 路径分隔符统一为 `/`；
- 不允许把 `C:\...`、`E:\...` 等绝对路径持久化进向量库。

### 4.3 语义切块优先于机械切块

切块必须继续保留 Markdown 结构感知能力，尽量按标题层级、段落边界、表格/代码块边界组织 chunk；仅在内容过长时做必要的二次拆分。

### 4.4 元数据增强以服务检索稳定性

`source` 继续保留，但检索侧不能只依赖单一原始路径字符串。需要增加更稳定的辅助 metadata，并让检索匹配逻辑优先依赖规范化后的身份字段。

### 4.5 小步修改，不扩大 blast radius

只修改与“重建新库 + 保证相对路径 + 小幅检索兼容”直接相关的文件，避免把一次建库整理扩展为全量 RAG 重构。

## 5. 推荐方案

采用“保留现有建库主链路 + 增强 chunk metadata + 同步微调检索匹配”的方案。

### 方案要点

1. 保留 `server/app/rag/build_chroma.py` 作为唯一主重建入口。
2. 保留 `server/app/rag/markdown_splitter.py` 的语义切块思路，不换成新的切块框架。
3. 在切块后、入库前统一清洗与补强 metadata。
4. 清空旧 Chroma 持久化目录后重建，避免旧块与新块混杂。
5. 小幅修改 `server/app/rag/knowledge.py` 中的 source identity / source filter 匹配逻辑，兼容新的 metadata 形式。
6. 不改变上层聊天工具和 API 的使用方式。

该方案可以在最小改动下满足“删旧库、重建新库、保留语义切块、支持目录搬迁”的核心诉求。

## 6. 目标文件与职责

### 6.1 `server/app/rag/build_chroma.py`

职责：作为重建主入口，串联“加载文档 → 语义切块 → metadata 归一化 → 重建 Chroma”。

本次应承担的新增/强化职责：

- 在重建前明确删除旧的 Chroma 持久化目录；
- 在切块后统一规范化 `source`；
- 为每个 chunk 注入稳定的辅助 metadata；
- 输出必要的构建日志，便于确认新书已真正入库。

### 6.2 `server/app/rag/markdown_splitter.py`

职责：按 Markdown 结构生成语义 chunk。

本次应承担的新增/强化职责：

- 保持标题层级感知；
- 保留或补齐标题路径类 metadata；
- 确保过长内容的二次切分不会破坏基本语义边界；
- 保证输出 metadata 结构稳定，便于 builder 统一归一化。

### 6.3 `server/app/rag/rag_config.py`

职责：提供构建期的文档根目录、Chroma 目录等路径常量。

本次应承担的新增/强化职责：

- 明确文档根目录与 Chroma 持久化目录的推导关系；
- 保持和当前目录布局一致；
- 避免构建期路径与运行期路径长期漂移。

### 6.4 `server/app/rag/knowledge.py`

职责：运行时 dense / sparse 检索、source filter 匹配与结果融合。

本次应承担的新增/强化职责：

- 对新的 metadata identity 字段做兼容解析；
- 在 `source_filter` 匹配时，优先利用规范化身份字段，而不是只依赖原始 `source` 子串；
- 保持对旧字段的向后兼容，避免评测与上层调用立刻失效。

### 6.5 `server/config.yaml`（仅在必要时）

职责：提供运行时知识库目录等配置。

本次只允许最小调整：

- 若当前配置与实际 builder 输出目录不一致，则修正为一致；
- 若已一致，则不做无关改动。

## 7. 数据流设计

### 7.1 重建流程

重建流程固定为以下顺序：

1. 解析文档根目录与 Chroma 持久化目录；
2. 校验文档根目录存在且包含 Markdown 文件；
3. 删除旧 Chroma 持久化目录；
4. 递归加载 Markdown 文档；
5. 执行语义切块；
6. 遍历 chunk，统一清洗并增强 metadata；
7. 初始化 embeddings 与 Chroma collection；
8. 将新 chunk 全量写入向量库；
9. 输出构建统计信息；
10. 进行基本回归验证。

### 7.2 metadata 归一化流程

metadata 归一化必须发生在“切块之后、写入 Chroma 之前”。对每个 chunk 至少做以下处理：

1. 读取原始 `metadata["source"]`；
2. 将其解析为相对于文档根目录的相对路径；
3. 使用 POSIX 风格输出，如 `computer_network/chapter1.md`；
4. 写回 `metadata["source"]`；
5. 派生更稳定的辅助字段，供检索与过滤使用；
6. 保留 chunk 顺序与标题层级信息。

### 7.3 运行时检索流程

运行时检索仍保持当前主流程：

1. 接收查询；
2. 进行 query routing / source_filter 推断；
3. 执行 dense 与 sparse 检索；
4. 使用统一身份匹配 source_filter；
5. 进行结果融合与格式化。

本次仅改变第 4 步的匹配依据，使其对新 metadata 更稳健。

## 8. Chunk metadata 设计

### 8.1 必需字段

每个 chunk 至少需要以下字段：

- `source`：相对于文档根目录的路径，例如 `computer_network/chapter1.md`
- `chunk_index`：chunk 在原文档中的顺序编号
- `book_name`：从相对路径或文件名提取出的稳定书籍名/书籍标识
- `heading_path` 或等价字段：标题层级链路
- `source_stem`：去扩展名、规范化后的文件标识

### 8.2 兼容字段

如果现有逻辑已依赖部分字段，本次不主动删除旧字段；可以在保留原字段的基础上，新增稳定字段。

### 8.3 规范化要求

- `source` 必须无绝对盘符；
- `source` 不能带 `./` 前缀；
- `source_stem` 应是无后缀、便于比较的规范化标识；
- `book_name` 应足够稳定，不直接依赖展示文案；
- 标题路径字段缺失时允许为空，但字段结构应稳定可读。

## 9. 语义切块设计

### 9.1 总体策略

沿用现有 Markdown 语义切块主思路，不引入全新切块框架。

切块策略应遵循：

1. 优先按 Markdown 标题层级切分；
2. 在单个语义单元中尽量保持段落完整；
3. 对超长片段做必要的二次切分；
4. 避免一个 chunk 混入多个主题；
5. 避免把连续解释切得过碎，影响 embedding 语义。

### 9.2 结构保留

切块过程中应尽量保留以下语义上下文：

- 当前章节标题；
- 父级标题路径；
- 必要时的段落上下文。

这样做的目的不是增加展示字段，而是提高：

- embedding 对 chunk 主题的表达能力；
- sparse retrieval 的关键词覆盖；
- 结果解释性。

### 9.3 不退化原则

若现有 `markdown_splitter.py` 已具备语义分块能力，本次不允许将其退化为简单的固定长度硬切块。必要的长度保护只能作为补充，而不是主策略。

## 10. 相对路径与目录搬迁保证

本次要保证的不是“任意单文件移动”，而是：

- 当整个知识库目录随项目一起移动时；
- 当新的机器上项目根目录绝对路径变化时；
- 已构建好的向量库不会因为持久化了旧绝对路径而失效。

### 10.1 保证方式

通过以下手段实现：

1. 入库时只保存相对路径；
2. 运行时只依赖相对路径和规范化身份字段做匹配；
3. 所有关键目录从项目内路径推导，而不是硬编码绝对盘符。

### 10.2 边界说明

如果用户只移动原始 Markdown 的一部分文件、但不重建知识库，本次不保证旧向量库一定还能正确反映新的文档布局。该情况应通过重新运行重建脚本解决。

## 11. 检索兼容增强设计

### 11.1 问题

当前运行时检索使用 `source_filter` 与 source identity 进行课程/书籍过滤。如果新书的相对路径命名、目录分层、文件名风格发生变化，只靠旧的 `source` 子串匹配容易失效。

### 11.2 方案

检索侧调整为“多层身份匹配”：

1. 优先使用新增的规范化 identity 字段（如 `book_name`、`source_stem`）；
2. 若新增字段缺失，则回退到旧的 `source` 文本匹配；
3. 统一 canonical identity 的提取逻辑，避免 dense / sparse 各自使用不同规则。

### 11.3 兼容要求

- 老库若仍只有旧 `source` 字段，检索逻辑仍能工作；
- 新库可优先走更稳定的 identity 字段；
- 不要求上层调用者改变参数结构。

## 12. 错误处理

只做必要错误处理，不额外引入复杂恢复逻辑。

### 12.1 构建阶段

- 文档根目录不存在：直接报错，输出解析后的绝对路径；
- 文档目录下没有 Markdown 文件：直接失败，不创建空库；
- 连接 embedding 服务失败或模型不可用：直接失败，输出模型与地址；
- chunk 缺失 `source`：写入可识别的回退值并打印告警；
- 删除旧库失败：直接失败，禁止新旧库混用。

### 12.2 检索阶段

- 新 metadata 字段缺失：自动回退到旧字段匹配；
- metadata 不完整：尽量降级可用，而不是直接崩溃；
- 若 source_filter 无法命中新字段，则允许继续尝试旧逻辑。

## 13. 可观测性与验证

### 13.1 重建脚本应输出的最小信息

- 原始文档数量；
- 切块总数；
- Chroma 目标目录；
- 若干个 chunk 的 `source` 示例；
- 是否检测到绝对路径残留。

### 13.2 最小完成标准

完成后必须满足：

1. 旧 Chroma 持久化目录已清空并重建；
2. 新 Markdown 书籍已全部重新入库；
3. 抽样 chunk 的 `source` 为相对路径；
4. 代码中不存在把旧绝对路径持久化进向量库的路径；
5. 检索入口能够正常命中新书内容；
6. source filter / canonical identity 匹配在新 metadata 下仍然可用。

### 13.3 建议验证方式

至少覆盖以下验证层次：

- builder 级：验证 `normalize_chunk_sources()` 与 metadata 增强逻辑；
- retrieval 级：验证 canonical identity / source filter 在新旧 metadata 下都能工作；
- smoke test：运行一次真实重建，并对新书执行 1~3 个基本查询。

## 14. 预期结果

完成后，知识库模块将具备以下特性：

- 能基于更新后的书籍全量重建；
- 不再把机器绝对路径写入 Chroma；
- 在目录整体迁移后仍可使用；
- 保留 Markdown 语义切块能力；
- 对书籍路径与命名变化具有更强的检索稳健性；
- 用户未来更新书籍时仍保持简单操作方式：替换原书并重跑重建脚本。

## 15. 实施边界总结

本设计是一次“在现有结构上稳健重建知识库”的收敛式改造，不是重写知识检索系统。它的重点在于：

- 重建；
- 相对路径；
- 语义切块；
- 检索兼容；
- 保持简单使用方式。

超出这些边界的优化（如系统性路由升级、大规模评测重构、平台化建库工具）不在本次范围内。
